# 收件 · intake

**受理现场需求与 BUG 的独立进件服务** —— 给产品经理 / 现场实施用，产出结构化、可被 AI 直接分析的进件，喂回各项目的开发流程。

> 从 **steward**（多项目研发编排中枢）会话里孵化、拆分出来的独立项目。与 steward 物理隔离，两者唯一耦合是各项目 git 里的 `docs/`。

## 是什么
- 现场/产品经理从被交付产品里点"反馈"，进到收件的 H5：**选需求/BUG → 填结构化表单 → AI 沟通补全、给处理意见 → 归档**。
- 提交带**产品版本（git tag）+ 现场**，开发侧按版本分析、切对应版本修复。
- 收件**只接收 + 沟通 + 归档**，不做开发、不生成任务；真正的分析/开发由本地 steward 跑 `/intake`。

## 核心原则（务必先读）
1. **版本 = git tag**，specs 留在各产品代码仓库（随 tag 快照）。
2. **intake 独立成库**（intake-store），收件写自己的库，**对产品代码仓只读**。
3. **绝不把密钥入库**；公网面必须认证。

## 目录
- `开工指引.md` —— **开工工单**（里程碑 M1/M2/M3 + 硬约束 + 待定项）。
- `docs/架构设计.md` —— 权威架构设计（边界 / docs 契约 / 版本=tag / 数据流 / 字段 / 未来 skill / 待定项）。
- `docs/沟通记录.md` —— 立项来龙去脉与历次决策（从 steward 会话迁移）。
- `prototype/` —— 从 steward 搬来的原型种子（`submit.html`、`model-config.html`、`server.mjs.reference`、Tabler 图标）+ `说明.md`（怎么提取后端）。

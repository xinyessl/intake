# CHG · TK-01 / 状态机 · 开发侧流转（开发中/已出包/待验证）不再由运营端手动逐条点

> 日期：2026-07-30　类型：逻辑/流程调整（涉及 spec：TK-01 + SPEC-工单状态机-001）　来源：用户裁决
> 页面：public/detail.html 工单详情「工单操作」面板

## 背景 / 决策
两条线设计（BP-01 / P0 §E）：**运营端** 负责到「已落实·排期(已立项 + 归批次)」为止；**开发侧(steward/研发)** 负责 `开发中 → 已出包(发包) → 待验证`（应由 steward 进度回写驱动，P2）。
实践中发现：运营端在详情里**逐条手点「进入开发」**属重复劳动，且是**状态漂移的根源**——用户以为点过了、实际"进入开发"是两步操作（点按钮只展开备注表单、需再点"确认"），漏了确认就没生效（实测工单 BUG-20260724-01 history 里根本无 `已立项→开发中`）。
**用户裁决（2026-07-30）**：运营端**不必**逐条「进入开发」；运营流程终点=「已落实·排期」，开发/交付段交给 steward 回写（未上线前停在"已立项"当作"已交接进开发管道"）。

## 改动
- `public/detail.html`：新增 `STEWARD_STATES = {开发中, 已出包, 待验证}`，`nextStates()` 过滤掉这三个开发侧/交付流水线态 → 详情「工单操作」面板**不再出现「进入开发 / 标记出包 / 转待验证」按钮**。
- 运营端保留自己该点的：`AI 分析初判`、`回复现场(已回复)`、`立项(已立项)`、`暂缓`、`驳回`、`关闭`、`重开`。
- 已在 `待验证` 态的工单仍有独立「验证处理结果(通过/打回)」卡（`doVerify`，不受影响）。开发/发包进度改为**只读展示**（lifecycle 徽标 + history + resolution，等 steward/批次回写）。

## 影响面
- 后端 `intake-transition` 不改（仍支持全部流转，只是运营端 UI 不再暴露开发侧按钮；steward 对接 P2 落地后由其驱动 开发中/已出包/待验证）。
- 存量已在 开发中/已出包 的工单：运营端只显示「关闭」(+AI初判)，符合"开发侧状态运营不手动推进"口径。
- 若将来需运营手动兜底推进（steward 未上线期间的应急），可在 STEWARD_STATES 加开关放开——当前按用户决策默认隐藏。

## spec 同步
TK-01 / SPEC-工单状态机-001 注明：`开发中/已出包/待验证` 为**开发侧(steward 回写)**状态，运营端不手动流转；运营端可操作集 = 回复/立项排期/暂缓/驳回/关闭/重开 + AI初判。

## 部署 / 验证
rsync `detail.html` → 线上（静态即时生效）；服务器确认 `STEWARD_STATES` 已在。已立项工单详情操作面板刷新后只剩「AI 分析初判 / 关闭」。

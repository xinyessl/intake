# CHG · 深入思考(deep-think)咨询答疑提示词 —— deep 分支强约束「据源码作答 + 点名出处 + 禁臆造」

- 日期：2026-08-06
- 关联 spec：无（纯 bug 修复 · 提示词调优；FS-06「深入思考」行为契约不变——「结合已检索源码更深入解释成因/实现」这条 spec 意图本就如此，是模型没落实，spec 是对的，无需同步 diff）
- 类型：纯 bug 修复（提示词）
- 改动范围：仅 `server.mjs` 的 `consultSystem(proj, ver, hits, specs, code)`（约 L891~906）的提示词字符串。函数签名、`codeSearch`、调用处（L2087/L2094）、返回结构、**非 deep 分支行为**均不动。

## 一句话
「深入思考」把真实源码片段喂给了模型，但旧提示词反复强调「优先依据相关规格摘录」、把「结合源码片段」写成软话，导致模型锚定「摘录里没有→泛泛答」，拿到源码却不引用、还臆造表名当答案。改为 **deep（有 code）分支切换"优先级"到源码片段、并加四条强约束**：必须落在源码上点名出处、禁开口说「摘录未包含」当没料、禁把猜测当事实、保留翻译大白话+以开发确认为准。**非 deep 分支一字不改**（仍「优先规格摘录」）。

## 已诊断根因
- `consultSystem` 提示词规则第 1 条恒为「**优先依据上面「相关规格摘录」里的真实内容作答**」，deep 分支只追加一条「可以结合源码片段更深入地解释」的**软措辞**。
- 模型据此把规格摘录当第一优先，源码当"补充"；当摘录不覆盖问题时，直接答"未包含"+ 通用 HIS 排查话术 + 臆造表名（如"常见如 `drug_instruction`""大概率在 kwsb"），**完全没用已喂入的源码片段**。
- 实测：pwrs 问「医嘱列表中的药品说明书在哪里配置」，深入思考已把 `intervention.vue`（`onDrugPath`→`$openUrl(...config.value)`、`v-if="config.open"`）喂给模型，但答复开头「根据目前提供的规格摘录，**未包含**…」，随后泛泛排查 + 臆造表名。

## 改了什么（只动 consultSystem 提示词字符串）
1. **`codeTxt` 导语加强**：把源码片段从"可据此更深入地解释"升格为"**本次回答的主要依据**，请据此说清该功能实际是怎么实现的"（每条含文件路径 + 具体代码）。
2. **规则分叉**：`deep`（有 code）与非 deep 走**两套规则文案**（`${deep ? `…` : `…`}`）：
   - **deep 分支（新）**——首条即「**请优先结合源码片段作答（规格摘录为辅），并点名源码出处**」，下挂四条：
     · 必须把答案落在源码片段上、点名具体出处（哪个文件/组件/函数，说清实际怎么做的，如「在 `intervention.vue` 的 `onDrugPath` 里…点按钮走 `$openUrl(...config.value)` 打开外部链接、由 `config.open/config.value` 控制」），而非泛泛排查话术；
     · **既然已检索到相关源码，就据源码作答，禁止开口说「规格摘录未包含/未收录/没有相关资料」当没料**——摘录只是补充，别把深入思考答成"我没有资料"；
     · **禁止把猜测当事实**：不写「常见如 `xxx_table`／大概率在 xxx」这种臆造表名/接口/字段当答案；只讲源码里实际出现的，源码没显示的（如后端落库表名）如实说"源码片段里只看到这段前端/这段逻辑，具体 XX 需看后端代码或问开发"，别编；
     · 保留原两条：① 翻译大白话、绝不贴大段代码；② 标注"这是根据代码实现推断的，最终以开发确认为准"。
     · 规格摘录降为补充：相关时可点名引用，源码与摘录都没有才说不确定 + 建议下一步。
   - **非 deep 分支（不变）**——维持原「优先依据相关规格摘录」两条，一字未改。
3. 收尾三条（能答就答/该转工单就明说/不臆造 spec·源码里没有的表字段；非 deep 保留"不写具体代码实现"）保持原样。

- **修复前（旧提示词）**：端到端 `/api/consult` 答复开头「当前提供的规格摘录与源码片段中，**未包含**"医嘱列表药品说明书"的配置入口…不在本次 `pwrs` 业务 spec 覆盖范围内」→ 通用 HIS 三段排查话术 + 臆造「内置知识库/第三方对接/静态附件」+ 断言"底层依赖的知识库表名/字段名需研发确认"，**全程未引用 `onDrugPath`/`$openUrl`**。

## 验证方式与一处重要观察（诚实记录）
- **提示词改动本身**：连 prod 真模型 A/B（BEFORE=git HEAD 版 `consultSystem` vs AFTER=已部署版），**注入诊断所指的 `intervention.vue` 片段**作 `code`，证明"当该片段到达模型时"新提示词让答复从"未包含+臆造表名"变为"点名 `onDrugPath`/`$openUrl`/`config` + 不臆造后端表名"。✅
- **端到端 `/api/consult`（deep=true）真跑同问题**：`codeSearch` 排序把 `intervention.vue` 排到 top-1（2026-08-05 稀有词加权 CHG 已修排序），但**本次抽取的片段窗口未包含答案行（L301 `查看药品说明书` / L1610-1613 `onDrugPath`/`$openUrl`）** —— 根因是 `codeSearch` 取片时 `f.lines.size < 40` 的行预算被大量 `医嘱` bigram 命中行先占满 + `slice(0,1500)` 从文件顶部截断，导致靠后的答案行落在窗口外。**这是与提示词无关、也与排序 CHG 不同的另一处"取片窗口"检索缺口**，本次严格按任务范围**未改**（诊断限定"只改提示词"、且判定"源码已能检索到"）。
  - 影响：当深入思考实际捕到答案行（如问法/词频让答案行进窗口，或后续修 windowing 后），新提示词即生效、按上面"修复后"效果引用源码。当前该特定问法下答案行未进窗口时，新提示词仍据"进了窗口的那段 intervention.vue"作答、且不臆造表名（比旧版仍更稳），但引用不到 `onDrugPath` 那几行本身。
  - 建议（**留给后续、非本次范围**）：另开一条修 `codeSearch` 取片——命中行按"稀有词优先"选进 40 行预算（别让大众 bigram 挤占）、或对每个稀有词命中行强制保留其 ±6 窗口，使 top 文件里"最判别性的匹配行"一定进片。

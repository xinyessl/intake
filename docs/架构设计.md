# 收件 `intake` —— 云端进件服务（需求 / BUG 提交）架构设计手册

> **项目名：收件 / `intake`**（独立 git 仓，与 steward 分开开发）。
> 目标：让**产品经理 / 现场实施**从被交付产品里提交**结构化**的需求 / BUG，AI 直接可分析；提交带**产品版本**，开发侧按版本分析、切对应版本修复。
> 定位：**独立于 steward 的一套干净服务**，与 steward 控制台物理隔离；两者唯一耦合是各项目 git 里的 `docs/`。
> 状态（2026-08 更新）：✅ **已抽出为独立服务并上线生产**。进件/对话/写盘早已从 steward 原型迁出，落地为本仓 `server.mjs`（单文件后端）+ `public/*.html`（前端）+ MySQL/文件存，且在此之上扩出工单管理、批次与发包、版本发版累积更新+合并SQL、部署清单、医院管理+维保提醒、经验库语义检索、模型配置、双域名部署等全套能力。**本文 §9/§10 的"迁移/待办"均已完成，仅作历史存档。现状看 `README.md` + `docs/specs/*`（21 份，系统事实源）+ `docs/board.md`。**

## 0. 决策纪要（已拍板）
1. **云端进件 = 单独一套干净服务**，不做进 steward（steward 控制台能起 `claude`/开终端，绝不暴露公网；进件是半公开面，权限面完全不同，物理隔离）。
2. **两系统唯一契约 = 各项目 git 的 `docs/`**，不互相调 API（符合"文件即接口"）。
3. **版本 = git tag**：一个产品发布版本 = 项目仓库一个 tag（如 `v1.3.0`）。`docs/specs/` 随 tag 原子快照，取某版本 spec = `git show v1.3.0:docs/specs/x.md`，不另建 spec 版本库。
4. **specs 留在代码仓库**（搬出去会拆掉"版本=tag"，且丢掉"checkout 一个 tag，spec+代码一起就位"）。
5. **intake（提交进来的需求/BUG）独立成一个 git 仓**（intake-store）：进件服务写自己这个库，**对代码仓库只读**。
6. 结果：进件服务**永不写代码仓库** → 上一版纠结的"公网表单要不要 push 到 main / 开 PR"消失；真正的 spec/代码改动仍由开发在代码仓库走正常 `/build`，一道人审。

## 1. 三套系统边界（别混）
| 系统 | 是什么 | 部署 | 对代码仓库的权限 |
|---|---|---|---|
| **被交付产品** | 潮夕夕 / pams… 跑在各现场 | 各现场 | —（内嵌"反馈"入口，见 §6） |
| **云端进件服务** | 提交 H5 + 对话 + 写 intake-store | 公网/内网服务器 | **只读**（读 tag 列表 + `spec@tag`） |
| **本地 steward** | 开发控制台，跑 `/intake`·`/build` | 开发本机 | 读写（正常开发） |

## 2. 唯一契约：`docs/` 的分工
| 目录 | 本质 | 放哪 | 谁写 |
|---|---|---|---|
| `docs/specs/`（+ `lessons.md`、`changes/`） | **产品的一部分**，随版本走 | **代码仓库**（随 tag 快照） | 开发（`/spec`·`/build`） |
| **intake 条目**（需求/BUG 提交） | **操作数据**，只*引用*某版本 | **独立 intake-store 仓** | 进件服务 + 开发回填 |

## 3. spec 版本管理 = git tag（唯一纪律）
- **每次给现场发版就打 tag**（如 `v1.3.0`）；需长期修补的版本再开 `release/1.3.x` 分支。
- 版本下拉候选 = 该项目仓库 `git tag -l`（过滤 release tag），或 `?ver=` 链接自动带。
- spec 头部沿用现有 `status`；若确需"某 AC 哪版加的"，顶多加 `since:` 标记——**起步别过度设计，tag 就是版本**。

## 4. 数据流（提交 → 分析 → 切版本开发 → 回填）
```
产品@现场 ─提交(project, version=tag, site, 结构化正文)→ 云端进件服务
                                                          │ ① 只读代码仓：tag 列表 + spec@tag（喂 AI 上下文）
                                                          │ ② AI 对话补全字段 / BUG 给初步处理意见
                                                          │ ③ 写 intake-store（该项目目录，status=待处理）
本地 steward ─ git pull intake-store ─ /intake <id> ─────►│
                                                          │ 读代码仓 spec@tag 做版本感知分析（§8）
                                                          ▼
                       修复/改 spec 走正常 /build，落进【代码仓库】（开发亲自 + 人审）
                       回填 intake-store：该条 status=已处理，关联 commit/PR + 修复版本
```

## 5. intake-store（独立 git 仓）结构
统一一个 intake 仓、按 project 分目录（也可每项目一个 `<project>-intake` 仓）：
```
intake-store/
  README.md
  <projectId>/
    BUG-20260707-01.json     # 事实源（结构化字段 + 沟通记录）
    BUG-20260707-01.md       # 人读渲染（frontmatter + 正文 + 沟通 + AI意见）
    XQ-20260707-01.json/.md
    media/<id>/img-*.png      # 截图
```
- status 用 frontmatter 字段驱动，**不挪文件**（列表按 status 过滤）。
- markdown 可读可 diff，开发 `git pull` 直接拿——保持"文件即接口"。

## 6. 进件条目结构（frontmatter 字段）
在现有字段基础上，**新增 `version` + `site`**（把"定位到人"扩展为"定位到人 + 现场 + 版本"）：
```yaml
id: BUG-20260707-01
type: requirement | bug
project: pams
version: v1.3.0          # ★ 新增：产品版本(git tag)，BUG 必填、需求选填
site: 北京协和           # ★ 新增：现场/客户，便于归并与回访
module: 审方             # 对应 spec 模块（可空）
title: …
reporter: 张三           # 定位到人
contact: 138…            # 便于回访
role: 现场实施 | 产品经理 | 其他
priority: 紧急|高|中|低
# —— BUG 专有 ——
severity: 阻塞|影响使用|轻微
scope: 单用户|批量|全部
env: 生产|预发|测试|开发
freq: 必现|偶现
status: 待处理 | 沟通中 | 已归档 | 已处理
submittedAt: 2026-07-07 15:40
linkedSpec: SPEC-审方-002   # 分析后回填
resolution:                 # 处理后回填
  commit: <sha> / PR#
  fixedIn: v1.4.0
  backportedTo: [v1.3.1]
```
**版本别靠人填（填不准）——靠链接带**：产品内嵌"反馈"入口打开
`https://<进件服务>/submit?project=pams&site=北京协和&ver=v1.3.0&type=bug`
`ver` 由产品自己的构建版本注入 → 提交页**预填并锁定** project/site/version，用户只描述问题，版本 100% 准确。直接打开页面的人 → 退回手选/手填兜底。

## 7. 进件服务职责与接口
- **读代码仓（只读）**：`git tag -l`（版本下拉）、`git show <tag>:docs/specs/**`（喂 AI 的版本上下文、模块清单）。可用本地 checkout 或裸仓库 mirror。
- **写自己库**：把提交 + 沟通写入 intake-store，commit/push（凭证只对 intake-store 有写权）。
- **对话**：接模型 API（API Key 配置，非交互登录；配置只存服务本机，不入库、掩码回传）。系统提示引导补全字段、BUG 给处理意见、信息够了归档。
- **认证**：公网面必须有登录/令牌（现场账号或一次性提交链接），不裸奔。

## 8. 版本感知分析（`/intake` skill 要做的判定）
开发侧 `/intake <id>` 读"条目 + `spec@version`"，三类判：
1. **该版本 spec 本就这样** → 不是 bug（可能是新需求）。
2. **违反该版本 spec** → 是 bug；再 diff `spec@version` vs `spec@main` / 查 `docs/changes` → 判断**新版是否已修**（可回复现场升级）/ **要不要 backport** 到 `release/x.y`。
3. **全新诉求** → 进下一版 spec，走正常 `/spec`·`/build`。
- 切版本开发：从 tag 或 `release/x.y` 开 hotfix 分支修 → forward-port 回 main → 回填 intake-store。
- **多现场归并**：同一现象多现场/多版本报回 → 按 title/module 聚合，看"通病 vs 某版本回归"。

## 12. 升级：开发 ↔ 现场「闭环迭代平台」（2026-07 对齐，取代"只收件"定位）

> 背景：原定位是"收件只收 + 沟通 + 归档，不做开发"。现升级为**贯穿产品线迭代的闭环沟通平台**：
> 接收需求/BUG → AI 分析初判 → 能解决直接回复、不能解决立项 → 开发 → 出包/发版 → 现场验证 → 关闭，全流程在平台里跟踪、可回溯。

### 12.1 三条已定边界（决策，NEEDS-HUMAN 已裁）
1. **平台定位 = 工作流 + 跟踪中枢**：平台管"流转 / 沟通 / 状态"，**真正写码 / 出包仍在 steward + 代码仓完成**，平台靠**状态回填**联动。→ 继续守住"平台对代码仓只读、绝不写产品码、intake-store 独立"。
2. **问题分析 = 平台内 AI**：平台用已配模型 + 已能读的 `spec@版本`，直接给**初判**（该版本本就这样=非bug／违反spec=bug、diff 新版判断是否已修／全新诉求=需求）+ 建议（直接回复 or 立项）。steward `/intake` 仍可做**深度复核**，非取代。
3. **账号 = 两类角色**：**开发方（公司）** 与 **现场方（实施/产品）** 两类账号，**服务端按角色鉴权**（认证从"可选"升为"必须"）。载体延续 §11：管理端口令 + 提交页 token 链接，之上加角色。

### 12.2 工单生命周期（状态机，详见 `docs/specs/SPEC-工单状态机-001.md`）
```
待处理 → 分析中 →┬─(能解决)→ 已回复 ──(现场确认)→ 已关闭
                └─(不能解决)→ 已立项 → 开发中 → 已出包 → 待验证 ─┬─(通过)→ 已关闭
                                                                   └─(不通过)→ 已重开 → 开发中
现场补充需求 / 版本修正现场问题：可对同一现象追加或新建，全程留痕、可回溯。
```

### 12.3 角色 × 权限（谁能做什么）
| 动作 | 现场方(实施/产品) | 开发方(公司) |
|---|---|---|
| 提交需求/BUG、补充需求、看自己现场的工单与进展 | ✅ | ✅(可看全部) |
| AI 分析初判、回复现场、立项、流转状态、关联版本/commit、关闭 | ✕ | ✅ |
| 现场验证（待验证 → 通过/不通过） | ✅ | ✅ |
| 项目管理、模型配置 | ✕ | ✅(管理员) |

### 12.4 数据落点（仍"文件即接口"）
工单的状态流转 / 分析 / 处理全部落 **intake-store 的 `<id>.json/.md`**，新增字段：
`lifecycle`(生命周期状态)、`history[]`(流转留痕：from→to/操作人/角色/时间/备注)、`assignee`、`analysis{verdict,category,suggestion,at}`、`resolution{commit,pr,fixedVersion,note,at}`；沟通 `chat[]` 的 role 扩展为 `user`(现场)/`assistant`(AI)/`dev`(开发)。steward `git pull` 即拿到，回填后 `push` 即回流。

### 12.5 分阶段落地（M4 起）
- **M4 闭环骨架**：工单状态机 + 平台内 AI 分析初判 + 开发侧工单操作台（回复/立项/流转/关联版本/关闭）+ 现场侧进度跟踪与验证。（本机先跑通，角色先作为概念标注）
- **M5 双向账号与鉴权**：开发方/现场方账号 + 服务端角色中间件 + 提交页 token。
- **M6 联动与看板**：版本/出包联动、状态变更通知、产品线迭代看板与回溯。

## 13. 持久层：MySQL 为准 + .md 双写（2026-07 对齐，取代"纯文件落盘"）

> 背景：早期数据落 `data/*.json` + `intake-store/<id>.{md,json}` 纯文件。为便于**结构化查询/报表/多维统计**，改为 **MySQL 持久化**；同时保留 `.md` 导出以延续"文件即接口"给 steward `git pull`。

### 13.1 决策
1. **业务数据全进 MySQL**：`projects`（含 `subsystems` JSON）、`accounts`、`sessions`、`intakes`（工单）、`kb_entries`（经验库）。**MySQL 为唯一事实源**。
2. **模型 API Key 不入库**：仍存收件本机文件（密钥不落库、GET 掩码），见 §7/安全红线。
3. **`.md/.json` 双写保留**：工单每次保存同时导出 `intake-store/<project>/<id>.{md,json}`，延续"开发 git pull intake-store"契约（§2/§5）；DB 为准、文件为可读镜像。
4. **引入 `mysql2` 依赖**：突破早期"零依赖"约定——MySQL 必需，已人裁认可。

### 13.2 运行架构（读缓存 · 写穿透）
- **启动**：连库→建表(IF NOT EXISTS)→`loadAll()` 把全库读进**内存缓存**；库某实体为空且旧文件在 → 一次性迁移入库。
- **读**：全部走内存缓存（`loadProjects/projById/loadIntake/listIntake/loadAccounts/loadKB/currentUser` 等保持同步、调用点不改）。
- **写**：`saveIntake/saveProjects/saveAccounts/saveKB` = 更新缓存 + `await` 写 MySQL（落库失败即报错）+ 导出 `.md/.json`；会话写库 fire-and-forget。
- *取舍*：单实例本地工具，读缓存换取"读路径零改动"；**直接改库需重启服务才反映**（后续可加轮询/触发刷新）。

### 13.3 库结构（`db.mjs`）
- 关键可查字段建成**列**：`intakes(project_id,id,type,version,site,subsystem,module,title,priority,severity,env,freq,status,lifecycle,assignee,reporter,submitted_at)`；嵌套（正文/`chat`/`history`/`analysis`/`resolution`/媒体）放 `data` JSON 列。工单主键 `(project_id,id)`（id 按项目内生成，跨项目可重）。
- `kb_entries(id,project_id,q,a,subsystem,module,tags,source,from_ref,created_at)`；`accounts`/`sessions`/`projects` 各一表，列 + JSON（projects.subsystems / accounts.projects·sites）。

### 13.4 配置与安全
- 连接配置 `data/db.json`（**gitignore**，含库口令），可用 `INTAKE_DB_HOST/PORT/USER/PASS/NAME` 环境变量覆盖。
- 本地默认：`intake@127.0.0.1:3306/intake`（Docker MySQL 8）。

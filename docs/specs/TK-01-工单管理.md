## 1. 用户故事 / 目标
作为**收件运营后台的产品经理 / 运营**，我要在一个页面里**受理并统一处理全部现场工单**——按状态流水线一眼看清各阶段积压、用富筛选快速定位、在「开发会议决策抽屉」里对待评审工单做**落实开发 / 直接答复 / 暂缓·驳回**三选一决策并留痕、对已决策工单查看**摘要 + AI 初判 + 流转留痕 + 附件**，以便让工单顺畅走完「评审 → 决策 → 排期 → 开发 → 交付」全流程。

> 注：本 spec 是**工单模块的单页综合规约**，对应原型单页 `admin/tickets.html`（列表 / 流水线 / 处理抽屉 / 详情四合一）。它**依赖并内联引用**状态机扩展点（见 §5.3，独立数据模型 spec `DM-02` 承载底层枚举/流转，本 spec 从 UI 与决策角度约束其行为）。spec 清单中的 `TK-02/TK-03` 若单列，其 AC 均被本 spec 覆盖。

## 2. 范围
- **包含**：
  - **状态流水线**：待评审 → 已落实·排期 → 开发中 → 已交付，＋ 已关闭聚合（含 已答复/暂缓/已驳回）；点每环按该状态筛列表。
  - **富筛选（选择即查）**：产品 / 子系统（随产品联动）/ 类型 / 状态 / 客户 / 提交人 / 提交日期范围 / 关键词，＋ 分页；筛选条件同步流水线高亮。
  - **列表**：编号 / 类型 / 标题（含产品副行）/ 子系统 / 客户 / 版本 / 状态（含停留·超期 chip）/ 提交人 / 更新时间 / 操作。
  - **工单处理决策抽屉**（核心「处理逻辑」）：三选一——① 落实开发（→ lifecycle `已立项` + 归入批次）② 直接答复（→ `已回复` + 回复内容，可勾选沉淀经验库）③ 暂缓 / 驳回（→ 新增态 `暂缓` / `已驳回` + 原因）；接现有 `POST /api/intake-transition`；决策写入 `history` 留痕。
  - **工单详情抽屉**：摘要 + AI 初判（`POST /api/intake-analyze`）+ 对话 / 流转留痕（`chat`/`history`）+ 附件（`GET /api/intake-media`）+ 决策回复；「沉淀到经验库」入口。
  - **后台代提工单**：运营代现场提交 需求/BUG/咨询（复用 `POST /api/intake-submit`）。
  - **导出**：复用 `GET /api/intake-export`（CSV）。
- **不包含**（另立 spec，本 spec 仅调用/预留）：
  - 批次表本身与批次管理（列表/详情/封板）→ `BP-01`；本 spec「落实」时**归入批次**只调用 `POST /api/batch-tickets`（BP-01 就绪前退化为「落实不带批次」，见 §5.2 与 `NEEDS-HUMAN-2`）。
  - steward 拉清单 / 回写进度 / 发包（`ST-01/02/03`）、版本回写（`customer-version`）。
  - 客户/账号/产品/经验库/模型的管理页（`CU/AM/PD/KB/MC`）。
  - AI 初判的**模型调用实现**（复用现有 `intake-analyze`，本 spec 只约束触发与展示）。

### 列表 / 筛选 / 流水线
- **AC-1（列表列齐全）【原型·已落地】** Given 已登录运营账号且当前产品下有工单 When 打开 `inbox.html`（工单管理）并请求 `GET /api/intake-list?project=` Then `.data-table` 每行渲染原型列 **编号/类型/标题(含产品或现场副行)/子系统/现场/版本/状态/提交人/更新时间/操作** 共 10 列；`type` 英文（bug/requirement/consult）映射中文徽标（BUG/需求/咨询，`.tag-bug/.tag-req/.tag-consult`）；`updateTime` 经共享 `fmtTime` 按 `yyyy-MM-dd HH:mm` 格式化，空值 `—`。〔真实数据无独立「客户」字段 → 原型「客户」列用真实 `site`（现场）承载，见 §5.4〕
- **AC-2（默认排序）【原型·已落地】** Given 列表有 ≥2 条工单 When 渲染 Then 列表按 `updatedAt`（无则 `submittedAt`）**倒序**（最新在前，后端 `listIntake` 已倒序，前端保持）。
- **AC-3（流水线计数）【原型·已落地】** Given 当前产品各状态均有工单 When 渲染顶部 `.pipeline` Then 显示 5 环 **待评审 / 已落实·排期 / 开发中 / 已交付 / 已关闭**，每环 `.ps-count` = 该环映射的真实 `lifecycle` 集合的工单数（映射见 §5.1：待评审=待处理+分析中；已落实·排期=已立项；开发中=开发中；已交付=已出包+待验证；已关闭环=已回复+暂缓+已驳回+已关闭）；计数随筛选联动。
- **AC-4（点流水线筛选）【原型·已落地】** Given 点某环 When 点击 Then 按该环 lifecycle 集合过滤列表、`.pipeline-step.active` 高亮、页码重置为 1；再点同环取消筛选（回全部）；状态下拉与流水线高亮同步（选某具体态时对应环高亮）。
- **AC-5（选择型筛选即选即查）【原型·已落地】** Given 处于工单管理页 When 改变 产品/子系统/类型/状态/现场 任一下拉 或 选日期范围 Then **不点查询按钮**即本地过滤重渲染、页码重置为 1（全局规范 §11）；产品下拉切换重新拉该产品 `intake-list`；子系统下拉随所选产品的 `subsystems` 联动。
- **AC-6（关键词搜索）【原型·已落地】** Given 关键词输入框 When 输入文本按回车（自由文本 → 回车触发，全局规范 §11） Then 按 标题/编号 大小写不敏感包含匹配本地过滤、重置到第 1 页。
- **AC-7（日期范围框）【原型·已落地】** Given 提交日期用单个 `.range-box`（起 ~ 止，全局规范 §9） When 选起/止日期 Then 按 `submittedAt` 日期部分（`yyyy-MM-dd`）区间过滤、即选即查、重置到第 1 页。
- **AC-8（分页正确）【原型·已落地】** Given 过滤后共 N 条、每页可选 10/20/50（原型 `.page-size-select`，默认 10）When 翻页/改每页数 Then 显示第 p 页切片，`共 N 条 · 第 p 页` 与页码器一致；过滤结果为 0 时展示 `.empty` 空态「没有匹配的工单」。
- **AC-9（筛选重置）【原型·已落地】** Given 点「重置」按钮 When 点击 Then 清空全部筛选项（产品保持当前）、`state.filters` 清空、回第 1 页、流水线高亮清除。

### 处理决策（核心）— 原型「工单处理决策抽屉」三选一
> **【原型·已落地】** 点列表行「处理」（待评审态 = `待处理`/`分析中`）打开 `.drawer#processDrawer`「工单处理 · 开发会议决策」：先渲染工单摘要 + AI 初判，再 `.decision-option` 三选一（落实开发 / 直接答复 / 暂缓·驳回），选中态 `.selected` 高亮、展开该分支的表单。「确认处理」按当前选中分支调 `POST /api/intake-transition`（`to` 不同）。非待评审态行点「查看」进查看抽屉。三分支后端行为（AC-13/15/17/18）已实现+连真库测试，本轮落抽屉 UI。

- **AC-11（可处理入口）【原型·已落地】** Given 列表某行 When 渲染「操作」列 Then 待评审态（`待处理`/`分析中`）显示「处理」（`ti-gavel`，打开处理决策抽屉），其余态显示「查看」（打开查看抽屉）；管理员可处理，现场(field)角色无「处理」入口（`intake-transition` 后端亦鉴权，AC-26）。
- **AC-12（处理抽屉摘要 + AI 初判）【原型·已落地】** Given 打开 `#processDrawer` Then `.summary-block` 展示 类型徽标/编号/提交时间/标题/提交人/现场/产品·子系统/版本/描述（+ 截图若有）；`.ai-judge` 展示 AI 初判（`analysis.verdict`/`detail`/建议；无 `analysis` 时不渲染该块或提示「未生成初判」）。
- **AC-13（分支①落实开发 → 已立项 + 归批次）【原型·已落地·已测后端】** Given 选中「落实开发（立项）」`.decision-option.success` 并（可选）填「归入批次」When 点「确认处理」 Then 调 `POST /api/intake-transition {to:"已立项", batch?, assignee?, note?}`（合法：`待处理/分析中/暂缓 → 已立项`）成功；`lifecycle` 变「已立项」；有批次则回写 `intake.data.batch`（放 `data JSON`、不加库列）；`history` 追加 `{from,to:"已立项",by,byRole,at,note}`；抽屉关闭 + 列表/流水线刷新。**BP-01 未上线退化**：批次为文本输入或占位下拉、选填、留空不阻断、不调 `batch-tickets`（`NEEDS-HUMAN-2`）。
- **AC-14（分支①校验）【退化·NH-2】** BP-01 未上线，落实**不强制选批次**（原型「未选批次内联拦截」待 BP-01 上线后补）；当前批次空值放行。
- **AC-15（分支②直接答复 → 已回复）【原型·已落地·已测后端】** Given 选中「直接答复（不开发）」并填回复内容 When 「确认处理」 Then 调 `POST /api/intake-transition {to:"已回复", reply}` 成功（回复空则前端阻止）；`lifecycle` 变「已回复」；回复 push 进 `chat`（role=dev）；`history` 追加；后端 `kbAddFromIntake`（`to=已回复` 触发，`from=工单id` 去重）返回 `kbSunk`；抽屉关闭 + 刷新。〔答复即后端自动沉淀经验库；原型的「同时沉淀到经验库」勾选为 UI 提示，真实为默认自动沉淀〕
- **AC-16（分支②校验）【原型·已落地】** Given 选「直接答复」但回复内容为空 When 「确认处理」 Then 前端阻止并提示「请填写回复内容」，不发请求。
- **AC-17（分支③暂缓 → 新增态 暂缓）【原型·已落地·已测后端】** Given 选中「暂缓 / 驳回」→ 单选「暂缓」并填原因 When 「确认处理」 Then 调 `POST /api/intake-transition {to:"暂缓", note:原因}` 成功；`lifecycle` 变「暂缓」；`status`=已处理（进「已关闭」环，`lifecycleToStatus` 已扩展）；`history` 追加；抽屉关闭 + 刷新。合法流转 `待处理/分析中 → 暂缓`。

- **AC-19（分支③校验）【原型·已落地·已测后端】** Given 选「暂缓/驳回」但原因为空 When 「确认处理」 Then 前端阻止并提示「请填写原因」，不发请求（后端亦对暂缓/已驳回 `note` 必填不作强制，前端把关）。
- **AC-20（未选决策拦截）【原型·已落地】** Given 打开处理抽屉但未选任何决策 When 点「确认处理」 Then 前端提示「请先选择一项决策」，不发请求。
- **AC-21（处理后刷新）【原型·已落地】** Given 任一决策 `intake-transition` 成功 When 回调 Then 关闭抽屉、重新拉 `intake-list`（+ `intake-aggregate` 若在归并 Tab）重渲染列表 + 流水线计数按新态更新。

### 详情（原型「查看抽屉」轻量 + 衔接 `detail.html` 完整承载）
- **AC-22（查看抽屉摘要 + 附件）【原型·已落地】** Given 点击非待评审态行的「查看」打开 `#viewDrawer` Then 展示 类型/状态徽标（+ 批次/stewardUC 徽标若有）、标题、摘要（提交人/现场/产品·子系统/版本/描述）、AI 初判（若有）、决策回复（若 `chat` 有 role=dev）、流转留痕时间线（由 `history` 构造）；抽屉底部「查看完整详情」跳 `detail.html?project=&id=`（截图经 `GET /api/intake-media` 取件、路径防穿越，由 `detail.html` 承载）。
- **AC-23（详情 AI 初判）【原型·已落地】** Given 工单含 `analysis`（`verdict`/`detail`）When 渲染查看抽屉 / `detail.html` Then 展示「AI 分析初判：类别 + 建议 + 疑似原因/说明」；无初判时该块不渲染。
- **AC-24（详情流转留痕）【原型·已落地】** Given 工单 `history`/`chat` 非空 When 渲染查看抽屉的 `.timeline` / `detail.html` Then 按顺序渲染「流转记录」时间线（各节点 to←from + 操作人/角色 + `yyyy-MM-dd HH:mm` + 备注）与「沟通记录」气泡（含 role=dev 的决策回复）。
- **AC-25（沉淀经验库）【原型·已落地】** 在 `to∈{已回复,已关闭}` 流转时**后端自动**触发 `kbAddFromIntake`（按 `from=工单id` 去重、返回 `kbSunk`）；原型查看抽屉的「沉淀到经验库」按钮为提示性入口（真实沉淀走自动，答复即沉淀，不依赖手动点）。

### 权限 / 非法流转（护栏）
- **AC-26（现场仅待验证可确认）** Given 以**现场(field)角色**调用 `POST /api/intake-transition` 且 `from ≠ 待验证` When 请求 Then 后端返回 403「现场仅可在「待验证」时确认验证结果」；仅 `from=待验证 → 已关闭/已重开` 放行（沿用现有 `isAdmin` 鉴权）。运营/管理员(admin)不受此限。
- **AC-27（非法流转拒绝）✅本单回归·已测** Given 一条工单 `lifecycle=待验证` When 提交 `to=已立项`（不在 `TRANSITIONS[待验证]` 内且非强制关闭） Then 后端返回 400「不能从「待验证」直接流转到「已立项」」，工单状态不变、无 history 追加。〔证明扩展未松动既有合法性校验〕
- **AC-28（未知目标态拒绝）✅本单已实现·已测** Given 提交 `to=不存在的态` When 请求 Then 后端返回 400「未知目标状态」（`to` 必须 ∈ 扩展后 `LIFECYCLE`，暂缓/已驳回 已入白名单不再被误拒）。
- **AC-29（强制关闭放行）✅本单回归·已测** Given 任一**非已关闭**态工单（含暂缓）When 提交 `to=已关闭` Then 放行（强制关闭），`history` 追加，触发 `kbAddFromIntake`。

### 5.1 状态机对齐（现有 lifecycle ↔ 原型 UI 标签）—— 权威 P0 §C

### 5.2 涉及的真实库表 / 字段（对照 `intake_bak/db.mjs`，禁止臆造）

### 5.3 【扩展点】本 spec 需明确的库/枚举扩展（承载于 DM-02，本 spec 从行为侧约束）
1. **【新增】状态枚举**：`LIFECYCLE` 增加 `暂缓`、`已驳回` 两态。

## 6. 业务规则 / 非功能
- **数据权限**（沿用现有 `intake-list/detail`）：非 admin 用户按 `accounts.projects`（产品）与 `accounts.sites`（负责现场）过滤可见工单；无权查看详情返回 403。运营/产品经理通常 admin 级可见全量。
- **按钮级权限 / 决策留痕**：处理决策（落实/答复/暂缓/驳回）应仅运营/管理员可操作；每次流转**强制写 `history`**（`{from,to,by,byRole,at,note}`），不可跳过——决策可追溯（护栏「操作留痕」）。
- **流转合法性（护栏）**：`to` 必须 ∈ 扩展后 `LIFECYCLE`；`from→to` 必须命中 `TRANSITIONS` 或为「强制关闭」；现场角色仅 `待验证→已关闭/已重开`（AC-26/27/28/29）。
- **幂等 / 并发**：重复提交同一决策以最新 `history` 追加为准；经验库沉淀按 `from=工单id` 去重（AC-15/25）。批次归入需幂等（同工单重复归入不产生多条，属 BP-01）。
- **AI 初判**：`intake-analyze` 未配置模型时返回 `{ok:false,configured:false}`，UI 需容错显示「未配置模型」而非报错（护栏·安全）。
- **时间格式**：所有展示时间统一 `yyyy-MM-dd HH:mm`，共享格式化函数，空值 `—`（全局规范 §12）。
- **筛选交互**：选择型即选即查、自由文本回车触发（全局规范 §11）；日期成对用单范围框（§9）；表格内部滚动、表头 sticky、不整页滚动（§3）；筛选栅格列数统一、超一行才出「展开更多」（§4/§10）。
- **列表持久化**（全局规范 §8）：从列表进详情/处理再返回，筛选条件 + 页码应保留（原型用 URL query `?status=&open=` 同步，实现可用 query 或 keep-alive）。
- `NEEDS-HUMAN-1`【本单按现状实现·待人确认最终粒度】：处理决策的**按钮级权限**具体到哪些角色。**本单沿用部署现状 `isAdmin(u)`（admin/dev）可处理流转、field 仅 `待验证` 确认**（暂缓/驳回/落实/答复均归 admin）。若需细分 pm/impl 权限，待人拍板后另调 `authGate`/`intake-transition` 判权。
- `NEEDS-HUMAN-2`【本单已按推荐默认实现】：BP-01 未上线，**已允许「落实不带批次」**——`intake-transition {to:已立项}` 批次选填、留空不阻断、不调 `batch-tickets`；`data.batch` 留空，BP-01 后补挂。仍需人确认此退化策略即最终方案。
- `NEEDS-HUMAN-3`【未落地·待定阈值】：待评审 SLA 停留/超期 chip 部署未实现（mock 预警 18h / 超期 36h）；阈值最终值待人确认后再落前端 chip。

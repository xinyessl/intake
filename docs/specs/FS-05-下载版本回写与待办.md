## 1. 用户故事 / 目标
作为**现场实施工程师（`impl`）**，我要在**「可下载」批次**里**下载产品更新包**、现场应用后**一键把该医院该产品的现场版本号从 `v_old` 改到 `v_new`**，并对该批次里**我提的每一条工单逐单确认「现场验证过」**（验证不过就**人工反馈/打回**及时处理）；当整批单都验证过、批次闭环为「已交付」——以便**现场部署与运营台账版本一致、逐单可追溯、验证结果闭环**，形成「上传包 → 下载 → 改版本 → 逐单验证 → 批次交付」的完整链路。

- 更新包由运营端管理身份上传（BP-01），现场**只下载与回写、逐单验证**，不自助发包。
- 版本回写**非强制但强提醒**（下载后提示 + 挂提醒，不阻断继续操作）。
- 逐单验证**每单一确认**：验证过 → 该单 `已关闭`；不过 → `已重开`（人工反馈）。

## 2. 范围
**包含：**
- **按批次视图**（FS-02 「按批次」落地）：把我负责医院的提交单**按落进的批次(产品)分组**，每组显示：产品 + 批次状态（开发中/可下载/已交付）+（可下载时）更新包信息 + 组内逐单列表（每单状态 + 逐单验证✅）。
- **更新包信息 + 下载**：「可下载」批次组内展示 `<产品> v<pkgVersion> 更新包`（发包时间 `yyyy-MM-dd HH:mm` + 更新说明 + 下载按钮）；点下载 → 调后端记录下载 + 返回 `artifactUrl` → 触发下载 / 提示地址；按钮转「已下载」。
- **一键改版本（版本回写）**：下载后出现改版本提示 `<医院> <产品/子系统> v_old → v_new` + `一键改版本`；点击 → `POST /api/customer-version`（回写 `data/customers.json` 该医院该产品/子系统版本 `v_old→v_new`）；成功后现场版本更新、提示转「已改版本」。
- **逐单确认「现场验证过」**：批次组内每条覆盖工单（我提的、`待验证` 态）有「确认验证过」✅ 动作 → `POST /api/intake-verify`（复用 `intake-transition` `待验证→已关闭`）→ 该单转「已验证/已关闭」；触发 BP-01 闭环检查（全验证过 → 批次「已交付」）。
- **验证不过 → 人工反馈**：逐单「反馈问题/打回」动作 → `intake-transition` `待验证→已重开`（带反馈说明留痕）→ 工单重开、及时处理；批次态不回退。
- **幂等**：版本回写同值幂等（`v_new==现场当前版本` 不重复写、不重复留痕）；下载重复调用不重复计数（`downloads` 不叠加）。
- **留痕**：下载与版本回写各记「谁/何时/哪家医院/哪个产品版本」；逐单验证/反馈复用工单 `history`。

**不包含（划归它处）：**
- 批次创建/定档/导清单/上传包/闭环判定本体（→ `BP-01` 运营端）；本条只**读**「可下载」批次 + 包信息、**写**下载事件/现场版本/逐单验证。
- 医院选择器 / 按类型视图 / 子项目筛选（→ `FS-02`，本条复用其批次分组容器挂更新包卡与逐单动作）。
- 系统视图归档版本、运营 tag 版本下拉（→ FS-03）；本条只管现场版本回写。
- 更新包**产物本体的生成/托管**（→ BP-01 `artifactUrl`；形式 URL vs 上传由 BP-01 NH-2）。
- **三类待办 popover**（旧稿 `f-todopop`）→ 降为可选增强（NH-4），非本期主线。

## 3. 验收标准（AC · Given-When-Then · 每条可自动化判定）
> ⚠️ 涉及批次/更新包/下载的 AC 依赖 **BP-01（批次「可下载」+ 包信息 + 上传包）**；BP-01 未上线前走占位分支（H 组降级）、不可正式验收。前端结构/交互可先在 `public/field.html` 静态锁定。

### A. 按批次视图（批次分组 · 对齐 FS-02 「按批次」落地）
- **AC-1** Given 当前所选医院在若干批次内（其提交单 `intakes.data.batch` 非空），When 切「按批次」视图，Then 按批次(产品)分组展示：每组头 `<产品> · <批次状态 tag>`（开发中/可下载/已交付，tag 色对齐 theme.css）+ 组内我提的工单逐单列表；无批次归属的单归「未入批」组或按 FS-02 降级处理。
- **AC-1b**（2026-07-26 补·排期可见）Given 某批次运营端已设排期（`scheduleDate` 非空，纯日期 `yyyy-MM-dd`），When 现场端切「按批次」视图渲染该组头，Then 组头显示排期「计划交付 <scheduleDate>」（次要色）；未排期（`scheduleDate` 空）显「未排期」灰字占位。后端 `GET /api/field/batches` 每个批次 group **必须回传 `scheduleDate` 字段**（旧批次回读为空串）——根因回归：该字段是排期后加的，`field/batches` 输出曾漏带，导致排期在实施端不可见。不使用「发包」类字样（现场端 A6 禁词）。
- **AC-1c**（2026-07-26 补·工单卡醒目显排期 · 2026-07-26 修订：底部灰字→顶行醒目 chip + 系统视图同显）Given 现场端工单卡（「按类型」视图 `mkItem` **或**「系统视图」`mkSysItem`）某工单已归批且该批设了排期，When 渲染该卡，Then 在**卡片顶行**（类型标签「BUG/需求/咨询」+ 状态标签行）之后追加一枚**醒目的排期 chip** `.f-sched-chip`（带日历图标 + 强调色字浅底，文案「计划交付 <scheduleDate>」，纯 `yyyy-MM-dd`），一眼可见、与状态标签配色分明；未归批或批次无排期则**不显**。旧实现把排期放在底部上下文行灰字（`.isched`）里太不起眼、用户看不到——现提升为顶行 chip 且**从底部去掉不重复**。`mkItem`/`mkSysItem` 两处用同一 `.f-sched-chip` 样式类、视觉一致。后端 `field/submissions` 每条 item **回传 `batchId` + `batchSchedule`**（`batchSchedule` = 该工单 `data.batch` 对应批次的 `scheduleDate`，读时按 `loadBatches()` 派生、不落库；无批次/无排期为空串）；`dimension=sys`（系统视图）与 `hosp`（按类型/医院视图）**共用同一 `mapItem`**，故系统视图 item 同样带 `batchSchedule`（无需额外改后端）。不使用「发包」类字样（A6 禁词）。
- **AC-2** Given 某批次状态=「可下载」，When 渲染该组，Then 组内出现更新包信息区：`<产品> v<pkgVersion> 更新包` + 发包时间（`yyyy-MM-dd HH:mm`）+ 更新说明（点开看 `releaseNote`）+ `下载更新包` 按钮。
- **AC-3** Given 某批次状态=「开发中」（未上传包），When 渲染该组，Then **不**出现更新包/下载区（仅「可下载/已交付」态挂包信息）；组内工单显各自 lifecycle 映射标签。
- **AC-4** Given 数据按 sites 隔离，When 生成按批次视图，Then 后端 `GET /api/field/batches` 只返回**当前账号 `sites`** 内医院涉及的批次 + 我提的单（`scopedForField`），换账号得不同集（对齐 FS-01 隔离 + §6 决策）。

### B. 下载 + 状态翻转
- **AC-5** Given 「可下载」批次的 `下载更新包` 按钮，When 点击，Then 调 `POST /api/batch-download {batchId, customerId}`（当前医院），成功后：① 按钮转「已下载」（`.done` 绿）；② 出现改版本提示条：`<医院> <产品/子系统> v_old → <b>v_new</b>` + `一键改版本`（该批次覆盖的我负责医院各一条）。
- **AC-6** Given 已下载过（后端 `downloads` 已计当前账号本次），When 重复调 `POST /api/batch-download`，Then **不重复计数**（`downloads` 不叠加）、返回同一 `artifactUrl`；前端不重复插入改版本提示条。
- **AC-7** Given `POST /api/batch-download` 返回 `artifactUrl`，When 前端拿到，Then 触发下载（新标签 / `<a download>`）或提示地址；地址为空（BP-01 产物形式未定）时降级提示「更新包地址待运营发布」，不报错。
- **AC-8** Given 越权：当前账号 `sites` 不含某医院，When 下载/生成提示条，Then 后端只按当前用户 `sites` 收敛（`scopedForField`），提示条只列我负责医院，越权医院不出现（`forbidden` 或收敛）。

### C. 一键改版本（版本回写 → POST /api/customer-version）
- **AC-9** Given 改版本提示条的 `一键改版本`，When 点击，Then 弹二次确认（`将 <医院> · <产品/子系统> 现场版本 v_old → v_new，确认？`），确认后调 `POST /api/customer-version {customerId, productId, subsystem?, version:v_new}`。
- **AC-10** Given 回写成功（`{ok:true}`），When 前端收到，Then：① 提示条转「已改版本」（或移除该条）；② 该医院现场版本更新为 `v_new`（`data/customers.json` 对应 `products[].subsystems[].version`（新）/ `products[].version`（旧）已改，`GET /api/customers` 回读为 `v_new`）；③ 提示「已回写版本号 v_new」。
- **AC-11** Given 版本回写**同值幂等**：`version` == 该医院该产品/子系统现场当前版本，When 调 `POST /api/customer-version`，Then 返回 `{ok:true}` 但**不重复写、不重复留痕**（`updatedAt` 可刷新，版本值不变），前端表现「已是最新版本」。
- **AC-12** Given `customerId` 不存在 / `productId` 不属该客户 products / `version` 为空，When 调用，Then 返回 `{error:"..."}`（400），不改任何数据。
- **AC-13** Given 越权：`customerId` 对应医院不在当前账号 `sites`，When 调 `POST /api/customer-version`，Then 后端 `forbidden`(403)（`authGate` deny-by-default + 服务层 sites 校验），不写库。
- **AC-14** Given 回写规则「是否强制/校验」未定（NH-2），When 下载后未改版本，Then **不阻断**任何后续操作（提交/切医院/退出均可），仅保留强提醒（非强制）。

### D. 逐单确认「现场验证过」（→ 待验证→已关闭）
- **AC-15** Given 批次组内某覆盖工单为 `待验证` 态、是我负责医院的单，When 点该单「确认验证过」✅，Then 调 `POST /api/intake-verify {project, id, result:"pass"}`（内部走 `intake-transition` `待验证→已关闭`），成功后该单标签转「已验证/已关闭」，`history` 记一条现场验证留痕。
- **AC-16** Given 工单**非 `待验证`** 态（如仍 `已出包`，尚未下载触发 `已出包→待验证`），When 点「确认验证过」，Then 后端拒绝（真库 L1292 现场仅可在 `待验证` 时确认）→ 前端提示「请先下载更新包后再验证」（不报错崩溃）。
- **AC-17** Given 批次覆盖工单 3 条，我逐条确认验证过，When 最后一条确认后，Then 触发 BP-01 闭环检查（`POST /api/batch-deliver-check {id}`）；全 `已关闭` → 批次转「已交付」，按批次视图该组头 tag 更新为「已交付」。

### E. 验证不过 → 人工反馈（→ 待验证→已重开）
- **AC-18** Given 批次组内某 `待验证` 工单验证不过，When 点「反馈问题/打回」并填反馈说明，Then 调 `POST /api/intake-verify {project, id, result:"fail", note:"<反馈>"}`（内部走 `intake-transition` `待验证→已重开`，带反馈留痕），成功后该单转「已重开」、`history` 记反馈说明，工单回到运营/开发处理流。
- **AC-19** Given 某工单被反馈打回（`已重开`），When 该批次做闭环检查，Then 该批次**不转「已交付」**（该单非 `已关闭`），保持「可下载」等待重新验证（对齐 BP-01 AC-18，批次态不回退）。

### F. 越权与数据隔离
- **AC-20** Given 越权：`project`/`id` 对应工单不属当前账号 `sites` 内医院（`intakes.site` 不在 sites），When 调 `POST /api/intake-verify`，Then 后端拒绝（`scopedForField` + `intake-transition` 现场态校验），不改工单。
- **AC-21** Given 按批次视图 / 下载 / 改版本 / 逐单验证 各接口，When 换不同 `impl` 账号登录，Then 各自只见/只操作自己 `sites` 内医院数据，互不可见（对齐 FS-01 + §6）。

### G. 闭环联动（下载 → 改版本 → 逐单验证 → 批次交付）
- **AC-22** Given 完成下载（AC-5），When 后端记录，Then 覆盖工单经 `已出包→待验证`（下载触发，见 §5.3），按批次视图该单出现「确认验证过」入口。
- **AC-23** Given 「一键改版本」+ 「逐单验证过」联动，When 全批单验证过（AC-17），Then 批次「已交付」、该组下载/验证入口收起或标记完成，闭环达成。

### H. 分期占位（BP-01 未上线时的降级）
- **AC-24** Given BP-01 未上线（`GET /api/field/batches` / `/api/batch-download` 未就绪），When 现场端渲染按批次视图，Then **不报错**：按批次视图显占位「批次功能待运营端上线」或降级为 FS-02 「按类型」视图；下载/改版本/逐单验证入口不出现（本条 §6 记待接续）。

## 4. 接口契约
> 统一前缀 `/api`；实施端接口按**当前登录用户 `sites`** 收敛，忽略前端越权传参；返回体 `{ok/error}` 或 `{...data}`。**新增端点均需显式加入 `server.mjs` 的 `FIELD_OK` 白名单**（否则 `authGate` deny-by-default 对现场 `impl` 403），且服务层再按 `sites` 二次校验。
> **⚠️ 双域名同步约束（2026-07-26 补·实测坑·对齐 FS-08 AC-9b）**：本条 4 个现场端点（`field/batches`/`batch-download`/`customer-version`/`intake-verify`）除进 `FIELD_OK` 外，**还必须同步加进 `server.mjs` 顶层 `FS08_FIELD_API`**（field 域名层外层闸的接口允许集）。漏配 `FS08_FIELD_API` 时：运营域（admin）能调、**实施域（field, `intake.lcpharmacy.cn`）被 `originGate` 判 `deny` 返 `{"error":"forbidden"}`** → 实施端整段批次流（按批次视图/下载/改版本/验证）挂掉且隐蔽（登录、页面都正常，仅接口越域拒）。回归由 `tools/fs-08.test.mjs` 的「FIELD_OK 的 /api/ 端点全部 ∈ FS08_FIELD_API」防漂移断言守。

## 6. 业务规则 / 非功能
- **数据权限（硬约束）**：下载/回写/逐单验证/按批次视图**全部限当前 `impl` 账号 `sites`**（服务层 `scopedForField` 过滤，忽略前端越权传参）；越权 `forbidden`(403)（对齐 FS-01 隔离 + 「①本项目信息·数据权限/留痕规则来源」authGate）。
- **按钮级权限**：现场端**无**定档/建批/上传包/账号管理入口；仅下载、一键改版本、逐单验证/反馈。新写端点默认**不进** `LINK_OK`（免登录访客无权）。
- **逐单验证态约束**：仅 `待验证` 态工单可确认验证/反馈（真库 L1292）；非该态拒绝并前端友好提示（AC-16）。
- **幂等**：① 版本回写同值幂等（AC-11）；② 下载重复不重复计数（AC-6）；③ 逐单验证对已 `已关闭` 的单重复确认不报错（transition 校验 + 前端入口收起）。
- **闭环不回退**：验证不过 → 工单 `已重开`（人工反馈），**批次态不回退**（对齐 BP-01 AC-18）；全验证过才 `batch-deliver-check` → 「已交付」。
- **留痕**：下载 + 版本回写各记「谁/何时/哪院/哪产品版本」（逐条落点 NH-3）；逐单验证/反馈复用工单 `history`（`intake-transition` 已留痕）。
- **回写非强制 + 强提醒**：下载后提示 + 强提醒，**不阻断**后续（AC-14）；是否强制/校验规则 **NH-2**。
- **时间格式**：发包时间等展示统一 `yyyy-MM-dd HH:mm`（全局 UI 规范⑫），空值 `—`。
- **降级**：BP-01 未上线时按批次视图/下载/改版本/逐单验证入口降级占位、不报错（AC-24）。

- **NH-2 版本回写是否强制 + 校验规则**：下载后是否必须改版本、版本号格式/单调递增校验 —— 待运营/管理确认。当前按「非强制 + 强提醒」落地。
- **NH-3 下载/版本回写逐条留痕落点**：`customers.json versionLog[]` vs 独立 `download-log.json`（§5.4）。
- **NH-4 三类待办 popover 是否保留**：旧稿 `f-todopop`（待下载/待改版本/待验证）降为可选增强；本期主线走「按批次视图」承载动作，独立 popover 是否仍要 → 待定（默认不做，视图内动作已覆盖）。

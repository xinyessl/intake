## 1. 用户故事 / 目标
- 作为**实施工程师**，当 AI 咨询答疑答不好时，我要一键「转人工」把这条咨询升级给运营，**但它仍是咨询、不转开发工单**，以便拿到更权威的人工答复。
- 作为**运营**，我要在后台看到「待人工回复」的咨询队列，打开看完整对话后写回复，回复直接进这条咨询的对话流；回复后可让 AI 把「原问题 + 我的权威回复」整理成经验库草稿，**我编辑确认后才入库**，以便下一个人问同类问题时 AI 能直接答上来（反哺闭环）。
- 作为**实施工程师**，我要在原咨询会话里看到运营的人工答复（区别于 AI 气泡），有未读时给我提醒。

## 2. 范围
- **包含**：
  1. 实施端「转人工」按钮 + 端点 `POST /api/consult-escalate`（在咨询记录 `data` JSON 打 escalated 标记，**不建工单**）。
  2. 运营端新页 `public/consult-reply.html`（导航「咨询回复」）+ 队列端点 `POST /api/consult-escalations` + 回复端点 `POST /api/consult-human-reply`（把人工回复 append 进咨询 chat，标 `human:true`）。
  3. 实施端只读渲染 chat 里 `human:true` 消息为「运营人工答复」样式 + 未读提醒 badge。
  4. AI 草稿端点 `POST /api/consult-kb-draft`（原问题 + 人工回复整理成 q/a，不入库）+ 运营编辑确认后沉淀 KB（`source=escalated`，复用现成 kb 保存机制）。
- **不包含**：
  - 不改 `/api/consult`、`answer_audit`、`consultAnswerSemanticAudit`、prompts 里 consult 答复模板（lsy 活跃维护区，只加新端点/新页/外挂）。
  - 不新建库表（全用 `intakes.data` JSON 附加字段 + 现有 `kb_entries` 表）。
  - 不改 `kbRetrieveScored` / `consultKbFilter` 检索逻辑——新 KB 条目**自动**被下次咨询检索命中（反哺闭环靠现成机制）。
  - 不把转人工的咨询转成开发工单（`consult-to-intake` 是另一条路，保持独立）。

## 3. 验收标准（AC · Given-When-Then）
- **AC-1（转人工·打标记不建单）** Given 一条存在、未删、type=consult 的咨询 When 实施端 POST `/api/consult-escalate {project, convId}` Then 该咨询 `data` JSON 置 `escalated:true, escalatedAt, escalatedBy, escalateQuestion`（=chat 最后一条 user 文本快照）；`type` 仍为 consult、**不产生新工单**；返回 `{ok:true}`。
- **AC-2（转人工幂等）** Given 一条已 escalated 的咨询 When 再次 POST `/api/consult-escalate` Then 不报错、返回 `{ok:true, alreadyEscalated:true}`，`escalatedAt` 不被后一次覆盖（首次为准）。
- **AC-3（转人工权限=field+admin）** Given 现场账号（impl/pm）已登录 When POST `/api/consult-escalate` Then 允许（端点 ∈ FIELD_OK ∩ FS08_FIELD_API）；越权对不在自己 sites 的咨询发起 → 403；admin 不限。
- **AC-4（队列 admin 限定）** Given 未登录 / 现场账号 When POST `/api/consult-escalations` Then 401 / 403（端点**不在** FIELD_OK/LINK_OK/FS08_FIELD_API）；admin 登录后返回 escalated=true 的咨询列表，带 `status`（待回复/已回复）、`escalateQuestion` 快照、`site`/`subsystem`/`project`/`escalatedAt`，**倒序 escalatedAt** 稳定排序，可按 `project`/`status` 过滤。
- **AC-5（人工回复 append 进 chat）** Given admin 打开一条 escalated 咨询 When POST `/api/consult-human-reply {project, convId, reply}` Then 咨询 chat 末尾 append `{role:'assistant', human:true, by:运营名, byRole:'admin', at, text:reply}`；置 `humanReplied:true, humanReplyAt, humanReplyBy`；返回 `{ok:true}`。reply 空 → 400。端点 admin 限定（不在 field 白名单）。
- **AC-6（实施端看人工回复）** Given 咨询 chat 含 `human:true` 消息 When 实施端 reopen 该咨询会话 Then 该消息渲染为「运营人工答复」样式（区别于普通 AI 气泡）；有未读人工回复时在对话记录入口给 badge/提醒。
- **AC-7（AI 草稿·不入库）** Given 一条已人工回复的 escalated 咨询 When admin POST `/api/consult-kb-draft {project, convId}` Then 用 AI 把「原问题 + 人工回复（权威答案）」整理成 `{q, a}` 返回，**不写 KB**；AI 未配/失败则用兜底（q=原问题、a=人工回复）。端点 admin 限定。
- **AC-8（确认沉淀 KB · source=escalated）** Given 运营编辑好 q/a When 走 kb 保存（`/api/kb-save` 带 `source:'escalated'` 或 `/api/kb-from-consult` 直传 q/a 路径）Then 存进 `kb_entries`，`source` 派生为 `escalated`（或 auto with from_ref），挂对应 project/subsystem/module。
- **AC-9（反哺闭环）** Given 沉淀了一条 escalated KB 条目 When 下次对同类问题调 `kbRetrieveScored(projId, query, 5, 2)` Then 能检索到该新条目（证 AI 下次可直接引用；不改检索逻辑）。
- **AC-10（隔离 lsy consult）** Given 本 spec 全部改动 When 审查 diff Then `/api/consult`、`answer_audit`、`consultAnswerSemanticAudit`、prompts consult 答复模板均**未改动**（新端点/新页/field.html 最小外挂）。
- **AC-11（两端轻量轮询·实时性增强）** Given 实施端已「转人工」、运营在「咨询回复」页答复 When 实施端 `public/field.html` 页面可见 Then 前端每 15~20s 轮询 `/api/field/conversations`（`document.visibilityState==='visible'` 才轮、切回可见立即拉一次、`inFlight` 防并发、登出/卸载 `clearInterval`）比对上次已知 `humanReplyAt` 检测「新人工回复」，命中即：① toast 提醒「运营已回复你的咨询」；② 翻新右上「对话记录」转人工徽标（待回复→已回复，抽屉开着时静默重载列表）；③ **若该咨询正开在右侧对话区**（`chat.convId` 匹配）则复用 `appendHumanReplyBubble` 增量 append 人工回复气泡（只补新增、不清空/不重建对话流、不动输入框），不在打开态则只提醒+翻徽标；顺带刷新 `/api/notifications` 待办计数。同样地，运营端 `public/consult-reply.html` 每 15~20s 可见时轮询 `/api/consult-escalations` 静默翻新队列（新「待回复」自动出现、已回复翻态），但**回复抽屉打开时跳过刷新**、不打断运营正在输入/看 AI 草稿。**为判「新」，`/api/field/conversations` consult 项出参补透 `humanReplyAt`**（其余后端逻辑不动；不改 `/api/consult` 答复 SSE）。
- **AC-12（人工回复纳入刷新恢复 · 回归）** Given 一条咨询正开在实施端右侧对话区、AC-11 轮询实时收到运营人工回复气泡（`syncOpenConsultMessages` 已 append 进 DOM）When 实施端**刷新页面（F5）**Then 该运营人工回复**不丢失**、随会话完整恢复，并渲染为「运营人工答复」样式（`f-human-reply` 绿色 headset 气泡 + 「运营人工答复·署名」标签），而非普通 AI 气泡或空白。**实现约束**：① 实时 append 人工回复时，除 append DOM 外必须同时把该回复 push 进 `chat.messages`（形状 `{role:'assistant', human:true, by, content, media?}`，同 `reopenConsult` 恢复口径）并 `saveDraft()` 落 sessionStorage 草稿；防重复以 `chat.messages` 里已持久化的 human/system 条数为增量基线（轮询多次/已 push 过的不重复加）。② 刷新恢复重放（`renderSavedConversation`）时，`chat.messages` 里 `role==='assistant' && human` 的消息必须走 `appendHumanReplyBubble`（而非普通 `appendBubble('ai',...)`）。③ 从「对话记录」`reopenConsult` 打开的咨询，其 `chat.messages` 必须保留每条消息的 `human`/`by`/`system`（默认只留 `role`/`content` 会丢标记）→ 刷新后仍能重放为人工/系统气泡。④ 纯咨询轮次（无人工回复）刷新恢复不回归——assistant 仍走普通 AI 气泡。

> ### 增强（2026-09 · 持续双向人工对话）：转人工后进入**持续人工对话模式**，直到运营「结束人工服务」才恢复 AI 答疑。

- **AC-13（转人工进入人工服务模式）** Given 一条 consult When 实施端 `POST /api/consult-escalate` Then 除 AC-1 效果外，`data` JSON 置 `humanActive:true`（进入人工服务模式）；实施端显「人工服务中」提示条。幂等：已 escalated 再点仍 `alreadyEscalated`、`humanActive` 不改（保持 true）。
- **AC-14（人工模式下实施发消息不调 AI）** Given 一条 escalated 且 `humanActive===true` 的咨询正开在实施端右侧 When 实施在该会话输入框发消息（文字/截图）Then 前端 `sendChat` **不调 `/api/consult`（不走 AI）**，改调 `POST /api/consult-human-message {project,convId,text,images?}`；该消息 append 进 chat 为 `{role:'user', human:true, byRole:'field', by:实施名, at, text, media?}`，实施端上屏为「me」气泡并 push `chat.messages`（`{role:'user',human:true,content,media?}`）+ `saveDraft`。截图复用咨询现有落盘（`media/<convId>/img-N.png`，累计封顶 6）。权限 ∈ FIELD_OK∩FS08_FIELD_API；现场按 `user.sites` 收敛越权 403；`humanActive===false`（非人工模式）时该端点返 409 `{humanActive:false}`（前端据此切回 AI 模式）；空文本且无图 → 400。
- **AC-15（运营持续回复·可发截图）** Given 一条人工服务中的咨询 When 运营在「咨询回复」页对话视图底部持续输入并发送（`POST /api/consult-human-reply`，扩展支持 `images?`）Then 每次 append 一条 `{role:'assistant', human:true, byRole:'admin', by, at, text, media?}`（reply 与 images 至少一项非空，皆空 → 400）；运营截图同样落盘挂消息 media。运营端抽屉是**完整对话视图**（现场消息 + 运营消息双向）+ 底部持续输入 + 「结束人工服务」按钮。
- **AC-16（仅运营可结束人工服务·恢复 AI）** Given 一条人工服务中的咨询 When 运营 `POST /api/consult-human-end {project,convId}`（admin 限定，不在任何 field/link 白名单，非 admin 401/403）Then 置 `humanActive:false, humanEndedAt, humanEndedBy`，append 一条系统提示 `{role:'assistant', human:true, byRole:'admin', system:true, text:'【人工服务已结束，后续将由 AI 助手继续为您答疑】'}`；返回 `{ok:true}`；幂等（已结束再点返 `{ok:true, alreadyEnded:true}`，不重复追加系统提示）。之后实施再发言恢复走 AI 答疑（`/api/consult`）。**仅运营能结束**（实施无此入口、调 human-end → 403）。
- **AC-17（双向实时轮询）** Given 一条人工服务中的咨询正开在实施端右侧 When 轮询（AC-11 机制）Then 实施端 `syncOpenConsultMessages` 对当前打开的咨询**无条件增量同步**（不再仅在 `humanReplyAt` 变化时触发）：拉 `/api/intake-detail` 把本地未渲染的**双方** `human`/`system` 消息按服务端真实时序增量 append（运营人工答复走 `appendHumanReplyBubble`、现场人工消息走 `me` 气泡兜底、系统提示走 `appendSystemNotice` 居中系统条），只补新增、不清空/不重建、不动输入框；并按 `item.humanActive` 校准 `chat.humanActive`（运营结束→翻 false→隐提示条+toast「人工服务已结束，已恢复 AI 答疑」）。同样地运营端**抽屉打开时**每 12s 轮询 `/api/intake-detail` 增量把现场新消息 append 进对话视图（不重建 body、不清运营正在写的输入/截图/AI 草稿；可见+抽屉开着才轮、`inFlight` 防并发、抽屉关/卸载清 interval）。为支撑：`/api/field/conversations` + `/api/consult-escalations` consult 项出参补透 `humanActive`（+ escalations 补 `lastMsgText/lastMsgRole/lastMsgAt/lastFieldMsgAt` 供运营队列看「进行中的人工会话」）。
- **AC-18（双向人工消息 + 系统提示纳入刷新恢复 · 回归）** Given 一条人工服务中的咨询含现场人工消息（`user human`）、运营人工答复（`assistant human`）、系统结束提示（`system`）When 实施端刷新（F5）Then 三类消息均**不丢失**、按真实时序恢复并渲染成对应样式：`user human`→实施侧「me」气泡、`assistant human`→「运营人工答复」气泡、`system`→居中系统条；`chat.messages` 保留 `human/by/system` 标记、`chat.humanActive` 随草稿 `save/restore` 且轮询二次校准。`kb-draft` 兜底取「最后一条 human assistant」时**跳过 `system` 消息**（系统提示不是权威答案，不能被当成 KB 的 a）。
- **AC-19（人工双向消息的截图 · 后端落盘 + 刷新恢复不丢图 · 回归）** Given 人工服务中的咨询里实施发了带截图的人工消息（`user human` + `media`）或运营发了带截图的人工答复（`assistant human` + `media`）When ①落盘 ②实施端刷新（F5）恢复 Then：① **后端真落盘**——`/api/consult-human-message` / `/api/consult-human-reply` 经 `persistConsultImages` 把 data URL 写到磁盘 `intake-store/<projId>/media/<convId>/img-N.png`（**文件确实存在且非空**，不能只在 chat/返回里有路径而盘上无文件）并回 `{media:[相对路径]}`；实施端 `sendHumanMessage` 用返回的 `media` **回填**刚 push 的那条 `chat.messages` 消息（`msg.media = r.media`）+ `saveDraft`（上屏气泡用 data URL 即时显示，但持久化必须用服务端落盘相对路径）。② **刷新恢复渲染截图**——`renderSavedConversation` 重放 `user human` / `assistant human` 消息时，`m.media` 存在即经 `mediaUrls(project, m.media)` 拼 `/api/intake-media` 显缩略图；**其中 `project` 必须解析出咨询真实 project**：对 consult，传入的 `projectFallback` 为空（新起会话 `reopenConvProject`/`reopenIntakeProject` 都为空）时兜底 `= chat.reopenProject || currentArchive().project`（与发送落盘时同一 project），否则 `mediaUrls` 因 `project` 空返 `[]` → **文字气泡在、截图全丢**（本次线上 bug 现象）。运营端每次重拉 `intake-detail` 渲染，图随服务端 media 不丢——前提是后端确已落盘（同①）。

## 4. 接口契约（本 spec 新增 4 端点）

### 4.1 `POST /api/consult-escalate`（field + admin）
- 权限：∈ FIELD_OK ∩ FS08_FIELD_API（实施可发起）。
- 入参：`{ project, convId }`。
- 校验：proj 存在；咨询存在、未删、`type==='consult'`；现场账号 site 收敛（不在 user.sites → 403，admin 不限）。
- 效果：`e.escalated=true; e.escalatedAt=<首次>; e.escalatedBy=<reporter/user 名>; e.escalateQuestion=<chat 末条 user text 快照>; e.updatedAt`；`saveIntake`。
- 返回：`{ ok:true }` 或 `{ ok:true, alreadyEscalated:true }`（幂等）。
- 错误：400（缺 convId / 咨询不存在），403（越权 site）。

### 4.2 `POST /api/consult-escalations`（admin 限定）
- 权限：不在任何 field/link 白名单 → authGate deny-by-default（非 admin 401/403）。
- 入参：`{ project?, status? }`（status ∈ {待回复, 已回复}，缺省全部）。
- 返回：`{ ok:true, items:[{ project, id, title, site, subsystem, escalateQuestion, escalatedAt, escalatedBy, status(待回复|已回复), humanReplyAt }] }`，倒序 `escalatedAt`。

### 4.3 `POST /api/consult-human-reply`（admin 限定 · 已扩展 images）
- 权限：admin 限定（同上）。
- 入参：`{ project, convId, reply, images? }`（`images` = data URL 数组，≤6，可选；运营也能发截图）。
- 校验：proj 存在；咨询存在、未删、`type==='consult'`；`reply` 与 `images` **至少一项非空**（皆空 → 400，允许「纯截图」回复）。
- 效果：截图复用 `persistConsultImages`（`media/<convId>/img-N.png` 累计封顶 6）；chat.push `{role:'assistant', human:true, by, byRole:'admin', at, text:reply, media?}`；`e.humanReplied=true; e.humanReplyAt=at; e.humanReplyBy=by`；`saveIntake`。
- 返回：`{ ok:true }`。

### 4.5 `POST /api/consult-human-message`（field + admin · 持续人工对话增强）
- 权限：∈ FIELD_OK ∩ FS08_FIELD_API（实施可发）。
- 入参：`{ project, convId, text, images? }`（`text` 或 `images` 至少一项非空）。
- 校验：proj 存在；咨询存在、未删、`type==='consult'`；现场按 `user.sites` 收敛（越权 403，admin 不限）；必须 `escalated && humanActive`，否则 409 `{ok:false, humanActive:false}`；空文本且无图 → 400。
- 效果：截图 `persistConsultImages`；chat.push `{role:'user', human:true, byRole:'field', by:实施名, at, text, media?}`；`e.humanReplied=false`（现场发言→回到待回复）、`e.lastFieldMsgAt=at`、`e.updatedAt`；`saveIntake`。
- 返回：`{ ok:true, media:[本轮落盘相对路径] }`。

### 4.6 `POST /api/consult-human-end`（admin 限定 · 持续人工对话增强）
- 权限：不在任何 field/link 白名单 → deny-by-default（非 admin 401/403）；**仅运营可结束**。
- 入参：`{ project, convId }`。
- 校验：proj 存在；咨询存在、未删、`type==='consult'`。
- 效果：`e.humanActive=false; e.humanEndedAt=at; e.humanEndedBy=by; e.updatedAt`；chat.push `{role:'assistant', human:true, byRole:'admin', by, at, system:true, text:'【人工服务已结束，后续将由 AI 助手继续为您答疑】'}`；`saveIntake`。
- 幂等：已结束（`humanActive===false`）再点返 `{ok:true, alreadyEnded:true}`、不重复追加系统提示。
- 返回：`{ ok:true }`。

### 4.7 出参扩展（只读附加字段，不改会话逻辑）
- `/api/field/conversations` consult 项补：`humanActive`、`humanEndedAt`（+ 已有 `escalated/humanReplied/humanReplyAt`）。
- `/api/consult-escalations` 项补：`humanActive`、`humanEndedAt`、`lastMsgText`、`lastMsgRole(field|admin|ai|system)`、`lastMsgAt`、`lastFieldMsgAt`（供运营队列看「进行中的人工会话」+ 最后消息摘要）。

### 4.4 `POST /api/consult-kb-draft`（admin 限定）
- 权限：admin 限定。
- 入参：`{ project, convId }`。

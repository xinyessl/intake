## 0. 一句话
现场实施工程师（`impl`）在**运营已上传包（批次转「可下载」）**后的一整套落地动作：**下载更新包 → 一键/自动改现场版本号 → 对我提的每条工单逐单确认「现场验证过」→ 全批验证过则批次「已交付」**；外加**维保到期回写提醒**与**更新包实施任务清单（跟随产品代码 · 按批次快照）**。运营侧（定档建批 / 导清单 / 上传包 / 审核部署清单 / 闭环判定）见 `BP-01`；本机制现场只**读**「可下载」批次 + 包信息、**写**下载事件 / 现场版本 / 逐单验证。

## 1. 机制全景（下载 → 改版本 → 逐单验证 → 批次交付 的闭环）

```
运营端 BP-01                              实施端（本机制 · FS-15/16/17）
────────────────────────                 ──────────────────────────────────
定档建批 → 导清单 → 上传包                  ①【FS-15】按批次视图：我负责医院的提交单按落进的

                                              ↓
                                          ②【FS-15】下载更新包（POST /api/batch-download）
                                              → downloads+1（幂等）
                                              → 覆盖工单「已出包→待验证」（系统动作）
                                              → 返回 bumps（我负责医院×子系统 v_old→v_new）
                                              ↓
                                          ③【FS-16】一键改版本（POST /api/customer-version）
                                              → 回写 data/customers.json 现场版本 v_old→v_new
                                              （非强制·强提醒；同值幂等；越权 403）

                                              ↓
运营端 BP-01 batch-deliver-check   ◀──────  ⑤【FS-16/FS-15】全批覆盖工单已关闭

   → 医院版本自动更到 pkgVersion               → 该院版本自动跟到新包版本（AC-23b/BP-01 AC-16b）
```

## 3. 关键机制口径（贯穿三条子 spec 的共同约定）

### 3.1 版本回写口径（现场版本 = `data/customers.json`，禁臆造库表）
- **不入 MySQL、不建 customers 表**（真库 `db.mjs` 无 customers 表——CU-01 已定文件存）。现场版本落 `data/customers.json` 的 `products`：
  - **新形状** `{ project, subsystems:[{name, version}] }`：按勾选子系统各维护一个版本（`version≤30`）；
  - **旧形状** `{ project, version }`（无 subsystems）：产品级版本，兜底「该产品全部子系统@该产品级 version」。
- **回写只改** `products[project==productId].subsystems[name==subsystem].version`（新）/ `products[project==productId].version`（旧）→ `v_new`。
- **两种触发**：① 手动「一键改版本」`POST /api/customer-version`（FS-16）；② 验证通过后**自动**更到 `bt.pkgVersion`（`bumpSiteVersionForBatch`，FS-16 AC-23b / BP-01 AC-16b）——现场版本自动跟到新包版本，与运营台账一致。
- **同值幂等**：`v_new == 现场当前版本` → 不重复写、不重复留痕（`updatedAt` 可刷新）。
- **留痕**：`customers.json` 每客户 `versionLog[]` 记「谁/何时/哪院/哪产品·子系统/v_old→v_new」（原 NH-3 已落地此方案）。

### 3.2 维保到期回写（旁路 · FS-17）
- 现场端「医院视图」归档条常驻显示该院 `data/customers.json` 的 `maintainEnd`（到期 ≤15 天标黄、已过期标红）+「编辑」入口。
- `POST /api/customer-maintain {site, maintainEnd}` 回写 `maintainEnd`（`c(maintainEnd,20)`）+ 追加 `maintainLog[]`（谁/何时/哪院/from→to）；同值幂等；格式须 `yyyy-MM-dd`（本期不支持清空）；越权 403（判定与 `customer-version` 一致）。
- `GET /api/notifications` 追加维保项（`daysLeft ≤ 15` 含负数=已过期持续提醒）；可见范围：管理员=全部医院、impl=仅 `user.sites`。

### 3.3 更新包跟随产品代码（旁路 · FS-17 · 按 tag / 按批次快照）
- 部署/更新清单**不在 intake 内手工维护**：是**产品代码的一部分**——各**子系统仓** `docs/deploy.json`（或目录形态 `docs/deploy/<版本>.json`）按 git tag 声明该版本 delta 任务 + SQL。
- **当前实现（2026-08-05 二次重构·以此为准）**：发包时运营审核冻结部署清单快照到 `batch.deployPlan`（BP-01 §K / AC-31~36）；实施侧按 `batchId` 读快照渲染（**不再实时读代码、不再实施侧跨版累积**）。
  - `GET /api/field/update-plan?site=&batchId=` 读 `batch.deployPlan` 快照 → 头显 `现场 <from> → 目标 <to>` + 进度 `N/M` + 累积实施任务逐条 + 末尾「执行数据库升级 SQL」单点。
  - `POST /api/field/update-toggle {site, batchId, kind:'task'|'sql', itemId, done}` 勾选，完成度键 = **(批次×医院)** `customer.updateProgress[batchId]`（tasks 桶 + sqlBundle 单点，假删·幂等·越权 403）。
  - `GET /api/field/update-sql-merged?site=&batchId=` 读快照冻结 SQL 正文合并为单 `.sql` 下载（**SQL 系统不执行**，仅列出让实施手动跑、勾「已执行」单点）。
  - 批次未审核部署清单 → `noManifest:true` + 「该批次尚未审核部署清单（运营审核确认后会出现在这里）」，不报错。
- **历史演进**（均已从代码删除，仅存 CHG 留痕）：原 §J 场景1「标准部署清单模板」（`deploy-template`）+ 场景2「批次实施清单」（`batch-task`/`implTasks`）→ 废弃改跟随产品代码；原 §K「实施侧实时读代码 + 跨版累积」（`update-plan?product=&target=`）→ 二次重构为「读批次快照」。首次部署（现场版本空）本次不做（RS-6·下一步）。

### 3.4 数据边界与降级（贯穿全机制）
- **数据权限硬约束**：下载/回写/验证/维保/清单/按批次视图**全部限当前 `impl` 账号 `sites`**（服务层收敛，忽略前端越权传参）；越权 `forbidden`(403)。隔离对齐 FS-01。
- **双域名同步约束**：本机制现场端点除进 `server.mjs` 的 `FIELD_OK` 白名单外，**还须同步进 `FS08_FIELD_API`**（field 域外层闸允许集），否则实施域（`intake.lcpharmacy.cn`）被 `originGate` 判 deny 隐蔽挂掉（对齐 FS-08 · `tools/fs-08.test.mjs` A-drift 守）。
- **BP-01 未上线降级**：按批次视图/下载/改版本/逐单验证入口降级占位、不报错（FS-15 H 组）。
- **时间格式**：展示统一 `yyyy-MM-dd HH:mm`（排期/维保为纯日期 `yyyy-MM-dd`），空值 `—`；文案避 FS-01 A6 禁词（不用「发包」类字样）。

## 1. 用户故事 / 目标
作为**现场实施工程师（`impl`）**，我要在下载更新包后**一键把该医院该产品的现场版本号从 `v_old` 改到 `v_new`**，并对该批次里**我提的每一条工单逐单确认「现场验证过」**（验证不过就**人工反馈/打回**及时处理）；当整批单都验证过 → 触发批次闭环「已交付」、该院版本自动跟到新包版本——以便**现场部署与运营台账版本一致、逐单可追溯、验证结果闭环**，且**绝不看到/操作别账号负责医院的数据**。

- 版本回写**非强制但强提醒**（下载后提示 + 挂提醒，不阻断继续操作）。
- 逐单验证**每单一确认**：验证过 → 该单 `已关闭`；不过 → `已重开`（人工反馈）。
- 全批验证过 → 该医院该产品本批覆盖子系统版本**自动**更到 `pkgVersion`（不再需手点「一键改版本」）。

## 2. 范围
**包含：**
- **一键改版本（版本回写）**：下载后（FS-15 返回 `bumps`）出现改版本提示条 `<医院> <产品/子系统> v_old → v_new` + `一键改版本`；点击 → `POST /api/customer-version`（回写 `data/customers.json` 该医院该产品/子系统版本 `v_old→v_new`）；成功后现场版本更新、提示转「已改版本」。同值幂等。
- **逐单确认「现场验证过」**：批次组内每条覆盖工单（我提的、`待验证` 态）有「确认验证过」✅ 动作 → `POST /api/intake-verify {result:"pass"}`（复用 `intake-transition` `待验证→已关闭`）→ 该单转「已验证/已关闭」；`pass` 后触发 BP-01 闭环检查（全验证过 → 批次「已交付」+ 该院版本自动更到 `pkgVersion`）。
- **验证不过 → 人工反馈**：逐单「反馈问题/打回」动作 → `POST /api/intake-verify {result:"fail", note}`（`intake-transition` `待验证→已重开`，带反馈说明留痕）→ 工单重开、及时处理；批次态不回退。
- **验证通过 → 医院版本自动跟到新包版本**：某院本批全部覆盖工单已关闭 + 批次有 `pkgVersion` → 服务端 `bumpSiteVersionForBatch` 自动把该院该产品本批覆盖子系统版本更到 `pkgVersion`（护栏幂等）。
- **越权与数据隔离**：改版本/逐单验证/反馈全部限当前 `impl` 账号 `sites`，越权 403、别账号数据不可见。
- **幂等**：版本回写同值幂等（`v_new==现场当前版本` 不重复写、不重复留痕）；逐单验证对已 `已关闭` 单重复确认不报错。

**不包含（划归它处）：**
- 按批次视图 / 更新包下载 / 下载触发「已出包→待验证」/ 闭环 tag 显示 / BP-01 未上线降级 → **FS-15**。
- 维保到期回写、更新包实施任务清单 → **FS-17**。
- 批次闭环判定本体 / 医院版本回写兜底遍历（`batch-deliver-check` 内）→ **BP-01**（本条 pass 后调它、并承载「per-hospital 主触发」的自动 bump）。
- 系统视图归档版本、运营 tag 版本下拉（→ FS-03）；本条只管现场版本回写。

## 3. 验收标准（AC · Given-When-Then · 每条可自动化判定）
> ⚠️ 逐单验证依赖 FS-15 下载先把覆盖工单翻到「待验证」；改版本依赖 FS-15 下载返回 `bumps`。BP-01 未上线前不可正式验收（走 FS-15 H 组降级）。

### C. 一键改版本（版本回写 → POST /api/customer-version）
- **AC-1**（原 C/AC-9）Given 改版本提示条的 `一键改版本`，When 点击，Then 弹二次确认（`将 <医院> · <产品/子系统> 现场版本 v_old → v_new，确认？`），确认后调 `POST /api/customer-version {customerId, productId, subsystem?, version:v_new}`。
- **AC-2**（原 C/AC-10）Given 回写成功（`{ok:true}`），When 前端收到，Then：① 提示条转「已改版本」（或移除该条）；② 该医院现场版本更新为 `v_new`（`data/customers.json` 对应 `products[].subsystems[].version`（新）/ `products[].version`（旧）已改，`GET /api/customers` 回读为 `v_new`）；③ 提示「已回写版本号 v_new」。
- **AC-3**（原 C/AC-11 · 同值幂等）Given 版本回写**同值幂等**：`version` == 该医院该产品/子系统现场当前版本，When 调 `POST /api/customer-version`，Then 返回 `{ok:true}` 但**不重复写、不重复留痕**（`updatedAt` 可刷新，版本值不变），前端表现「已是最新版本」。
- **AC-4**（原 C/AC-12）Given `customerId` 不存在 / `productId` 不属该客户 products / `version` 为空，When 调用，Then 返回 `{error:"..."}`（400），不改任何数据。
- **AC-5**（原 C/AC-13 · 越权）Given 越权：`customerId` 对应医院不在当前账号 `sites`，When 调 `POST /api/customer-version`，Then 后端 `forbidden`(403)（`authGate` deny-by-default + 服务层 sites 校验），不写库。
- **AC-6**（原 C/AC-14 · 非强制）Given 回写非强制（NH-1），When 下载后未改版本，Then **不阻断**任何后续操作（提交/切医院/退出均可），仅保留强提醒（非强制）。

### D. 逐单确认「现场验证过」（→ 待验证→已关闭）
- **AC-7**（原 D/AC-15）Given 批次组内某覆盖工单为 `待验证` 态、是我负责医院的单，When 点该单「确认验证过」✅，Then 调 `POST /api/intake-verify {project, id, result:"pass"}`（内部走 `intake-transition` `待验证→已关闭`），成功后该单标签转「已验证/已关闭」，`history` 记一条现场验证留痕（关闭即自动沉淀经验库）。
- **AC-8**（原 D/AC-16）Given 工单**非 `待验证`** 态（如仍 `已出包`，尚未下载触发 `已出包→待验证`），When 点「确认验证过」，Then 后端拒绝（真库现场仅可在 `待验证` 时确认，server.mjs L1292）→ 前端提示「请先下载更新包后再验证」（不报错崩溃）。
- **AC-9**（原 D/AC-17）Given 批次覆盖工单 3 条，我逐条确认验证过，When 最后一条确认后，Then 触发 BP-01 闭环检查（`POST /api/batch-deliver-check {id}`）；全 `已关闭` → 批次转「已交付」，按批次视图该组头 tag 更新为「已交付」（tag 显示由 FS-15 承载）。
- **AC-10**（原 D/AC-23b · 验证通过 → 现场医院版本自动更到新包版本 · 2026-08-07）Given 我负责医院在本批的**全部覆盖工单已关闭**（逐单验证过）、批次有 `pkgVersion`，When `intake-verify` pass（该院最后一单验证过·主触发），Then 服务端自动把**该医院该产品本批覆盖子系统**的现场版本更到 `bt.pkgVersion`（`bumpSiteVersionForBatch`，`data/customers.json` 回写 + 留痕，见 BP-01 AC-16b），响应带 `versionBumped`。**不再需要手点「一键改版本」**——现场版本自动跟到新包版本、与运营台账一致（护栏幂等：无 pkgVersion / 未全关闭 / 找不到医院 → 跳过；已是目标版本 → 不重复）。

### E. 验证不过 → 人工反馈（→ 待验证→已重开）
- **AC-11**（原 E/AC-18）Given 批次组内某 `待验证` 工单验证不过，When 点「反馈问题/打回」并填反馈说明，Then 调 `POST /api/intake-verify {project, id, result:"fail", note:"<反馈>"}`（内部走 `intake-transition` `待验证→已重开`，带反馈留痕），成功后该单转「已重开」、`history` 记反馈说明，工单回到运营/开发处理流。
- **AC-12**（原 E/AC-19）Given 某工单被反馈打回（`已重开`），When 该批次做闭环检查，Then 该批次**不转「已交付」**（该单非 `已关闭`），保持「可下载」等待重新验证（对齐 BP-01 AC-18，批次态不回退）。

### F. 越权与数据隔离
- **AC-13**（原 F/AC-20）Given 越权：`project`/`id` 对应工单不属当前账号 `sites` 内医院（`intakes.site` 不在 sites），When 调 `POST /api/intake-verify`，Then 后端拒绝（`scopedForField` + `intake-transition` 现场态校验），不改工单。
- **AC-14**（原 F/AC-21）Given 改版本 / 逐单验证 各接口，When 换不同 `impl` 账号登录，Then 各自只见/只操作自己 `sites` 内医院数据，互不可见（对齐 FS-01 + §6）。

## 4. 接口契约
> 统一前缀 `/api`；实施端接口按**当前登录用户 `sites`** 收敛，忽略前端越权传参；返回体 `{ok/error}`。**新增端点均需显式加入 `server.mjs` 的 `FIELD_OK` 白名单**，且服务层再按 `sites` 二次校验。
> **⚠️ 双域名同步约束（对齐 FS-08 AC-9b）**：本条 2 个现场端点（`customer-version` / `intake-verify`）除进 `FIELD_OK` 外，**还必须同步加进 `server.mjs` 顶层 `FS08_FIELD_API`**（漏配 → 实施域 `originGate` deny 隐蔽挂掉；`tools/fs-08.test.mjs` A-drift 守）。

### 4.1 🆕 现场版本回写 —— `POST /api/customer-version`
```
POST /api/customer-version
body: { "customerId":"c1a2b3c4", "productId":"psp", "subsystem":"kwsb"(可选·新形状按子系统), "version":"v2.1" }
  →  200 { "ok":true, "customer": {id,name,products:[...],updatedAt} }
     400 { "error":"客户不存在" | "产品不属该客户" | "版本号为空" }
     403 forbidden（越权：customerId 不在当前 impl 账号 sites）
```
- 回写 `data/customers.json`：**新形状** `products[project==productId].subsystems[name==subsystem].version = version`；**旧形状**（无 subsystems）`products[project==productId].version = version`。真实字段见 §5.1（server.mjs L188-215 核对）。
- **幂等**：`version` == 现存版本 → 不改值（`updatedAt` 可刷新）、不重复留痕，仍返回 `ok:true`（AC-3）。
- **留痕**（§6）：记「谁/何时/customerId/productId/subsystem/v_old→v_new」，落 `customers.json versionLog[]`（原 NH-3 已实现此方案）。

### 4.2 🆕 逐单确认验证 —— `POST /api/intake-verify`（薄封装 `intake-transition`）
```
POST /api/intake-verify
body: { "project":"psp", "id":"T-1028", "result":"pass"|"fail", "note?":"反馈说明" }
  →  200 { "ok":true, "lifecycle":"已关闭"|"已重开", "batchDelivered":bool, "versionBumped":[...] }
                                          // pass→已关闭；fail→已重开；batchDelivered=闭环是否达成；versionBumped=自动改版本结果(AC-10)
     400 { "ok":false, "error":"该工单当前不可验证（需处于待验证态）" }    // 非 待验证 态（AC-8）
     403 forbidden（越权 sites / 现场态限制，对齐真库 L1292）
```
- **内部复用真库 `intake-transition`**：`result="pass"` → `待验证→已关闭`；`result="fail"` → `待验证→已重开`（带 `note` 留痕）。真库 L1292：现场（非 admin）仅可在 `待验证` 时 `已关闭/已重开`——本端点即该受限场景的语义封装（原 NH-5 采纳薄封装 `intake-verify`，以便 `pass` 后自动触发 `batch-deliver-check` + 自动 bump）。
- `pass` 后自动调 BP-01 `batch-deliver-check`（该工单所属批次），返回 `batchDelivered` 表示是否全验证过闭环（AC-9）；并按 per-hospital 主触发自动把该院版本更到 `pkgVersion`（AC-10，`versionBumped`）。

## 5. 数据契约
> **对照真实结构核对，禁止臆造列名。**

### 5.1 现场版本（真实已有 · 文件存）—— `data/customers.json`
- 结构（server.mjs L182-215 实测）：`{ id:'c'+4字节hex, name(≤60), level(三甲/三乙/二甲), region(≤40), impl:{name,phone}, status(已开通/未开通), products:[...], versionLog[], updatedAt }`。
- **products 两形状并存**（server.mjs L186-215）：
  - **新形状** `{ project, subsystems:[{name,version}] }`：勾选子系统各维护一个版本（`name` ∈ 该产品 `subsystems[].name`，`version ≤30`）；
  - **旧形状** `{ project, version }`（无 subsystems）：产品级版本，兜底按「该产品全部子系统@该产品级 version」。
- **本条只改** `products[project==productId].subsystems[name==subsystem].version`（新）/ `products[project==productId].version`（旧）→ v_new；**绝不迁 MySQL、绝不建 customers 表**（真库 `db.mjs` 无 customers 表——CU-01 已定文件存）。
- `productId` = `products[].project`（如 `psp`）；`projById(productId)` 有效性校验。
- **版本留痕** `versionLog:[{productId,subsystem,fromVer,toVer,by,at}]`（原 NH-3 已落此）。
- 医院-账号边界 = `accounts.sites`（JSON，负责医院列表）；隔离见 FS-01。

### 5.2 工单联动（复用真库 `intakes` + `TRANSITIONS`，禁臆造）
- **逐单验证过**：`待验证→已关闭`（真库 `TRANSITIONS['待验证']=['已重开']` + 「任意非关闭态→已关闭」放行，server.mjs L523+L1293；现场 L1292 允许 `待验证→已关闭`）。
- **验证不过**：`待验证→已重开`（真库 L1292 现场可 `已重开`）。
- 均复用现有 `intake-transition` 留痕（`history[]`），本条不重造流转。
- **自动 bump**：全院关闭后 `bumpSiteVersionForBatch`→`bumpCustomerVersion` 写 `customers.json`（AC-10 / BP-01 AC-16b），护栏幂等。

## 6. 业务规则 / 非功能
- **数据权限（硬约束）**：改版本/逐单验证/反馈**全部限当前 `impl` 账号 `sites`**（服务层 `scopedForField` 过滤，忽略前端越权传参）；越权 `forbidden`(403)（对齐 FS-01 隔离 + authGate）。
- **按钮级权限**：现场端仅一键改版本、逐单验证/反馈；无定档/建批/上传包/账号管理入口。新写端点默认**不进** `LINK_OK`。
- **逐单验证态约束**：仅 `待验证` 态工单可确认验证/反馈（真库 L1292）；非该态拒绝并前端友好提示（AC-8）。
- **幂等**：① 版本回写同值幂等（AC-3）；② 逐单验证对已 `已关闭` 的单重复确认不报错（transition 校验 + 前端入口收起）；③ 自动 bump 已是目标版本不重复写。
- **闭环不回退**：验证不过 → 工单 `已重开`（人工反馈），**批次态不回退**（对齐 BP-01 AC-18）；全验证过才 `batch-deliver-check` → 「已交付」+ 自动 bump。
- **留痕**：版本回写记「谁/何时/哪院/哪产品版本」落 `customers.json versionLog[]`；逐单验证/反馈复用工单 `history`（`intake-transition` 已留痕）。
- **回写非强制 + 强提醒**：下载后提示 + 强提醒，**不阻断**后续（AC-6）；是否强制/校验规则 NH-1。
- **时间格式**：展示统一 `yyyy-MM-dd HH:mm`，空值 `—`。文案避 FS-01 A6 禁词。

**NEEDS-HUMAN（本条待裁决）：**
- **NH-1 版本回写是否强制 + 校验规则**：下载后是否必须改版本、版本号格式/单调递增校验——待运营/管理确认。当前按「非强制 + 强提醒」落地。

# 进件工单生命周期状态机

把"进件（需求/BUG）"从一次性提交升级为**可流转、可跟踪、可回溯的工单**，支撑开发↔现场闭环。
本 spec 是 M4 的核心契约；数据落 intake-store 的 `<id>.json/.md`（文件即接口）。

## 1. 生命周期状态（`lifecycle`）

| 状态 | 含义 | 谁推进到此 |
|---|---|---|
| `待处理` | 现场刚提交，待三分类/分析 | 现场提交 |
| `分析中` | 平台内 AI 正在/已给初判，待开发决策 | 系统/开发触发分析 |
| `已回复` | 能当场解决，开发已直接回复现场（无需开发改动） | 开发 |
| `已立项` | 判定要开发，已建为工作项 | 开发 |
| `开发中` | 在 steward + 代码仓开发（关联 spec/commit） | 开发 |
| `已出包` | 修复已随某版本(tag)出包 | 开发 |
| `待验证` | 已通知现场，等现场验证 | 开发 |
| `已关闭` | 验证通过 / 已回复被现场确认，闭环完成 | 现场或开发 |
| `已重开` | 验证不通过，回到开发 | 现场 |

> 旧字段 `status`（待处理/沟通中/已归档/已处理）保留兼容：无 `lifecycle` 的历史条目按映射派生（待处理→待处理、沟通中→分析中、已处理/已归档→已关闭）。

## 2. 合法流转（transition）

```
待处理 ──▶ 分析中
分析中 ──▶ 已回复 | 已立项
已回复 ──▶ 已关闭 | 已重开
已立项 ──▶ 开发中
开发中 ──▶ 已出包
已出包 ──▶ 待验证
待验证 ──▶ 已关闭 | 已重开
已重开 ──▶ 开发中 | 分析中
（任意非关闭态 ──▶ 已关闭：开发可强制关闭并注明原因）
```
- 非法流转后端拒绝（返回 `{ok:false,error}`），前端只展示当前态的合法下一步。
- 每次流转追加 `history[]`：`{from,to,by,byRole,at,note}`。

## 3. 数据结构增量（在现有进件对象 e 上新增）

```jsonc
{
  "lifecycle": "待处理",
  "assignee": "",                        // 开发经办人
  "history": [ {"from":"","to":"待处理","by":"张三","byRole":"field","at":"2026-07-08 10:00","note":"提交"} ],
  "analysis": {                          // 平台内 AI 初判（§4）
    "category": "bug|需求|非bug|该版本已修",
    "verdict": "一句话结论",
    "suggestion": "reply|file",         // 建议：直接回复 or 立项
    "detail": "给开发看的分析要点",
    "at": "2026-07-08 10:05", "model": "opus[1m]"
  },
  "resolution": { "commit":"", "pr":"", "fixedVersion":"", "note":"", "at":"" }
}
```
沟通 `chat[]` 的 `role` 扩展：`user`(现场) / `assistant`(平台AI) / `dev`(开发回复)。

## 4. 平台内 AI 分析初判（`/api/intake-analyze`）

输入一条工单 → 读该条 `spec@version`（M2 已具备）+ 正文 → 模型输出**结构化初判**：
- `category`：`非bug`(该版本 spec 本就这样) / `bug`(违反该版本 spec) / `该版本已修`(diff 新版已修复，建议升级) / `需求`(全新诉求)。
- `suggestion`：`reply`(能当场答复，给答复草稿) / `file`(需开发，建议立项)。
- `detail`：可能原因 / 建议先查什么 / 落在哪个模块。
写入 `analysis`，工单转 `分析中`；开发据此一键"回复"或"立项"。**AI 只给建议，最终由开发决策**（守 §12.1）。

## 5. 角色可见/可做（对齐 架构设计 §12.3）
- **现场(field)**：提交、补充、看**本现场**工单与进展、`待验证`时做验证（通过/不通过）。
- **开发(dev)**：分析、回复、立项、流转、关联 commit/version、关闭；看全部。
- M4 先把 role 作为**概念标注**（history 记 byRole）；真正服务端鉴权在 M5。

## 6. 验收标准（AC）
1. **AC1 流转合法性**：对每个状态，只能走第 2 节允许的下一步；非法流转被后端拒绝且不改数据。
2. **AC2 留痕**：任一次流转/回复/分析都在 `history[]` 或 `chat[]` 留一条（含操作人、角色、时间）。
3. **AC3 兼容**：历史无 `lifecycle` 的进件按 §1 映射正常显示、可继续流转。
4. **AC4 AI 初判**：对一条 BUG，`/api/intake-analyze` 能读到 `spec@version` 并返回结构化 `category/suggestion/detail`；未配模型时返回明确提示、不报错。
5. **AC5 闭环可回溯**：一条工单从 待处理 走到 已关闭 后，`.md` 能完整看到"提交→分析→回复/立项→开发→出包→验证→关闭"的时间线。
6. **AC6 md 渲染**：`renderIntakeMd` 输出含 生命周期、流转时间线、分析初判、处理结果(commit/版本) 各区。

## 7. 冒烟（连真库/真模型）
- 造一条绑 repoPath 的项目下的 BUG → analyze 读 `spec@v1.3.0` 得初判 → 立项 → 开发中 → 已出包(关联 v1.4.0) → 待验证 → 现场验证通过 → 已关闭；核 `.md` 时间线完整、`history` 每步有痕。

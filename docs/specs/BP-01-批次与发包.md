> ## 0. 定稿逻辑（唯一事实源 · 2026-07-24 用户拍板）
>
> **批次全链路：**
> ```
> 实施提单(BUG/需求·带图) → 运营【逐单评审】(落实/暂缓/驳回) → 运营【定档】
> → 分批次：该产品所有"已落实"单(跨全部医院合并) → 一个批次(=一条产品线)，内部【按子系统分组】
> → 【导出开发清单】(按子系统·描述清晰·带截图) → 各开发拿清单去 steward 完成开发任务
> → steward 打包 →(外部测试验收，不在本框架)→ 【管理身份上传包】(填包版本/说明/地址 + 转「可下载」)
> → 实施【下载/应用更新包 + 一键改版本】 + 【逐单确认"现场验证过"】(验证不过→人工反馈及时处理)
> → 全批单验证过 → 批次闭环(已交付)
> ```
>
> **本 spec 相对原设计推翻的点（逐条声明）：**
> 1. **【推翻·批次粒度】** 原「批次 = 产品·周期（一周期一包）」→ 改为 **批次 = 一条产品线**（药师工作站一批、合理用药一批），**跨全部医院合并**该产品所有「已落实」单，批次内部**按子系统分组**（kwsb/adr/ysmz…）。**去掉 `uk_product_week` 唯一约束**（不再一周期一批，而是运营定档时按产品新开一批，同产品可先后有多批）。
> 2. **【推翻·时间主导】** 原「固定 1周/N周自动周期 + `batchCycleWeeks` 配置 + 周日 24:00 封板定时任务 + `cycle_weeks` 快照」→ **全部删除**。时间主导改为 **运营需求评审后【定档】**：运营逐单评审 → 定档 → 定档时把该产品所有「已落实（=已立项）」单归成该产品的一个批次。**无固定周期、无自动封板 cron。**
> 3. **【推翻·收集中/封板阶段】** 原状态机 `收集中→待开发会议→开发中→可下载→已交付` + 「收集中」阶段可归入/移出 + `batch-lock` 封板 → **改为**：批次在**定档时创建即含全部已落实单**（无「收集中」游离期）；单个工单的评审归入即入批。新状态机见 §0.第7点。
> 4. **【推翻·test 角色】** 原设想引入独立测试验收角色/节点 → **无 test 角色**：外部测试验收是**框架外**动作，不在本平台建模。包验收后**由管理身份（admin）直接【上传包】**（填包版本/说明/地址 + 转「可下载」）。账号角色仍 `admin/pm/impl`（真库枚举，见 §5），**不新增角色**。
> 5. **【推翻·steward 三接口自动化】** 原 P0 §E「① steward 拉落实清单 ② steward 回写进度 ③ steward 发包」三接口**本期不做自动对接**。改为：
>    - **出站** = 批次【导出开发清单】（按子系统分组的可读/可下载产物，开发拿去 steward 手工做），见 §0.第5.1点 + AC-D 组。
>    - **入站** = **先由运营/管理身份手动【上传包】**转可下载（填包信息），见 AC-E 组。
>    - **steward → intake 自动回写包**（发包接口自动把产物推回 intake）列为**后续增强 / future**，见 §附录·分期 + NH-6，**不在本期**。
> 6. **【新增·实施端动作】** 现场实施新增三类动作（详见 `FS-05`，本 spec 提供批次侧数据/状态支撑）：① 现场更新（下载/应用更新包 + 一键改版本，回写 `customers.json` 该医院该产品版本）；② **逐单确认「现场验证过」**（每工单一个确认 → 该单转「已验证/已关闭」）；③ 验证不过 → **人工反馈**（打回/重开，及时处理）。
> 7. **【定稿·状态机】**（据新逻辑重定，别用原「收集中→待开发会议」）：
>    ```
>    批次：开发中(已导清单) → 可下载(已上传包) → 已交付(全验证过)
>    ```
>    - 批次在**定档时创建**，初始态 = **`开发中`**（已含该产品全部已落实单，可导清单；**无「收集中/封板」阶段**）。
>    - 进/出规则：`开发中 --上传包(admin)--> 可下载 --全批单现场验证过--> 已交付`；不可跨级、不可回退（异常反馈走工单侧 `已重开`，不回退批次态，见 §6）。
>    - 与工单 lifecycle 联动：`已立项(已落实)` --归批--> 工单进批（`data.batch` 回链，态不变，仍 `已立项/开发中`）→ 上传包后覆盖工单转「已出包」→ 现场逐单验证：`已出包→待验证`（下载后）→ 现场确认验证过 `待验证→已关闭`；验证不过 `待验证→已重开`（复用真库 `TRANSITIONS`，见 §5.3）。

## 1. 用户故事 / 目标
作为**运营（admin/pm）**，我要在逐单评审把工单落实后，对某产品**一键【定档】把该产品所有已落实单（跨全部医院合并）归成一个批次、内部按子系统分组**，然后**【导出按子系统的开发清单】**（描述清晰、带截图）发给开发去 steward 做；开发打包、外部测试验收通过后，我以**管理身份【上传包】**（填包版本/说明/地址）把批次转「可下载」；现场实施**下载、一键改版本、逐单确认验证过**；当**全批单都验证过**时批次自动闭环为「已交付」——以便**按产品线稳定分批交付、开发清单可直接落地、现场下载改版本与逐单验证全程可追溯**。

## 2. 范围
**包含：**
- **定档建批**：运营对某产品【定档】→ 系统把该产品当前所有「已落实（`lifecycle=已立项`）且尚未归批」的工单（**跨全部医院合并**）归成一个新批次，初始态 `开发中`，内部**按子系统分组**（`subsystem`）。
- **批次列表**（按产品/状态筛，选择即查 + 分页）+ **批次详情**（产品 / 状态 / 定档时间 / 覆盖工单按子系统分组清单 / 覆盖医院 / 包信息）。
- **批次状态机** `开发中 → 可下载 → 已交付`（§0.第7点），及与工单 lifecycle 的联动。
- **覆盖工单回链**：`batches.ticketIds`（数组）↔ 工单 `intakes.data.batch`（挂 data JSON，不加库列，复用真库范式）。
- **导出开发清单**（出站产物）：按子系统分组，每条含 工单号/类型/标题/**描述(清晰)**/验收标准/AI 初判/涉及医院(跨院合并后哪些医院提了)/现场版本/**截图(media)**。形态：**可下载 Markdown（结构化，含图链接）**（§0.第5.1 + AC-D 组；也可在详情页内可读展示，本期以「可下载 Markdown」为主产物）。
- **上传包（管理身份）**：admin 填包版本 `pkgVersion` / 更新说明 `releaseNote` / 包地址 `artifactUrl` / 上传时间 `releaseTime` → 批次转 `可下载`，覆盖工单转「已出包」。
- **批次闭环判定**：当批次覆盖工单**全部**被现场确认验证过（`已关闭`）时，批次转 `已交付`（可由现场逐单验证动作触发检查，见 §6）。

**不包含（划归它处）：**
- 工单**逐单评审的决策交互本身**（落实/暂缓/驳回）→ 属 `TK-01`（已 accepted，走 `intake-transition`）；本 spec 只**读**「已落实」工单 + 定档时归批。
- 现场端**下载 / 应用更新包 / 一键改版本 / 逐单确认验证过 / 人工反馈 / 按批次视图** → 属 `FS-05`（本 spec 提供批次数据/状态支撑，接口由 FS-05 承载现场侧交互）。
- 现场**版本回写**落 `customers.json` 的具体端点（`POST /api/customer-version`）→ 属 `FS-05`；本 spec 只定义「上传包 → 覆盖工单转已出包」这一步。
- **steward 自动对接三接口**（拉清单 / 回写进度 / 自动发包）→ **future**（§附录·分期 + NH-6），本期不实现。
- **导出清单产物本体的托管/下载路由细节**（若做成服务器生成文件下载）→ 实现期定，本 spec 定其数据结构 + 产物形态。

## 3. 验收标准（AC · Given-When-Then · 每条必须可自动化判定）

### A. 定档建批（跨医院合并 · 按子系统分组）
- **AC-1** Given 产品「药师工作站」下有 3 条「已落实」（`lifecycle=已立项`）且未归批的工单（分属医院甲/乙/丙、子系统 kwsb/adr），When 运营 `POST /api/batch-arrange {product:"psp"}`（定档），Then 新建一个批次落 `batches` 存储：`status="开发中"`、`ticketIds` 含这 3 条工单 id、`product="psp"`、`arrangedAt` 记定档时间、`pkgVersion="-"`、编号形如 `B-<seq>`（§6 编号规则）；且这 3 条工单的 `intakes.data.batch` = 该批次 id（双向回链）；列表能查到它。
- **AC-2** Given 定档时该产品**无**任何「已落实且未归批」工单，When `POST /api/batch-arrange {product:"psp"}`，Then 返回 `{ok:false, error:"该产品当前无可归批的已落实工单"}`，**不创建空批次**。
- **AC-3** Given 同一产品已定档过一批（含工单 T1/T2），此后又有工单 T3「已落实」，When 再次 `POST /api/batch-arrange {product:"psp"}`，Then **新开第二个批次**只含 T3（已归批的 T1/T2 不重复归入）——**同产品可先后多批**（推翻原「一周期一包唯一」）。
- **AC-4** Given 批次覆盖工单跨医院甲/乙/丙、子系统 kwsb/adr，When `GET /api/batch-detail?id=<批次id>`，Then 返回按子系统分组的覆盖工单清单（`groups:[{subsystem, items:[{id,type,title,customer,...}]}]`）+ 去重的覆盖医院列表 + 批次全字段。

### B. 列表 / 详情
- **AC-5** Given `batches` 存储有多个批次，When `GET /api/batches?product=psp&status=开发中`，Then 只返回产品=psp 且状态=开发中的批次；无筛选参数时返回全部，按定档时间倒序（新批在前）；分页参数 `page/size` 生效、返回 `total`。
- **AC-6** Given 批次已上传包（`可下载`），When `GET /api/batch-detail?id=<id>`，Then 返回体含 `pkgVersion/releaseNote/artifactUrl/releaseTime`；未上传包（`开发中`）时这些字段为占位（`pkgVersion="-"`、其余空/`—`）。

### C. 覆盖工单回链
- **AC-7** Given 批次 `B-01` 覆盖工单 `T-1028`，When 读工单 `GET /api/intake-detail?...&id=T-1028`，Then 其 `data.batch === "B-01"`（回链，见 §5.2）；读批次 `batch-detail` 其 `ticketIds` 含 `T-1028`。
- **AC-8** Given 定档时某工单已归入别的批次（`data.batch` 非空），When 再次定档同产品，Then 该工单**不被重复归入**新批次（AC-3 同理，防重复归批）。

### D. 导出开发清单（出站产物 · 按子系统 · 带截图）
- **AC-9** Given 批次 `B-01` 覆盖工单跨子系统 kwsb（2 条）/adr（1 条），When 运营 `GET /api/batch-checklist?id=B-01`（或 `?format=md` 导出），Then 返回**按子系统分组**的开发清单，每条含：`ticketId / type(BUG|需求) / title / desc(描述清晰) / accept(验收标准) / ai(AI初判) / hospitals(涉及医院·跨院合并后哪些医院提了) / siteVersion(现场版本) / media(截图链接数组)`；结构形如 `{batch, product, groups:[{subsystem, items:[...]}]}`。
- **AC-10** Given 同上，When 以 `?format=md` 请求，Then 返回**可下载 Markdown**（`Content-Type: text/markdown` 或 `text/plain`；含子系统分节标题、每单描述、验收标准、截图为图片链接 `![](url)`），内容与 AC-9 的结构数据一致；无截图的单不报错（截图段留空）。
- **AC-11** Given 工单含 `media[]`（截图），When 导出清单，Then 每条截图以可访问链接（复用现有 `/api/intake-media` 或存储 URL）出现在该单条目下；`media` 为空时该单不含截图段但其余字段完整。

### E. 上传包（管理身份 → 可下载）

- **批次 → 工单**：`batches.ticketIds`（数组）。
- **工单 → 批次**：复用**现有** `intakes.data JSON` 内 `batch` 字段（对齐 server.mjs L1305 现有 `to='已立项' 时写 e.batch`；P0 §B「intake.data 加 batch/stewardUC」）。**不新增 `intakes` 列**（真库 `data JSON NOT NULL` 已承载）。`data.stewardUC` 字段保留（若后续 steward 自动回写用），本期不写。
- **归批条件**：定档时选 `lifecycle=已立项` 且 `data.batch` 为空（未归批）的工单，跨全部医院合并（不按 site 过滤）。

### 5.3 工单状态联动（复用真库 `TRANSITIONS`，不重造流转）
真库 `LIFECYCLE`/`TRANSITIONS`（server.mjs L519-525，逐字核对）：
```
已立项 → 开发中；开发中 → 已出包；已出包 → 待验证；待验证 → 已重开（或 已关闭）；已重开 → 开发中/分析中
```
- **上传包**（`/api/batch-release`）：对每条覆盖工单 `intake-transition` 到 **`已出包`**（`from` 须 ∈ `{已立项→开发中→已出包}` 链路；若工单尚在 `已立项`，需先经 `开发中`——**联动细节 NH-5**：上传包时工单可能停在 `已立项`，是否自动补跳 `已立项→开发中→已出包` 或要求先置开发中 → 实现期定，倾向上传包时对覆盖工单批量推到 `已出包`，中间态由 transition 校验，非法态跳过并记 warning，不阻断整批）。
- **现场下载后**：`已出包→待验证`（由 FS-05 下载动作触发，本 spec 不承载）。
- **现场逐单确认验证过**：`待验证→已关闭`（真库 L1292 现场仅可在 `待验证` 时确认，正合逐单验证语义）。
- **现场验证不过**：`待验证→已重开`（真库 L1292 现场可 `已重开`）→ 工单重新走开发，**批次态不回退**（§6）。
- **幂等**：批量 transition 对已在目标态的工单不报错、不重复留痕（真库 transition 已按 `TRANSITIONS` 校验非法态；本 spec 要求批量路径吞掉「非法/已在目标态」并计 skip，不中断整批）。

### 5.4 现场版本 / 覆盖医院（复用 `data/customers.json`，禁臆造）
- 覆盖医院列表：由覆盖工单的 `intakes.site` 去重派生（真库 `intakes.site VARCHAR(80)`）。
- 导清单 `siteVersion`（现场版本）：读 `data/customers.json` 该医院该产品版本——**真实形状**（server.mjs L188-215 核对）：`products:[{project, subsystems:[{name,version}]}]`（新）或 `{project,version}`（旧兼容）。导清单按子系统时取对应子系统版本，旧形状兜底产品级 version，空显 `—`。
- **版本回写**（下载后一键改版本）属 `FS-05`，落 `customers.json` `products[].subsystems[].version`（新）/ `version`（旧）——**本 spec 不写 customers**。

### 5.5 部署/更新清单（跟随产品代码）+ 累积完成态（🆕 2026-08-05 架构重构 · §I）
- **清单事实源 = 产品代码 `docs/deploy.json`**（每子系统仓根 · 按 git tag 读 · 非 intake 文件、非 MySQL）。约定见 `docs/约定-产品部署清单.md`：
  ```jsonc
  {                                                       // 每子系统仓 docs/deploy.json（该 tag 的 delta）
    "tasks": [ { "id":"env",    "title":"环境准备",   "desc":"确认服务器/数据库/网络就绪" } ],  // title 非空·title≤120/desc≤2000
    "sql":   [ { "id":"s1",     "file":"sql/2.8_upgrade.sql", "desc":"本版本升级脚本" },        // file=仓内相对路径（git show <tag>:<file> 读正文）
               { "id":"s2",     "content":"ALTER TABLE ...;", "desc":"内联兜底" } ]              // file 优先；file 缺才用 content（≤20000）
  }
  ```
  **intake 只读**：`readDeployManifest(proj, tag)`（server.mjs·带 (projId,tag) 轻缓存）对该产品每个子系统仓 `git show <tag>:docs/deploy.json` → `JSON.parse` → `normDeployManifest` 规范化（gid=`<子系统>:<id>`）→ 聚合。缺失/JSON非法/tag无文件 → 跳过（不报错）。**废除** `data/version-releases.json`。

## 6. 业务规则 / 非功能
- **批次粒度 = 产品线**（§0.第1点）：一次定档 = 一个产品的一批；跨全部医院合并；内部按 `subsystem` 分组。**无周期、无 `batchCycleWeeks`、无自动封板 cron**（§0.第2点）。
- **批次编号** `B-<seq>`：`seq` 为全局递增序号（简单可读、无产品序歧义；推翻原 `B-{周}{产品序}`）。生成时读现存 `batches` 最大 seq +1（文件存下无并发写压力；若迁表用自增/序列）。**编号规则若需含产品/日期前缀 → NEEDS-HUMAN（NH-7，本 spec 默认 `B-<seq>`）**。
- **状态流转合法性**：仅 `开发中→可下载→已交付` 顺序；跨级/回退拒绝（AC-14 同理）。异常（现场验证不过）在**工单侧**循环（`待验证→已重开→开发中`），**批次态不回退**（AC-18）。
- **闭环判定**：批次转「已交付」当且仅当**全部** `ticketIds` 对应工单 `lifecycle=已关闭`（现场逐单验证过）；判定在现场逐单验证动作后触发（FS-05 调 `batch-deliver-check`）或运营手触（AC-16/17）。
- **数据权限 / 按钮级权限**：批次管理（定档/导清单/上传包/闭环检查）为**运营 admin** 操作（`isAdmin`，含遗留 `dev`）；非 admin（impl）不可，`authGate` deny-by-default + 服务层 `isAdmin` 双层（AC-13）。**`pm` 是否可操作 → NH-1**。
- **操作留痕**：定档/上传包/交付各写 `batches.history`（`{action,by,at,note}`）；工单联动复用工单 `history`（真库 `intake-transition` 已留痕，见「①本项目信息·数据权限/留痕规则来源」）。
- **幂等**：定档对已归批工单不重复归入（AC-3/8）；上传包对非「开发中」批次拒绝（AC-14）；覆盖工单批量 transition 对已在目标态者 skip 不报错（§5.3）。
- **展示格式**：定档/上传/交付时间统一 `yyyy-MM-dd HH:mm`（全局 UI 规范⑫），空值 `—`。
- **性能**：批次列表分页 + 筛选选择即查（全局 UI 规范⑪⑫）。
- **导清单描述清晰 + 带截图**（§0.第5.1）：每单必含 `desc`（描述）、`accept`（验收标准）、`media`（截图链接）；缺字段不报错但清单标注（如「（无验收标准）」）。

**NEEDS-HUMAN（本 spec 待人拍板 · 评审关卡）：**
- **NH-1 pm 权限**：`pm` 能否定档/导清单/上传包（本 spec 默认仅 admin，pm 只读）→ 待运营/管理确认按钮级权限矩阵。
- **NH-2 导出清单产物形态**：`json`+`md 可下载` 是否足够，是否需 zip 打包截图 / 服务器落文件 / 直连 steward 目录（本 spec 默认 md/json 可下载）。
- **NH-3 换包/撤包**：上传包后能否换包/撤回（AC-14 先拒绝重复上传）。
- **NH-4 批次存储形态**：**文件存 `data/batches.json`（建议，与 customers 同范式、不改库）** vs 新增 MySQL `batches` 表——二选一，实现前拍板。
- **NH-5 上传包时工单联动跳态**：覆盖工单若停在 `已立项`（未经开发中），上传包批量转「已出包」是否自动补跳中间态 / 跳过非法态记 warning（本 spec 倾向批量推 `已出包`、非法态 skip 不阻断）。**【第 3 期实现已裁决·选型 A】** batch-release 作为批次驱动系统动作**直接置 `已出包`**（补 history 系统留痕 + fixedVersion，不走中间 `开发中` 态，避免噪音）；已在出包/待验证/已关闭态的工单幂等 skip。见「🚧 实现进度·第 2-3 期」。
- **NH-6 steward 自动回写包（入站自动对接）= future**：本期只做「导出开发清单出站 + 人工上传包入站」；steward→intake 自动发包接口列为后续增强，不在本期。
- **NH-7 批次编号规则**：默认 `B-<seq>`；是否需产品/日期前缀（如 `B-psp-20260724-01`）待定。
- **NH-8 下载计数落点**：`downloads` 由 FS-05 现场下载维护，挂 `batches` 字段还是独立留痕 → 与 FS-05 对齐。

> # 📘 本文是「批次与发包」域的**导读（type: guide）** —— 机制全景 + 数据模型 + 更新流 + 子 spec 地图
>
> **本文不含可验证 AC**（AC 在各 feature spec）。它把批次域的**现状机制**串成一张图，让新人/AI 先看懂「批次是什么、更新包怎么从代码流到现场、工单和批次怎么互相挂」，再按需跳到具体 feature spec。
>
> **⚠️ spec = 现状快照，非变更日志。** 本域历经多次架构重构（周期封板→定档、手工版本登记→跟随产品代码、实施侧实时读代码→发包快照冻结）。**本导读及各 feature spec 只描述最新现行机制**；被取代的旧方案只在 `docs/changes/CHG-*.md` 时间线留证（见 §7）。

## 1. 一句话定位
运营（admin/pm）在逐单评审把工单落实后，对某产品**一键【定档】**把该产品所有已落实单（跨全部医院合并、内部按子系统分组）归成**一个批次（= 一条产品线的一次交付）**；**导出开发清单**发开发去做；开发打包、外部测试通过后，运营以**管理身份【上传包】**转「可下载」并**审核冻结部署清单快照**；现场实施**下载、按快照逐项勾选执行、逐单确认验证过、医院版本自动跟到新包版本**；**全批单验证过 → 批次闭环「已交付」**。以便**按产品线稳定分批交付、开发清单可直接落地、现场更新与逐单验证全程可追溯**。

## 3. 批次数据模型（现状 · 事实源）
> 🚫 已核 `db.mjs`：**`batches` 表不存在**（真库仅 `projects/accounts/sessions/intakes/kb_entries` 5 表；`customers`/`model-api` 为文件存 `data/*.json`）。批次沿用平台既有**文件存**范式，落 `data/batches.json`（NH-4 已裁决 A=文件存不改库，与「不擅改库」护栏一致）。字段契约详见各 feature spec §5，此处只给全景。

**`data/batches.json`（`{batches:[...]}`）核心字段：**
- `id`（`B-<seq>`，全局递增，无产品/周期前缀·NH-7）、`product` / `productName`、`status`（**`开发中 | 可下载 | 已交付`**）。
- `ticketIds[]`（覆盖工单 id，定档跨院合并归入）、`arrangedAt`（定档时间·实现字段名 `createdAt`）、`scheduleDate`（计划交付日期 `yyyy-MM-dd`，可空）。
- `pkgVersion`（上传包前占位 `-`/`""`）、`releaseNote` / `artifactUrl` / `releaseTime`、`deliveredAt`。
- `deployPlan`（发包审核冻结的**部署清单快照**：`{from,to,tasks[],sql[]含content冻结正文,reviewedBy,reviewedAt}`，见 §4）。
- `history[]`（`{action,by,at,note}`；action ∈ `arrange|release|deliver|update|deploy-review|site-version`）。
- ⚠️ 已删 `batch.implTasks`（旧「批次内嵌实施清单」，2026-08-05 重构改为跟随产品代码，见 BP-05）。

**批次 ↔ 工单 双向关联（复用真库 `intakes.data JSON`，不加库列）：**
- 批次→工单：`batches.ticketIds[]`。工单→批次：`intakes.data.batch`（真库 `data JSON NOT NULL` 承载，对齐 server.mjs 现有 `to='已立项' 时写 e.batch`）。两向同步、两边 `history` 留痕。

**批次状态机（现状 · 无「收集中/待开发会议/封板」）：**
```
开发中(已导清单) --上传包(admin)--> 可下载(已上传包) --全批单现场验证过--> 已交付
```
不可跨级、不可回退；现场验证不过在**工单侧**循环（`待验证→已重开→开发中`），**批次态不因单个反馈回退**。与工单 lifecycle 联动：`已立项`--归批-->进批（态不变）→上传包覆盖工单`→已出包`→现场下载`已出包→待验证`→验证过`待验证→已关闭`（不过`→已重开`）。

## 4. 核心更新流：代码=草稿源 → 发包人审可改 → 快照进批次 → 实施用快照（§K · 现行）
> 这是本域**最关键、也最容易被旧文档误导**的机制。**现行**流程（2026-08-05 用户拍板·取代早期「实施侧实时读代码累积」§I）：

```
① 草稿源 = 产品代码 @HEAD
   各子系统仓 docs/deploy/<版本>.json（一版一文件）+ sql/*.sql；intake 只读 clone，git show HEAD:... 读。
        │
② 发包 = 人审核关（运营 admin）
   上传包后（批次已有 pkgVersion）→ batch-deploy-draft 从代码拉 (起始版本, pkgVersion] 累积草稿
   （tasks + sql，SQL 正文一并读出）→ 运营【可增删改】标题/说明/SQL 正文/加条/删条
   → 确认 → batch-deploy-save 冻结进 batch.deployPlan（含 SQL 正文 + reviewedBy/At）。
        │
③ 实施 = 读并执行快照（现场 field）
   按 batchId 读 batch.deployPlan 快照渲染更新计划 → 逐条勾选（update-toggle）
   → 下载合并 SQL（读快照冻结正文，不再读 git）。【不再实时读代码、不在实施侧跨版累积】
        │
④ 完成度按 (批次 × 医院) 记：customer.updateProgress[batchId] = {tasks:{...}, sqlBundle:{...}}（存 intake，不回写产品仓）。
        │
⑤ 验证闭环最后一环：某院本批全部覆盖工单已关闭 → 服务端把该院该产品本批覆盖到的子系统版本自动更到 pkgVersion（AC-16b，见 BP-04）。
```

**为什么这样设计**：早期 §I 让实施侧实时读代码 + 跨版累积，风险是「代码在变、现场看到的清单不稳定」且无人审核关。改为**发包时一次算好 → 运营人审可改 → 快照冻结**：清单在发包那一刻定死进批次，实施读的是冻结快照，稳定、可审、可追溯。首次部署（现场版本空=未部署）本次不做（RS-6·下一步）。

**更新包「跟随产品代码」（§I · 保留为备用 + 数据格式约定源）**：清单/SQL 是产品代码的一部分（子系统仓 `docs/deploy.json` 或目录形态 `docs/deploy/<版本>.json`），intake 只读、不回写产品仓；按 git tag / @HEAD 读、跨子系统聚合、按版本累积。§I 的 `readDeployManifest`（按 tag 读单文件）保留为「首次部署」备用；**实施更新流以 §K 快照机制为准**。数据格式约定见 `docs/开发规范-产品部署清单.md` / `docs/约定-产品部署清单.md`。

## 5. 全链路时序（现状全景）
```
实施提单(BUG/需求·带图) → 运营【逐单评审】(落实/暂缓/驳回·TK-01) → 运营【定档】(BP-02)
 → 分批次：该产品所有"已落实"单(跨全部医院合并) → 一个批次(=一条产品线)，内部【按子系统分组】
 → 【导出开发清单】(按子系统·描述清晰·带截图·BP-03) → 各开发拿清单去 steward 完成开发任务
 → steward 打包 →(外部测试验收，框架外)→ 管理身份【上传包】(填包版本/说明/地址 + 转「可下载」·BP-03)
 → 运营【审核部署清单草稿→冻结快照进批次】(BP-05 §K)
 → 实施【下载/应用更新包 + 按快照勾选执行 + 一键改版本】 + 【逐单确认"现场验证过"】(FS-05)
 → 某院全覆盖工单验证过 → 该院该产品版本自动跟到 pkgVersion(BP-04 AC-16b)
 → 全批单验证过 → 批次闭环(已交付·BP-04)
```

## 6. 鉴权与护栏（全域通用 · 各 feature spec §6 细化）
- **运营侧批次接口**（定档/导清单/上传包/闭环/改元信息/发包审核）= **admin**（`isAdmin`，含遗留 `dev`；`authGate` deny-by-default，需显式进 admin 白名单）；非 admin 403。`pm` 权限矩阵 → **NH-1**。
- **现场侧**（`field/update-*`）= 管理员 + field，**按 `user.sites` 越权收敛**，越权 site 403。
- **禁臆造库表列名**：写持久层前对照 `db.mjs` / `docs/P0-数据模型对账与接口清单.md` 核字段；批次为文件存，工单侧复用 `intakes.data JSON`，均不加库列。
- **时间展示** 统一 `yyyy-MM-dd HH:mm`（纯日期字段如 `scheduleDate` 到 `yyyy-MM-dd`），空值 `—`。

## 8. NEEDS-HUMAN（全域待人裁决 · 汇总，各 feature spec 引用）
- **NH-1 pm 权限**：`pm` 能否定档/导清单/上传包（默认仅 admin，pm 只读）。
- **NH-2 导出清单产物形态**：`json`+`md 可下载` 是否足够，是否需 zip 打包截图 / 服务器落文件 / 直连 steward 目录。
- **NH-3 换包/撤包**：上传包后能否换包/撤回（现 AC-14 先拒绝重复上传）。
- **NH-4 批次存储形态**：**已裁决 A = 文件存 `data/batches.json`**（不改库）；备选 MySQL `batches` 表未采纳。
- **NH-5 上传包时工单联动跳态**：**已裁决 选型 A** = batch-release 作为系统动作直接置 `已出包`（补 history 系统留痕 + fixedVersion，不走中间 `开发中`），已在出包/待验证/已关闭态幂等 skip。
- **NH-6 steward 自动回写包（入站自动对接）= future**：本期只做「导出开发清单出站 + 人工上传包入站」。
- **NH-7 批次编号规则**：默认 `B-<seq>`；是否需产品/日期前缀待定。
- **NH-8 下载计数落点**：`downloads` 由 FS-05 现场下载维护，挂 `batches` 字段还是独立留痕 → 与 FS-05 对齐。

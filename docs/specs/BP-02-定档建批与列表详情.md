## 1. 用户故事 / 目标
作为**运营（admin/pm）**，我要在逐单评审把工单落实后，对某产品**一键【定档】把该产品所有已落实单（跨全部医院合并）归成一个批次、内部按子系统分组**，并能在**列表按产品/状态筛选、进详情看按子系统分组的覆盖工单 + 覆盖医院**；当**落单工单没赶上建批**时，还能**批次侧勾选加/移工单、工单侧指派/换/移批次**——以便**按产品线稳定分批、归批灵活可纠错、覆盖关系全程双向可查**。

## 2. 范围
**包含：**
- **定档建批**：运营对某产品【定档】→ 把该产品当前所有「已落实（`lifecycle=已立项`）且尚未归批」工单（**跨全部医院合并**）归成一个新批次，初始态 `开发中`，内部**按子系统分组**；定档 modal 可勾选子集（默认全选）。
- **批次列表**（按产品/状态筛，选择即查 + 分页 + 定档时间倒序）+ **批次详情**（产品/状态/定档时间/覆盖工单按子系统分组/覆盖医院去重/包信息占位）。
- **覆盖工单双向回链**：`batches.ticketIds[]` ↔ 工单 `intakes.data.batch`（不加库列）。
- **工单↔批次双向编辑**：工单侧指派/换/移批次（`ticket-set-batch`）；批次侧批量加/移工单（`batch-add-tickets` + `ticket-set-batch{batch:''}`）。护栏：仅 `已立项` 工单可归批/换批、仅 `开发中` 批次可增减成员、工单 product == 批次 product、双向引用同步、两边 `history` 留痕。

**不包含（划归它处）：**
- 工单**逐单评审的决策交互本身**（落实/暂缓/驳回）→ `TK-01`（走 `intake-transition`）；本 spec 只**读**「已落实」工单 + 定档归批。
- 导出开发清单 / 上传包 → `BP-03`；批次闭环 / 排期 → `BP-04`；部署清单快照 / 更新流 → `BP-05`。
- 现场端下载 / 改版本 / 逐单验证 / 按批次视图 → `FS-05`。

## 3. 验收标准（AC · Given-When-Then · 每条必须可自动化判定）

### A. 定档建批（跨医院合并 · 按子系统分组）
- **AC-1** Given 产品「药师工作站」下有 3 条「已落实」（`lifecycle=已立项`）且未归批的工单（分属医院甲/乙/丙、子系统 kwsb/adr），When 运营 `POST /api/batch-arrange {product:"psp"}`（定档），Then 新建一个批次落 `batches` 存储：`status="开发中"`、`ticketIds` 含这 3 条工单 id、`product="psp"`、`arrangedAt` 记定档时间、`pkgVersion="-"`、编号形如 `B-<seq>`（§6 编号规则）；且这 3 条工单的 `intakes.data.batch` = 该批次 id（双向回链）；列表能查到它。
- **AC-2** Given 定档时该产品**无**任何「已落实且未归批」工单，When `POST /api/batch-arrange {product:"psp"}`，Then 返回 `{ok:false, error:"该产品当前无可归批的已落实工单"}`，**不创建空批次**。
- **AC-3** Given 同一产品已定档过一批（含工单 T1/T2），此后又有工单 T3「已落实」，When 再次 `POST /api/batch-arrange {product:"psp"}`，Then **新开第二个批次**只含 T3（已归批的 T1/T2 不重复归入）——**同产品可先后多批**（推翻原「一周期一包唯一」，无 `uk_product_week` 唯一约束）。
- **AC-4** Given 批次覆盖工单跨医院甲/乙/丙、子系统 kwsb/adr，When `GET /api/batch-detail?id=<批次id>`，Then 返回按子系统分组的覆盖工单清单（`groups:[{subsystem, items:[{id,type,title,customer,...}]}]`）+ 去重的覆盖医院列表 + 批次全字段。

### B. 列表 / 详情
- **AC-5** Given `batches` 存储有多个批次，When `GET /api/batches?product=psp&status=开发中`，Then 只返回产品=psp 且状态=开发中的批次；无筛选参数时返回全部，按定档时间倒序（新批在前）；分页参数 `page/size` 生效、返回 `total`。
- **AC-6** Given 批次已上传包（`可下载`），When `GET /api/batch-detail?id=<id>`，Then 返回体含 `pkgVersion/releaseNote/artifactUrl/releaseTime`；未上传包（`开发中`）时这些字段为占位（`pkgVersion="-"`、其余空/`—`）。

### C. 覆盖工单回链
- **AC-7** Given 批次 `B-01` 覆盖工单 `T-1028`，When 读工单 `GET /api/intake-detail?...&id=T-1028`，Then 其 `data.batch === "B-01"`（回链，见 §5.2）；读批次 `batch-detail` 其 `ticketIds` 含 `T-1028`。
- **AC-8** Given 定档时某工单已归入别的批次（`data.batch` 非空），When 再次定档同产品，Then 该工单**不被重复归入**新批次（AC-3 同理，防重复归批）。

### L. 工单↔批次双向编辑（🆕 2026-08-06 · 用户反馈：落单工单没赶上建批就归不了批）
> 痛点：一张已立项工单在定档建批之后才进来，`batch-arrange` 一刀切全归、给它只能单独建一批。需要：批次侧勾选工单 + 工单侧指派批次，双向可编。护栏：仅 `已立项` 工单可归批/换批、仅 `开发中` 批次可增减成员、工单 product == 批次 product、双向引用（`e.batch` ↔ `bt.ticketIds`）同步、两边 `history` 留痕。均 admin（未进 FIELD_OK → 非 admin 403）。
- **AC-37**（定档建批·勾选子集）Given 定档建批 modal 列出该产品全部「已立项+未归批」工单（默认全选），When `POST /api/batch-arrange {product, ticketIds:[...]}` 传勾选子集，Then **只归勾中的**（每个仍校验 已立项+未归批+同 product，非法跳过）；**不传 `ticketIds` 则维持原「全部已立项未归批」**（向后兼容 AC-1/3）；勾选集全不可归 → `{ok:false,error:'所勾选工单均不可归批'}`。
- **AC-38**（工单侧指派/换/移批次）Given 工单 `lifecycle=已立项`，When `POST /api/ticket-set-batch {project,id,batch}`，Then `batch=<开发中批次id>` → 指派/换入：旧批（若真实存在且开发中）`ticketIds` 删该 id、新批 `ticketIds` 加（去重）、`e.batch=<id>`、两边 history 留痕；`batch=''` → 移出：从旧批 `ticketIds` 删、`e.batch=''`、留痕；返回 `{ok:true, batch:e.batch}`。**护栏拒绝**（400）：非已立项工单、consult、目标批次不存在/非开发中（`仅开发中批次可增减工单`）、跨 product、原批已锁定（非开发中）不可移出其成员。已在该批 → 幂等 noop。前端工单详情（`inbox.html`·仅已立项）显「当前批次 + 指派下拉（默认列该产品开发中批次 + 移出 + 新建）」，改后漏斗随 `effLifecycle` 归位。
- **AC-39**（批次侧批量加/移工单）Given 开发中批次详情，When `POST /api/batch-add-tickets {batchId, ticketIds:[...]}`（每个复用 AC-38 核心，非法跳过）Then 返回 `{ok:true, added:[...], skipped:[{id,reason}]}`；`batch` 非开发中 → 拒（成员锁定）。移出复用 `ticket-set-batch {batch:''}`。前端 `batches.html` 批次详情（仅开发中）显「添加工单（勾选未归批已立项）+ 每条移出」；可下载/已交付批次不显增减入口（锁定）。

## 4. 接口契约
> 统一前缀 `/api`；运营侧批次接口按 admin 鉴权（`isAdmin`，`authGate` deny-by-default，需显式加入 admin 可达白名单）。**所有端点均为 db.mjs/server.mjs 原无、BP 系列新建。** 出参统一 `{ok/error}` 或 `{...data}`。

### 4.1 本 spec 端点
| 端点 | 方法 | 入参 | 出参 | 说明 |
|---|---|---|---|---|
| `/api/batches` | GET | `product?`, `status?`, `page?`, `size?` | `{items:[batch...], total}` | 列表 + 筛选（选择即查）+ 分页；按 `arrangedAt` 倒序（AC-5） |
| `/api/batch-detail` | GET | `id` | `{item:batch, groups:[{subsystem,items:[{id,type,title,customer}]}], hospitals:[...]}` | 详情：覆盖工单按子系统分组 + 覆盖医院去重（AC-4/6） |
| `/api/batch-arrange` | POST | `{product, ticketIds?, scheduleDate?}` | `{ok, item}` / `{ok:false,error}` | **定档建批**：归入该产品「已落实且未归批」工单（传 `ticketIds` 则只归勾中子集），跨院合并，初始态 `开发中`；`scheduleDate` 见 BP-04（AC-1/2/3/37） |
| `/api/ticket-set-batch` | POST | `{project, id, batch}` | `{ok:true, batch}` / `{ok:false,error}` | 🆕 **工单侧指派/换/移批次**（admin）：仅已立项工单、目标批次须开发中；双向同步 + 两边 history（AC-38） |
| `/api/batch-add-tickets` | POST | `{batchId, ticketIds:[...]}` | `{ok:true, added:[...], skipped:[{id,reason}]}` / `{ok:false,error}` | 🆕 **批次侧批量加工单**（admin）：每个复用 ticket-set-batch 核心，非开发中批次拒（AC-39） |

### 4.2 复用现有端点（不改语义）
| 方法 | 路径 | 用途 | 出处 |
|---|---|---|---|
| GET | `/api/intake-detail` | 定档时读工单 desc/accept/ai/media/version + 回读 `data.batch` | server.mjs |
| GET | `/api/customers` | 覆盖医院去重 + 现场版本 | server.mjs L919 |

> **NH-1 鉴权范围**：批次运营接口按现有 `isAdmin`（含遗留 `dev`）放行；`pm` 是否可定档待人确认（本 spec 默认 admin 全放行、非 admin 403；pm 权限矩阵 → 见 BP-01 导读 §8·NH-1）。

## 5. 数据契约
> 🚫 已核真库 `db.mjs`：**`batches` 表/存储不存在**（现只有 `projects/accounts/sessions/intakes/kb_entries` 五表；`customers`/`model-api` 为文件存 `data/*.json`）。批次落文件存 `data/batches.json`（NH-4 已裁决 A=文件存）。工单侧复用现有 `intakes.data JSON`（不加库列）。

### 5.1 批次存储 —— 文件存 `data/batches.json`（NH-4 已裁决 A）
> 与 `customers.json`/`model-api.json` 同范式（server.mjs `loadCustomers/saveCustomers` 同款），批次为运营低频写、量小 → 文件存，无需改库、不加表，与「不擅改库」护栏一致。备选 MySQL `batches` 表未采纳（迁表时字段名转 snake_case 一一对应）。

**`data/batches.json` 结构（本 spec 涉及字段；完整字段见 BP-01 导读 §3）：**
```jsonc
{ "batches": [ {
  "id":          "B-01",              // 批次编号 B-<seq>（§6；seq 全局递增）
  "product":     "psp",               // 产品 id（对齐 projects.id / intakes.version 归属 / customers.products[].project）
  "productName": "药师工作站",          // 冗余产品名（展示用，读时可由 projById 派生，落存可选）
  "status":      "开发中",             // 开发中 | 可下载 | 已交付
  "ticketIds":   ["T-1028","T-1025"], // 覆盖工单 id 数组（定档归入 · 跨院合并）
  "arrangedAt":  "2026-07-24 10:30",  // 定档时间（建批时间）【实现字段名=createdAt】
  "pkgVersion":  "-",                 // 包版本（上传包前占位 "-"/实现空串）
  "history":     [ { "action":"arrange|update", "by":"<username>", "at":"...", "note":"..." } ]
} ] }
```
- **状态枚举**：`开发中 | 可下载 | 已交付`（无「收集中/待开发会议/封板」）。
- **无唯一约束**：同产品可先后多批（AC-3）；批次 id 全局唯一即可（`B-<seq>`）。

### 5.2 批次 ↔ 工单 关联（复用真库 `intakes.data JSON`，不加列）
- **批次 → 工单**：`batches.ticketIds`（数组）。
- **工单 → 批次**：复用**现有** `intakes.data JSON` 内 `batch` 字段（对齐 server.mjs 现有 `to='已立项' 时写 e.batch`；P0 §B「intake.data 加 batch/stewardUC」）。**不新增 `intakes` 列**（真库 `data JSON NOT NULL` 已承载）。`data.stewardUC` 字段保留（若后续 steward 自动回写用），本期不写。
- **归批条件**：定档时选 `lifecycle=已立项` 且 `data.batch` 为空（未归批）的工单，跨全部医院合并（不按 site 过滤）；传 `ticketIds` 时再交集勾选子集（AC-37）。

### 5.3 现场版本 / 覆盖医院（复用 `data/customers.json`，禁臆造）
- 覆盖医院列表：由覆盖工单的 `intakes.site` 去重派生（真库 `intakes.site VARCHAR(80)`）。
- 现场版本读 `data/customers.json` 该医院该产品版本——**真实形状**（server.mjs L188-215 核对）：`products:[{project, subsystems:[{name,version}]}]`（新）或 `{project,version}`（旧兼容）。

## 6. 业务规则 / 非功能
- **批次粒度 = 产品线**：一次定档 = 一个产品的一批；跨全部医院合并；内部按 `subsystem` 分组。**无周期、无 `batchCycleWeeks`、无自动封板 cron**。
- **批次编号** `B-<seq>`：`seq` 为全局递增序号（简单可读、无产品序歧义；推翻原 `B-{周}{产品序}`）。生成时读现存 `batches` 最大 seq +1（文件存下无并发写压力；若迁表用自增/序列）。**编号规则若需含产品/日期前缀 → BP-01 导读 §8·NH-7，本 spec 默认 `B-<seq>`**。⚠️ 孤儿批次号导致建批卡死已修（见 CHG-batch-arrange-孤儿批次号导致建批卡死）。
- **双向编辑护栏**（§L）：仅 `已立项` 工单可归批/换批、仅 `开发中` 批次可增减成员；工单 product == 批次 product；双向引用同步；两边 `history` 留痕；已在目标批幂等 noop。均 admin，非 admin 403。
- **数据权限 / 按钮级权限**：定档 / 双向编辑为**运营 admin** 操作（`isAdmin`，含遗留 `dev`）；非 admin（impl）不可，`authGate` deny-by-default + 服务层 `isAdmin` 双层。**`pm` 是否可操作 → NH-1**。
- **操作留痕**：定档写 `batches.history`（`{action:'arrange',by,at,note}`）；双向编辑两边各写 history；工单联动复用工单 `history`（真库 `intake-transition` 已留痕）。
- **幂等**：定档对已归批工单不重复归入（AC-3/8）；工单已在目标批 noop（AC-38）。
- **展示格式**：定档时间统一 `yyyy-MM-dd HH:mm`（全局 UI 规范⑫），空值 `—`。
- **性能**：批次列表分页 + 筛选选择即查（全局 UI 规范⑪⑫）。

**NEEDS-HUMAN**（引用 BP-01 导读 §8）：**NH-1** pm 权限；**NH-4** 批次存储形态（已裁决 A=文件存）；**NH-7** 批次编号规则（默认 `B-<seq>`）。

## 1. 这块是什么（一句话）
作为**运营 / 管理员**，维护一份「客户（现场 / 医院）台账」——每家医院的名称、等级、地区、负责实施人、开通状态、上了哪些产品及各自版本、工单数、维保到期、激活文件等；并让**提交需求 / BUG 时选客户即自动带出产品 + 版本**，把工单对齐到正确的客户与版本。

## 2. 关键事实 · 存储在哪（**先看这里，禁臆造**）
> ⚠️ **客户 / 医院数据是 JSON 文件，不是 MySQL 表。** 真库 `db.mjs init()` 只有 **5 张表**（`projects` / `accounts` / `sessions` / `intakes` / `kb_entries`），**无 `customers` 表**（连本地真库 `SHOW TABLES` 已确认，扩字段后仍不建表）。是否迁 MySQL = **NEEDS-HUMAN**（见 §5 待决策 1），批准前**不建表 / 不加列 / 不改 db.mjs**。

### 3.1 `products[]` 两形状并存（2026-07-23 裁决 · 向后兼容 · 不破坏性迁移）
`normProduct()`（L413-427）产出两种形状，**照存照读**：
- **新形状** `{ project, subsystems:[{name, version}] }`：勾选的子系统各维护一个版本；`name` 须 ∈ 该产品 `subsystems[].name`（`normProduct` 用 `subsystemNames(proj)` 校验，不命中丢弃、防臆造），`version` = `String().trim().slice(0,30)`、按 `name` 去重。空 `subsystems:[]` 仍保留该产品（实施端兜底显全部）。
- **旧形状** `{ project, version }`（无 `subsystems` 字段）：产品级版本，照存照读；消费方（实施端 `buildSubOptions`/`currentArchive`/`renderHospChip`、`custProductVersion`/`custSubVersion`）遇无 `subsystems` → 兜底按「该产品全部子系统 @ 该产品级 version」处理（行为不变，绝不删老字段、不强迁）。
- `project` = 产品 id（如 `hlyy`），展示映射为产品中文名（`projById` / `pname()` / `/api/projects`），未知 id 回退显示 id。

## 4. 关系图 · 关联键（重名串号 = NEEDS-HUMAN）
```
                     account.sites (JSON, MySQL·唯一真源)
                            │  含医院名 ⇒ 该账号负责该院
        双向写穿(CU-03 AC-20) │  反查派生(CU-03 AC-19)
                            ▼
customers.json.name ◀────────────────▶ customer.impl (读时派生, 死值不信)
        │  === (医院名字符串，重名会串号)
        ├──────────────▶ intakes.site (MySQL) ⇒ ticketCount 派生 (CU-02 AC-18)
        └──────────────▶ account.sites 元素 ⇒ 实施端可见性 + 全后端隔离 scopedForField 唯一认它
customer.products[].project === projById(id) (projects 表) ⇒ 产品中文名 / 子系统全集校验
customer.products[].subsystems[].name === projById(project).subsystems[].name ⇒ 子系统校验
```
**唯一关联键 = 医院名字符串**（`account.sites` 元素 `===` `customer.name` `===` `intakes.site`）。真库无 `customerId` 列，**重名会串号 = NEEDS-HUMAN**（见 §5 待决策 3/4）。

## 5. 全局 NEEDS-HUMAN / 待决策清单（逐项待批 · 不阻塞已落地部分）
> 已落地：原型 UI（整宽表格 + 抽屉 + 筛选分页）+ 扩字段 level/region/impl/status（走文件）+ ticketCount 按 site↔name 派生 + impl↔账号双向写穿 + 激活文件 + 维保回写。下面各项需人拍板，涉及迁库/改库的**批准前不动**。

1. **是否迁 MySQL `customers` 表**——推荐迁（利于按负责人 / 状态查、加 `customerId` 精确关联工单数）；**批准前不建表、不改 db.mjs**。本单先扩文件结构过渡。（对应 `00-运营后台-spec清单.md` 决策 3、原 DM-01 客户迁库并入 CU-01 §5。）
2. **`name` 长度统一 60 vs 40**：代码 / 本单实际 60，原型 40——需人定一个值，前后端（+ 若迁库则库）对齐。本单暂用 60（兼容存量部署）。
3. **医院名 `name` 是否唯一**：无唯一约束；作工单 `site` / `account.sites` 关联键时重名会串号——需人拍板（迁库可加 `customerId` 精确关联根除）。
4. **工单数关联键**：本单落地为 `intakes.site ↔ customers.name` **按名称匹配**（含全部非 consult 工单）。是否改为加 `customerId` 列精确关联（要改 `intakes` 表结构，另立）、是否排除已关闭工单——待决策。
5. ~~**负责实施人来源**：本单为自由文本输入。~~ **【2026-07-22 已定版】** 实施人**姓名**改为**账号台账下拉**（`#edImplName`，候选 = `/api/accounts` 中 `role∈{impl,pm}` 且启用的账号），**电话取自账号 `accounts.phone`**（AM-01 新增列，单一来源）；2026-07-23 进一步定为**唯一真源 = `account.sites`、读时派生**（CU-03 AC-19~21）。
6. **停用 / 开通独立切换 + 留痕**：本单状态由抽屉编辑改、删除为硬删、无操作日志。是否加独立「停用 / 开通」行操作 + 软删 / 留痕——待决策。

## 6. 全局护栏（两条子 spec 共用）
- **🚫 禁臆造库表列名**：客户走**文件** `data/customers.json`（字段见 §3），**不是表**；工单关联源 = `intakes.site`（真库现有列，`VARCHAR(80)`）。查不到对应字段 → 标 `NEEDS-HUMAN` 停下。
- **权限**：`customer-save` / `customer-delete` / `activation/generate` = **仅管理员**（不在 `FIELD_OK`/`LINK_OK`/`FS08_FIELD_API`，`authGate` deny-by-default；field 域经 `originGate` deny→403）；`GET /api/customers` **在 `LINK_OK`/`FIELD_OK` 白名单**（同时供提交端现场下拉，现场侧只用 `id/name/products`——扩字段对现场无害）。
- **时间展示**：`updatedAt` 由 `nowStamp()` 生成，已是 `yyyy-MM-dd HH:mm`（对齐全局 UI 规范第 12 条）。
- **界面基线**：部署页 `public/customers.html`（对齐原型 `prototype/admin/customers.html`）为唯一前端基线。
- **测试**：`tools/cu-01.test.mjs` 连本地真库冒烟（`SHOW TABLES` 断言扩字段后仍无 `customers` 表 + 5 基线表在；`SHOW COLUMNS FROM intakes` 断言 `site VARCHAR(80)`）；客户走文件，测试备份 / 还原 `data/customers.json`，不污染真库。

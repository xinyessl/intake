## 1. 用户故事 / 目标
作为**运营（admin）**，我要在批次的覆盖工单**全部被现场逐单确认验证过**时让批次**自动闭环「已交付」**，并在某医院本批全部覆盖工单验证过时**把该院该产品本批覆盖的子系统版本自动更到新包版本**（不再停在老值、无需手点「一键改版本」）；同时我要能在**定档时填计划交付日期、之后任意状态随时改**——以便**交付闭环有据可查、医院版本随发布自动跟包、排期可持续调整**。

## 2. 范围
**包含：**
- **批次闭环判定**：当批次覆盖工单**全部**被现场确认验证过（`lifecycle=已关闭`）时，批次转 `已交付`（现场逐单验证动作后由 FS-05 调用，或运营手触 `batch-deliver-check`）。
- **验证过 → 医院版本跟到新包版本**（AC-16b · 发布闭环最后一环）：某院本批全部覆盖工单已关闭 → 服务端把该院该产品本批实际覆盖到的子系统版本更到 `pkgVersion`（新形状写 `subsystems[name].version`、旧形状写 `version`；未覆盖子系统不动·宁少勿错）。
- **排期时间**（计划交付日期 `scheduleDate` `yyyy-MM-dd`，可空）：定档可填、详情任意状态可改，列表/详情展示。

**不包含（划归它处）：**
- 定档建批 / 列表详情 / 双向编辑 → `BP-02`；导清单 / 上传包 → `BP-03`；部署清单快照 / 更新流 → `BP-05`。
- 现场端下载 / 应用更新包 / 一键改版本（手动）/ 逐单确认验证过 / 人工反馈 / 按批次视图 → `FS-05`（本 spec 提供闭环判定 + 版本回写服务支撑，现场逐单交互由 FS-05 承载）。

## 3. 验收标准（AC · Given-When-Then · 每条必须可自动化判定）

### F. 批次闭环（全验证过 → 已交付）
- **AC-16** Given 批次 `B-01`「可下载」、覆盖工单 3 条，其中 2 条已被现场确认验证过（`lifecycle=已关闭`）、1 条尚未，When 触发闭环检查（现场逐单验证动作后由 FS-05 调用，或运营 `POST /api/batch-deliver-check {id:"B-01"}`），Then 批次**仍为「可下载」**（未全验证）。
- **AC-17** Given 同上但 3 条全部已验证过（全 `已关闭`），When 触发闭环检查，Then 批次转「已交付」；`GET /api/batches?status=已交付` 能查到它。
- **AC-18** Given 某覆盖工单现场验证不过 → 走工单侧 `待验证→已重开`（FS-05 动作），When 闭环检查，Then 批次**不转已交付**（该单未 `已关闭`），保持「可下载」等待重新验证——**批次态不因单个反馈回退**（异常在工单侧循环）。
- **AC-16b【验证通过 → 医院版本更到新包版本 · 发布闭环最后一环 · 2026-08-07】** Given 批次有 `pkgVersion`（已出包），某医院在本批的**全部覆盖工单已关闭**（现场逐单验证过）When 现场 `intake-verify` pass（per-hospital 主触发）或 `batch-deliver-check` 转「已交付」（兜底遍历各覆盖医院）Then 服务端 `bumpSiteVersionForBatch`→`bumpCustomerVersion` 把**该医院该产品本批实际覆盖到的子系统**版本更到 `bt.pkgVersion`（新形状写 `subsystems[name].version`、旧形状写 `pr.version`；未覆盖子系统不动·宁少勿错），`saveCustomers` + `versionLog[]` + 批次 `history` 记 `site-version` 留痕。**护栏/幂等**：无 pkgVersion / 未全关闭 / 台账无该医院 → 跳过不报错；已是目标版本 → 不重复写。响应带 `versionBumped:[{site,bumped:[{subsystem,fromVer,toVer}]}]`。闭链：出包 → 现场下载 → 逐单验证 → **医院版本自动跟到新包版本**。

### G. 排期时间（计划交付日期 · 2026-07-26 用户反馈补）
> 定档建批时没处填「排期时间/计划交付日期」，建完也没处改。补一个可空的 `scheduleDate`（纯日期 `yyyy-MM-dd`），定档可填、详情可改，列表/详情展示。
- **AC-19** Given 运营定档建批时填了排期时间，When `POST /api/batch-arrange {product:"psp", scheduleDate:"2026-08-15"}`，Then 批次落 `scheduleDate="2026-08-15"`（`yyyy-MM-dd`）；**不填**（缺省）→ `scheduleDate=""`（允许后补）；**非法格式**（如 `2026/8/15`）→ 规范化为 `""`（**不报错**、正常建批）。
- **AC-20** Given 批次已建（有/无排期），When `GET /api/batches`（列表）或 `GET /api/batch-detail?id=<id>`，Then 返回体含 `scheduleDate`（原样返回，无排期为空串；前端未设时显「未排期」）。
- **AC-21** Given 已建批次（**任意状态**：开发中/可下载/已交付都允许运营调整计划），当前登录 admin，When `POST /api/batch-update {id:"B-01", scheduleDate:"2026-08-20"}`，Then `scheduleDate` 改成功、回读一致、`history` 记 `action:"update"` 留痕、**不改批次状态**；非法日期 → 规范化为空（清排期，不报错）；**非 admin → 403**（`authGate` deny-by-default，未进 FIELD_OK/LINK_OK）；**批次不存在 → 404**。本期 `batch-update` 只开放改 `scheduleDate`（+ 包信息，见 §4），预留结构可扩别的元字段。

## 4. 接口契约
> 统一前缀 `/api`；运营侧批次接口按 admin 鉴权（`isAdmin`，`authGate` deny-by-default）。出参统一 `{ok/error}` 或 `{...data}`。

### 4.1 本 spec 端点
| 端点 | 方法 | 入参 | 出参 | 说明 |
|---|---|---|---|---|
| `/api/batch-deliver-check` | POST | `{id}` | `{ok, item, delivered:bool, versionBumped:[{site,bumped:[{subsystem,fromVer,toVer}]}]}` | 闭环检查：全覆盖工单 `已关闭` → 转「已交付」；兜底遍历各覆盖医院 bump 版本（AC-16~18/16b；FS-05 现场逐单验证后调用，或运营手触） |
| `/api/batch-update` | POST | `{id, scheduleDate?, pkgVersion?, artifactUrl?, releaseNote?}` | `{ok, item}` / `{ok:false,error}` | **改批次元信息**（admin）：改 `scheduleDate`（排期）/ 包信息；任意状态可改，`history` 记 `update`；非 admin 403 / 非法 id 404（AC-21）。⚠️ 2026-08-05 架构重构删 `implTasks` 分支（批次不再内嵌实施清单，见 BP-05） |
| `/api/batch-arrange` | POST | `{product, ticketIds?, scheduleDate?}` | `{ok, item}` | 定档建批（主体见 BP-02）；本 spec 关注可选 `scheduleDate`（非法/空存空）（AC-19） |

> 版本回写主触发 `POST /api/intake-verify`（现场 per-hospital，复用 `intake-transition`，端点属 **FS-05**）；本 spec 提供 `bumpSiteVersionForBatch`/`bumpCustomerVersion` 服务 + `batch-deliver-check` 兜底遍历。

### 4.2 复用现有端点（不改语义）
| 方法 | 路径 | 用途 | 出处 |
|---|---|---|---|
| POST | `/api/intake-transition` | 现场逐单验证 `待验证→已关闭/已重开`（闭环判定读结果） | server.mjs（L1292 现场仅 `待验证→已关闭/已重开`） |
| GET | `/api/customers` | 版本回写读/写医院该产品版本 | server.mjs L919 |

## 5. 数据契约
> 🚫 已核真库 `db.mjs`：批次落文件存 `data/batches.json`（NH-4 已裁决 A）；医院版本落文件存 `data/customers.json`（不入库）；工单侧复用 `intakes.data JSON`。

### 5.1 批次存储 —— 闭环/排期相关字段（`data/batches.json`）
```jsonc
{ "batches": [ {
  "id":"B-01", "product":"psp", "status":"已交付", "pkgVersion":"v2.1",
  "scheduleDate":"2026-08-15",  // 排期时间（计划交付日期，yyyy-MM-dd）；定档可带、详情可改；空=未排期，非法格式规范化为空（AC-19~21）
  "deliveredAt":"2026-08-16 10:00", // 闭环（已交付）时间
  "history":[ { "action":"deliver|update|site-version", "by":"<username>", "at":"...", "note":"..." } ]
} ] }
```
- 状态枚举 `开发中 | 可下载 | 已交付`；仅 `开发中→可下载→已交付` 顺序，跨级/回退拒绝；异常（现场验证不过）在**工单侧**循环，**批次态不回退**（AC-18）。

### 5.2 工单状态联动（复用真库 `TRANSITIONS`）
- **现场逐单确认验证过**：`待验证→已关闭`（真库 L1292 现场仅可在 `待验证` 时确认）。
- **现场验证不过**：`待验证→已重开`（真库 L1292）→ 工单重新走开发，**批次态不回退**。
- **闭环判定**：批次转「已交付」当且仅当**全部** `ticketIds` 对应工单 `lifecycle=已关闭`（现场逐单验证过）。

### 5.3 医院版本回写（AC-16b · 复用 `data/customers.json`，禁臆造）
- 回写落 `data/customers.json` 该医院该产品——**真实形状**（server.mjs L188-215）：新形状 `products:[{project, subsystems:[{name,version}]}]` 写 `subsystems[name].version`；旧形状 `{project,version}` 写 `version`。
- **只更本批实际覆盖到的子系统**（由该院覆盖工单 `subsystem` 派生），未覆盖子系统不动（宁少勿错）。
- 留痕 `versionLog[]`（挂 customer）+ 批次 `history` 记 `site-version`。**幂等**：无 pkgVersion / 未全关闭 / 台账无该医院 → 跳过不报错；已是目标版本 → 不重复写。

## 6. 业务规则 / 非功能
- **闭环判定**：批次转「已交付」当且仅当**全部** `ticketIds` 对应工单 `lifecycle=已关闭`；判定在现场逐单验证动作后触发（FS-05 调 `batch-deliver-check` 或 `intake-verify`）或运营手触（AC-16/17）。
- **状态流转合法性**：仅 `开发中→可下载→已交付`；跨级/回退拒绝；异常在**工单侧**循环（`待验证→已重开→开发中`），**批次态不回退**（AC-18）。
- **版本回写护栏**（AC-16b）：per-hospital 全关闭才 bump；只动覆盖子系统；幂等（同值不重复写、缺 pkgVersion/未全关闭/无台账跳过不报错）。
- **排期**：`scheduleDate` 可空/非法存空（不报错）；定档可填、任意状态详情可改（AC-19~21）；纯日期 `yyyy-MM-dd`（原生 `<input type=date>`）。
- **数据权限 / 按钮级权限**：闭环检查 / 改排期为**运营 admin**（`isAdmin`，含遗留 `dev`）；非 admin 403（AC-21）。现场 `intake-verify` 触发路径属 FS-05（管理员+field·按 sites 收敛）。**`pm` → NH-1**。
- **操作留痕**：交付写 `batches.history`（`{action:'deliver',...}`）；改排期/包信息 `{action:'update',...}`；版本回写 `{action:'site-version',...}` + customer `versionLog[]`。
- **展示格式**：交付时间 `yyyy-MM-dd HH:mm`（全局 UI 规范⑫）；`scheduleDate` 纯 `yyyy-MM-dd`；空值 `—`/「未排期」。

**NEEDS-HUMAN**（引用 BP-01 导读 §8）：**NH-1** pm 权限；**NH-8** 下载计数落点（`downloads` 由 FS-05 现场下载维护，与 FS-05 对齐）。

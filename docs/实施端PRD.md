# 收件平台 · 实施端（现场提交端）产品需求文档 PRD

> 版本：v1.0 · 状态：开发评审稿
> 配套原型：`redesign.html`（① 实施端 · 现场提交）
> 关联文档：《运营端 PRD》（`运营端PRD.md`）—— 数据模型 / 后端规范 / 接口契约与本文共用
> 技术栈：**与收件平台运营端同栈**——Node.js 零依赖原生 `http`（单文件 `server.mjs`）+ `mysql2` + MySQL；前端**原生 HTML/JS**（`public/*.html` + `assets/theme.css` 靛蓝设计系统 + `assets/ui.js`），图标 Tabler 本地字体。**不使用 Vue/Element/Vite/Java**（那是被本平台跟踪的产品的栈，非本平台）。部署：Docker `node:20-slim`，`node server.mjs`。

## 1. 产品概述

### 1.1 定位
**实施端**给**现场实施工程师 / 产品**使用：以**医院为主线**，把现场遇到的需求 / BUG / 咨询，通过 **AI 对话**快速提交并标准化归档到运营端；同时看自己负责医院的**批次进度**、**下载更新包**、**回写现场版本号**。

一句话：现场只管"说清楚问题"，AI 负责"判类型 + 补要素 + 归档"，运营端接住后进入开发交付流。

### 1.2 与运营端的关系
```
实施端（本文）                          运营端
─────────────                        ─────────────
AI 对话提交 需求/BUG/咨询  ──────────▶  工单管理（待评审）→ 开发会议决策 → 批次
看批次进度 / 下载更新包    ◀──────────  批次「可下载」（steward 发包）
回写现场版本号            ──────────▶  客户台账版本更新
```
- 实施端**只提交与查看**，不做决策/开发；决策与开发在运营端 + steward。
- 现场账号、负责医院、产品版本**均由运营端分配/维护**（实施端不自助添加医院/产品）。

### 1.3 角色
| 角色 | role | 说明 |
|---|---|---|
| 实施工程师 / 产品（现场） | `field` | 实施端唯一使用者；绑定负责的医院（sites）；只见/操作自己负责医院数据 |
| 免登录访客 | link | 凭运营端生成的**提交链接 token** 打开的干净提交页（只提交，无导航） |

### 1.4 名词表
| 名词 | 说明 |
|---|---|
| 工作空间 | 一个现场账号登录后的视图；**按账号隔离**，只含其负责的医院 |
| 医院视图 / 系统视图 | 顶部维度：以医院为主线 / 忽略医院按系统聚合（跨我负责的全部医院） |
| 子系统（子项目） | 产品下的一个代码仓，如 合理用药 下的 审方/干预/点评… |
| 批次 | 运营端按「产品·周」聚合的交付包；对现场 = 一个可下载的**更新包 + tag 版本** |
| 现场版本 | 某医院某产品当前实际运行的版本（台账维护） |
| 运营维护版本(tag) | 运营端/steward 为产品发布的版本 tag（= 批次产物版本） |

## 2. 整体架构

### 2.1 技术栈
**与收件平台运营端完全同栈**（落地即现有 `server.mjs` / `public/*.html`）。实施端是同一 Node 平台里的现场端页面，复用同一套 `theme.css` 设计系统 / `ui.js` 弹窗助手 / `/api` 层。

- 前端：**原生 HTML/JS**——新增 `public/field.html`（工作空间 SPA：登录门 + 医院/系统视图 + 右侧对话 + 待办），复用 `assets/theme.css`（靛蓝设计系统）+ `assets/ui.js`；图标 Tabler（本地字体，离线可用）。**无构建步骤、无框架**（不引入 Vue/Element/Vite/Pinia）。
- 后端：**同一 `server.mjs`**（Node 零依赖原生 `http` 单文件）、同一 MySQL 库（真实五表 `projects/accounts/sessions/intakes/kb_entries` + 文件存 `data/customers.json`），新增的实施端 `/api/field/*` 端点按当前登录用户 `accounts.sites`（负责医院）数据权限收敛。
- **部署（两域名）**：admin（运营后台）与 field（实施端）各用一个**完全独立的域名**，但**共用同一 `server.mjs` + 同一 MySQL**——只在 web/域名层拆：两个 nginx vhost，各自 `/api/*` 同源反代到同一后端（免 CORS），各域名独立登录会话，域名层 deny-by-default 只暴露各自页面/接口。详见规约 `FS-08 双域名部署与访问隔离`。

> 注：本文若干处用 `intake_*` 概念表名、`role='field'` 等，均为需求视角写法；**真实落地映射**（如 `intake_ticket→intakes` 表、`role='field'→'impl'`、`intake_customer→data/customers.json`、`intake_batch→待运营端 BP-01 建 batches 表`）见 `docs/specs/00-实施端-spec清单.md` §4 映射表，实现以真实库/端点为准，禁臆造。

### 2.2 前端结构（实施端部分 · 原生 HTML/JS，无框架）
```
public/
├── field.html            # 实施端工作空间单页：登录门 + 顶部维度切换(下拉 + 平铺 tab) + 左侧提交清单 + 右侧 AI 对话 + 待办 popover
│                         #   业务逻辑以页面内 <script> 分区实现（auth/dimension/list/chat/todo/version），
│                         #   对应原型 redesign.html 的各 IIFE 脚本块（非 Vue 组件/composable）
├── submit.html           # 复用：免登录访客干净提交页（已存在，token 校验走 linkUserFrom）
└── assets/
    ├── theme.css         # 复用：靛蓝设计系统（与运营后台同一份 Design Token + 组件）
    └── ui.js             # 复用：uiConfirm / uiAlert / uiPrompt 弹窗助手

server.mjs                # 复用同一后端；新增实施端 /api/field/* 端点
                          #   （field/submissions · field/systems · field/todos · customer-version …）
```

## 3. 通用设计（工作空间外壳）

### 3.1 布局
```
┌──────────────────────────────────────────────────────────────┐
│ 顶栏(深色): 品牌 │ [维度下拉▾] ┊ 平铺(医院/系统)tab │ 待办 经验库 用户 │
├───────────────────────────┬──────────────────────────────────┤
│ 左：提交清单               │ 右：AI 对话提交                    │
│  子切换/筛选 + 分组列表     │  归档上下文chip + 类型切换 + 对话   │
└───────────────────────────┴──────────────────────────────────┘
```

### 3.2 登录门（gate）
- 未登录时**整端遮罩**为登录页；未登录不可进入任何工作空间数据。
- 登录：用户名 + 密码；错误内联提示。提示文案：现场账号由运营端开通并绑定负责医院，账号之间数据相互独立。
- 登录态 `localStorage` 持久化（刷新保留），退出清除。
- 现场账号一律由运营后台开通并绑定负责医院；登录页**不提供**演示账号快捷入口（已去除原型的「演示账号（点击填入）」块）。
- 密码框支持**显示/隐藏切换**（右侧眼睛图标），点击可查看自己录入的明文，便于确认无误。

### 3.3 工作空间隔离（核心约束）
- 登录后只加载**当前账号负责的医院**（`account.sites`）；医院 tab、提交清单、系统聚合、待办、版本，全部限定在这些医院内。
- 不同账号登录 = 不同、互相独立的工作空间。
- 后端所有实施端接口以**当前登录用户的 sites** 为数据边界（拦截器/服务层双重校验，不信任前端传参）。

### 3.4 顶部维度切换（层级区分）
> 维度是"看问题的角度"，与"具体实体"是两个层级，视觉必须区分。

- **维度选择器**：一个**下拉**（`医院视图 ▾ / 系统视图`）—— 半透明描边 + chevron + 弹菜单，明确是"选维度"。
- **实体 tab**：下拉右侧、以竖分隔线隔开的**平铺 tab**（医院们 / 系统们）—— 实心高亮，明确是"选具体项"。
- 两者视觉语言不同（下拉 vs tab），层级一眼可辨。

## 4. 功能需求

### 4.1 医院视图（维度：按医院）
- 顶部**平铺我负责的医院** tab（如 山东省立医院 / 郑州人民医院 …）+ 末尾灰色不可点提示「🔒 医院由运营端分配」。
- 选医院 → 左侧提交清单显示**该医院**的提交记录；右侧归档上下文 = 该医院。
- 提交清单子控件：**按批次 / 按类型** 切换 + **全部子项目** 下拉筛选。
- **不提供**"添加医院/产品"（由运营端账号管理绑定）。

#### 4.1.1 按批次（默认）
- 按「产品 · 周批次」分组，组头显示：产品名、周次(时间范围)、批次状态、条数、节奏提示。
- 批次状态与现场语义：
  | 批次状态 | 现场含义 | 组内附加 |
  |---|---|---|
  | 收集中（本周） | 本周还能提，周日截止进开发会议 | 「周日截止 → 开发会议」 |
  | 待开发会议 | 已进收件箱，等运营决策 | 「已进收件箱」 |
  | 开发中 | steward 开发中 | 回链 steward UC |
  | 可下载 | 已发包，可下载更新现场 | **更新包卡（下载 + 一键改版本）** |
  | 已交付 | 已交付 | — |
- 组内每条记录：类型标签(需求/BUG/咨询)、标题、状态标签(待评审/开发中/本包已含/已答复…)、子系统·医院、时间。

#### 4.1.2 按类型
- 把同一批提交**跨批次**按 **需求 / BUG / 咨询** 重组（回答"我提的这类诉求都到哪步了"）。
- 与按批次**同一数据源**，每条保留其状态与上下文。

### 4.2 系统视图（维度：按系统，忽略医院）
- 顶部**平铺系统** tab：`全部系统` + 各子系统（审方 / 抗网上报 / 药学门诊 / 点评 …，取自我负责医院已上产品的子系统）。
- 选系统 → 左侧**跨我负责的全部医院**、只显示该系统的提交记录；顶部提示条「跨全部医院，只看『审方』系统」。
- 系统视图下**隐藏**「全部子项目」下拉与「按批次/按类型」切换（系统已是顶部 tab）。
- `全部系统` = 各系统分组一起看。

### 4.3 AI 对话提交（右侧 · 现场提交入口）
> 现场只需自然语言描述，AI 完成分类 + 要素补齐 + 归档确认。

- **归档上下文 chip**（工具条最前，版本感知）：
  - 医院视图：`🏥 <医院> · 现场版本：<产品> <ver> · …`（跟随所选医院，只读）。
  - 系统视图：`📦 <产品> · <子系统> · <版本▾>`，版本是**运营维护 tag 版本下拉**（最新在前），选定后**提问基于该版本**。
- **提交类型切换**：`提需求 / 报BUG`（默认）｜`咨询答疑`。
- **对话流程**：
  1. 现场输入自然语言（回车发送）。
  2. AI 判断类型（需求 / BUG / 咨询），必要时追问补齐**现象 / 复现 / 影响**。
  3. AI 给出归档建议：`产品 · 子系统 · 版本 · 客户医院`，请现场确认。
  4. 确认 → 生成工单：
     - 需求 / BUG → `intake_ticket`（状态 `PENDING`），进入运营端工单流。
     - 咨询 → 咨询工单，AI 直接答复；有价值可被运营端沉淀经验库；**不进批次**。
- **新对话**：清空当前会话开新单。
- 归档目标的**版本**取自 §4.6 的版本模型（系统视图=运营 tag 版本；医院视图=该医院现场版本）。

### 4.4 待办（顶栏）
- 顶栏「待办 N」红标，点开 popover，列出现场需跟进事项（随当前医院/维度生成）：
  | 类型 | 事项 | 操作 |
  |---|---|---|
  | 待下载 | 某批次已发包（可下载更新包） | 去下载 → 定位更新包卡 |
  | 待改版本 | 下载后需回写现场版本号（v_old→v_new） | 一键改版本 |
  | 待验证 | 已交付功能待现场验证 | 去验证 |
- 计数 = 待办条数；点操作项 → 执行/定位并反馈。

### 4.5 更新包下载 + 版本回写（闭环）
- 「可下载」批次内展示**更新包卡**：产品 vX.Y 更新包、发包时间、大小、更新说明、`下载更新包`。
- 下载后按钮转「已下载」，并出现**改版本号提示**：`<医院> v_old → v_new`，`一键改版本`。
- `一键改版本` → 调 `POST /api/customers/{id}/version`（该医院该产品版本），回写运营端台账；成功后现场版本更新，相关待办清除。
- （规则）版本回写是否强制、校验规则见《运营端 PRD》§17 待确认。

### 4.6 版本模型（两类版本，务必区分）
| 版本 | 来源 | 用途 | 交互 |
|---|---|---|---|
| **运营维护版本(tag)** | 运营端/steward 发布的产品 tag（= 批次产物 `intake_batch.pkg_version`） | 系统视图归档上下文；"提问基于哪个版本" | 下拉可选，最新在前 |
| **现场版本** | `intake_customer_product.version`（某医院某产品当前版本） | 医院视图归档上下文；下载后回写 | 跟随所选医院，只读展示；`一键改版本` 更新 |

- 子系统 → 产品映射（`SUB_PRODUCT`）决定归档上下文的产品与可选版本集。

### 4.7 免登录提交链接（访客模式）
- 运营端产品管理可生成**免登录提交链接**（token，见《运营端 PRD》§7.4 `/api/submit-link`），带 `site / ver / type / days`。
- 访客凭链接打开**干净提交页**（无导航、无工作空间），仅 AI 对话提交；提交归属链接预置的 site/产品/版本。
- 用于现场临时人员、无账号场景。

### 4.8 经验库入口
- 顶栏「经验库」入口：现场可检索「问题 → 解法」（运营端沉淀），先自查再提单。

## 5. 数据模型（复用 `intake_*`，实施端相关字段）

> 表定义见《运营端 PRD》§12。实施端主要**读**台账/批次/工单、**写**工单与版本回写。

- `intake_account`：`role='field'`；`intake_account_hospital`：账号-负责医院（= 工作空间边界）。
- `intake_customer` / `intake_customer_product`：医院及其**现场版本**（`version`）。
- `intake_product` / `intake_subsystem`：产品与子系统（系统视图/归档上下文取数）。
- `intake_batch`：批次 + `pkg_version`(运营 tag 版本) + `status`(可下载/已交付…) + `release_note`。
- `intake_ticket`：实施端提交写入（`submitter`=当前用户，`status='PENDING'`，`customer_id`/`product_id`/`subsystem_key`/`version`）。
- `intake_submit_link`：免登录提交 token。
- （建议）`intake_download_log`：批次更新包下载记录（`batch_id`/`customer_id`/`account_id`/`time`），支撑"待验证/下载情况"。

## 6. 接口设计（实施端）

> 统一前缀 `/api`；实施端接口均按**当前登录用户的 sites** 收敛数据；返回体 `{code,data,msg}`。

| 方法 | 路径 | 说明 |
|---|---|---|
| POST | `/api/field/login` | 现场账号登录（返回用户 + 负责医院 sites） |
| GET | `/api/me` | 当前用户 + 角色 + sites |
| GET | `/api/logout` | 退出 |
| GET | `/api/field/hospitals` | 我负责的医院（含各医院现场版本） |
| GET | `/api/field/systems` | 我负责医院已上产品的子系统清单（系统视图 tab） |
| GET | `/api/field/submissions` | 提交清单（参数：`dimension=hosp\|sys`、`hospitalId?`、`system?`、`groupBy=batch\|type`） |
| GET | `/api/field/batches?hospitalId=` | 某医院批次（进度/可下载/更新包） |
| GET | `/api/product-versions?product=` | 某产品运营维护 tag 版本列表（系统视图版本下拉） |
| POST | `/api/field/submit` | AI 对话提交 → 建工单（body: 类型/描述/product/subsystem/version/customerId/会话摘要） |
| POST | `/api/field/consult` | 咨询提交（AI 答复，不进批次） |
| POST | `/api/ai/classify` | AI 判类型 + 补要素 + 归档建议（供对话逐步生成） |
| POST | `/api/batches/{id}/download` | 记录更新包下载（返回下载地址 + 版本提示） |
| POST | `/api/customers/{id}/version` | 现场版本回写（body: `productId`/`version`） |
| GET | `/api/field/todos` | 待办（待下载/待改版本/待验证） |
| GET | `/api/kb/search?q=` | 经验库检索 |
| GET | `/api/s/{token}` | 免登录提交页上下文（校验 token → site/product/version） |

## 7. 权限与数据隔离

- **登录门**：未登录不可访问任何实施端接口/页面。
- **数据权限（硬约束）**：`field` 用户所有查询/写入以 `intake_account_hospital` 的负责医院为边界；后端服务层用当前用户 sites 过滤，**忽略前端越权传参**。
- **按钮级**：实施端无决策/发包/账号管理入口；仅提交、下载、版本回写。
- **免登录 token**：校验有效期与绑定 site/product；越权即拒。
- **留痕**：提交、下载、版本回写均记录（谁/何时/哪家医院/哪个产品版本）。

## 8. 非功能需求

| 维度 | 要求 |
|---|---|
| 幂等 | 提交（会话去重/防重复建单）、版本回写（同值幂等）；下载重复不重复计数 |
| 并发 | 多端同账号 → 以最新登录为准；版本回写乐观锁 |
| 离线/弱网 | 图标本地字体；提交失败可重试，草稿本地暂存 |
| AI 兜底 | 分类/建议超时降级为"人工选择产品·子系统·类型"，不阻断提交 |
| 安全 | Session/JWT + 拦截器；提交链接 token 不可枚举、可吊销 |
| 性能 | 提交清单分页/按医院懒加载；系统视图聚合走服务端 |

## 11. 待人工确认（NEEDS-HUMAN）
1. 现场账号登录用 Session 还是 JWT；是否复用运营端同一鉴权/用户中心。
2. AI 分类/归档由后端统一调模型，还是前端直连（Key 安全见运营端 §11 模型配置）。
3. 版本回写是否强制（下载后必须改）与校验规则。
4. 免登录提交链接的权限边界（可提交类型、是否限单医院、有效期默认值）。
5. 系统视图的"系统"来源：取我负责医院**已上产品**的子系统，还是全部产品子系统。
6. 咨询工单是否允许现场对 AI 答复发起追问/转需求。
7. 提交清单默认加载范围（我负责全部医院 vs 当前医院），大数据量分页策略。

# 约定 · 产品部署 / 更新清单（`docs/deploy.json`）

> **给产品团队（各子系统仓 dev）照着落地的数据格式约定。**
> intake 平台（进件/实施端）不再手工登记版本部署清单；它改为**从产品代码仓按 git tag 读取** `docs/deploy.json`，跨子系统聚合、跨版本累积，自动生成实施端「更新计划」+ 合并 SQL 下载。
>
> 一句话：**清单 / 升级 SQL 是产品代码的一部分，跟着版本 tag 走**——你在自己的子系统仓里维护，打 tag 发版时它就自动被 intake 读到，不用再去 intake 后台登记。

---

## 1. 放哪里

每个**子系统仓**根目录下：`docs/deploy.json`。

- 一个「产品」在 intake 里可以挂 N 个子系统仓（`proj.subsystems[].repoPath`）。**每个子系统各自维护自己的 `docs/deploy.json`**，intake 读取时把同产品下所有子系统的清单**聚合**在一起。
- 该文件**必须提交进 git**（intake 用 `git show <tag>:docs/deploy.json` 读，只读工作树的没打 tag 的版本读不到）。
- 没有这个文件的子系统 / tag —— intake **静默跳过**，不报错（该子系统该版本无部署清单而已）。

## 2. 什么时候写

在**打版本 tag 之前**，把「这个版本相对上一版，实施要做的事 + 要跑的 SQL」写进 `docs/deploy.json`，随代码一起提交，然后打 tag。

- intake 按 **git tag** 读：`git show v2.8:docs/deploy.json`。所以 **tag 那一刻文件里是什么，实施端看到的就是什么**。
- 每个 tag 的 `deploy.json` 只写**该版本的 delta**（本次升级新增的实施动作 + SQL），不用累积——跨版本累积由 intake 负责（实施端从现场版本 X 升到目标版本 Y，intake 自动取 `(X, Y]` 区间内每个 tag 的清单并起来）。

## 3. Schema（JSON，本平台零依赖 · `JSON.parse` 直读 · 禁止 YAML）

```jsonc
{
  // 本版本的实施任务（实施人在现场逐条勾「已完成」）
  "tasks": [
    { "id": "env",     "title": "环境准备",   "desc": "确认服务器/数据库/网络就绪" },
    { "id": "backup",  "title": "备份数据库", "desc": "升级前全量备份，保留回滚点" }
  ],
  // 本版本要执行的 SQL 脚本（实施人手动跑，intake 只列出/合并下载，不碰库）
  "sql": [
    { "id": "s1", "file": "sql/2.8_upgrade.sql", "desc": "本版本升级脚本" },
    // 也兼容内联正文（file 优先；file 读不到才用 content）：
    { "id": "s2", "content": "ALTER TABLE ...;", "desc": "小改动内联" }
  ]
}
```

### 字段说明

| 字段 | 位置 | 必填 | 说明 |
|---|---|---|---|
| `tasks[].id` | 任务 | 建议填 | 本子系统内**稳定唯一**的短 id（如 `env`/`backup`）。intake 会把它拼成全局 id `<子系统>:<id>` 避免跨子系统撞号。缺省会自动补，但**完成态是按 id 记的——id 变了 = 换了一条新任务，之前的勾选会丢**，所以尽量给稳定 id。 |
| `tasks[].title` | 任务 | **是** | 任务标题（空则该条被丢弃）。 |
| `tasks[].desc` | 任务 | 否 | 说明/操作要点。 |
| `sql[].id` | SQL | 建议填 | 同 `tasks[].id`，本子系统内稳定唯一。 |
| `sql[].file` | SQL | file / content 二选一 | **仓内相对路径**（如 `sql/2.8_upgrade.sql`）。intake 用 `git show <tag>:<file>` 读正文——所以脚本文件也要提交进 git 且在该 tag 下存在。**推荐用 file**（脚本单独成文件，好维护/复用）。 |
| `sql[].content` | SQL | file / content 二选一 | 内联 SQL 正文。**只有 `file` 缺失/读不到时才用**（file 优先）。适合三两行的小改动。 |
| `sql[].desc` | SQL | 否 | 该脚本用途说明。 |

### 约束 / 上限（intake 侧规范化）

- `tasks[].title` ≤ 120 字、`desc` ≤ 2000 字；`sql[].desc` ≤ 200 字；内联 `content` ≤ 20000 字（超长截断）。
- 同一子系统内 `id` 去重（重复自动改名）；tasks / sql 各上限 200 条。
- **JSON 必须合法**——非法 JSON 的 `deploy.json` 会被 intake 静默跳过（该子系统该版本视为无清单）。发版前自己 `node -e "JSON.parse(require('fs').readFileSync('docs/deploy.json','utf8'))"` 校验一下。

## 4. intake 怎么读（读取规则）

1. **按 tag 读**：实施端在某院把某产品从「现场版本 X」升到「目标版本 Y」→ intake 取版本区间 `(X, Y]`（不含 X、含 Y；版本序 = 各子系统仓 git tag 并集，版本号排序）。
2. **跨子系统聚合**：区间内**每个 tag**，对该产品**每个子系统仓**执行 `git show <tag>:docs/deploy.json`，`JSON.parse` 后把 `tasks` / `sql` 合并（各项带 `subsystem` 来源；任务全局 id = `<子系统>:<原id>`）。读不到 / JSON 非法的子系统跳过。
3. **跨版本累积**：区间内所有 tag 的 tasks 累积成一份「实施任务清单」（按版本升序、逐条可勾）；所有 sql 累积成**一个「执行升级 SQL」条目**（一个完成态）。
4. **合并 SQL 下载**：把区间内所有 sql 按版本升序拼成**一个 `.sql` 文件**——每段前有分隔注释 `-- ==== <产品> <版本> <子系统> <脚本> ====`。`file` 的用 `git show <tag>:<file>` 读正文；`file` 缺则用 `content`。
5. **完成度**：实施人逐条勾任务、勾「SQL 已执行」，完成态存在 intake（`customer.updateProgress`），**不回写产品仓**。任务完成态按 `(医院 × 产品 × 版本 × 任务全局id)` 记——所以 id 稳定很重要（见上）。

> **优雅降级**：某 tag / 某子系统没有 `docs/deploy.json`，或文件缺失 / JSON 非法 → 静默跳过，不报错、不 500。整个区间都没有清单 → 实施端友好提示「该版本区间未在代码中声明部署清单 `docs/deploy.json`」。

## 5. 给产品 dev 团队的落地示例

在你的子系统仓（如合理用药 `kwsb`）里：

```
kwsb/
  docs/
    deploy.json        ← 本约定文件
  sql/
    2.8_upgrade.sql    ← 本版本升级脚本（被 deploy.json 引用）
```

`docs/deploy.json`：

```json
{
  "tasks": [
    { "id": "env",    "title": "环境检查",   "desc": "确认目标库版本 ≥ 5.7、磁盘空间充足" },
    { "id": "backup", "title": "全量备份",   "desc": "升级前备份，保留回滚点" },
    { "id": "restart","title": "重启服务",   "desc": "SQL 执行完毕后重启应用" }
  ],
  "sql": [
    { "id": "s1", "file": "sql/2.8_upgrade.sql", "desc": "2.8 版本结构升级（新增字段/索引）" }
  ]
}
```

发版流程：改代码 → 写/更 `docs/deploy.json` + `sql/*.sql` → `git add . && git commit` → `git tag v2.8 && git push --tags`。
intake 下次刷新仓（`refreshRepos`）后，实施端升到 2.8 就能看到这份清单并逐条落地。

## A. 现有真实资产盘点（不臆造，逐条来自 db.mjs / server.mjs）

### A.1 MySQL 表（5 张，`db.mjs init()`）
| 表 | 关键列 | 说明 |
|---|---|---|
| `projects` | id, name, repo_path, specs_path, **subsystems JSON**, created_at | 产品；subsystems=[{name,key,desc,repoUrl,repoPath}] |
| `accounts` | id, username, role, name, salt, hash, must_change, **projects JSON, sites JSON**, **enabled TINYINT**, created_at | 账号；role∈{admin,pm,dev,impl}（NH-4 定版，`dev`≠admin）；sites=负责现场；enabled=启用/停用 |
| `sessions` | token, user_id, exp | 登录会话 |
| `intakes` | project_id, id, type, version, site, subsystem, module, title, priority, severity, env, freq, **status, lifecycle**, assignee, reporter, submitted_at, **data JSON**, created_at, updated_at | 工单（列做查询，嵌套放 data JSON） |
| `kb_entries` | id, project_id, q, a, subsystem, module, tags JSON, source, from_ref, created_at | 经验库 |

### A.2 文件存储（2 个，data/ 下，不入库）
- `data/customers.json`：`{customers:[{ id, name, products:[{project,version}], updatedAt }]}` —— **最简**（无等级/地区/负责人/状态）。
- `data/model-api.json`：`{models:[{provider,model,baseUrl,primary,apiKey,mask}]}`。
- `data/git-config.json`：`{baseUrl, token}`。
- `data/intake-store/<projId>/<id>.md/.json`：工单可读镜像（给开发 git pull）。

### A.3 工单状态机（真实 `LIFECYCLE` + `TRANSITIONS`）
```
待处理 → 分析中 / 已回复 / 已立项
分析中 → 已回复 / 已立项
已回复 → 已重开
已立项 → 开发中
开发中 → 已出包
已出包 → 待验证
待验证 → 已重开（或 已关闭）
已重开 → 开发中 / 分析中
（任意非关闭态 → 已关闭：强制关闭）
```
`intake.data` 内含：desc/errorInfo/steps/expectResult（BUG）、bg/reqDesc/accept/relate（需求）、opinion(AI意见)、analysis(初判)、resolution(处理结果:{fixedVersion,commit,pr,note})、chat[]、history[]（流转留痕）、media[]。

### A.4 现有 API 端点（43 个，按模块归类）
- **工单**：intake-list / intake-detail / intake-submit / intake-chat / intake-reply / **intake-transition**(流转+留痕) / intake-analyze(AI初判) / intake-aggregate / intake-export / intake-media / notifications
- **答疑**：consult
- **产品**：projects / project-save / project-delete / project-git / versions / spec-modules / spec-search / git-inspect / git-refresh / git-config / git-config-save
- **客户**：customers / customer-save / customer-delete
- **经验库**：kb-list / kb-save / kb-delete / kb-from-consult
- **账号**：accounts / account-save / account-delete / login / logout / me / change-password / submit-link
- **模型**：model-config / model-config-save / model-test
- **工作台**：overview
- 其它：health / version

## C. 工单状态机对齐（现有 ↔ 原型标签）

| 原型标签 | 映射现有 lifecycle | 处理 |
|---|---|---|
| 待评审 | 待处理 / 分析中 | 复用（UI 可显示为"待评审"） |
| 已落实·排期 | **已立项** | 复用（"落实"=已立项 + 归批次） |
| 开发中 | 开发中 | 复用 |
| 已交付 | 已出包 → 待验证 → 已关闭 | 复用（发包=已出包） |
| 已答复 | 已回复 | 复用 |
| **暂缓** | — | 🔴 新增态 |
| **已驳回** | — | 🔴 新增态（或用"已关闭 + 驳回原因"） |

> 建议：`TRANSITIONS` 增加 `待处理/分析中 → 暂缓/已驳回`，`暂缓 → 分析中/已立项`（可复议）。标签层「待处理→待评审、已立项→已落实」只做**展示别名**，底层枚举不必大改，降低迁移风险。

## D. 需新增/改的接口清单

### D.1 批次与发包（新增）
| 端点 | 用途 |
|---|---|
| `GET /api/batches?product=&status=` | 批次列表（按产品/状态筛） |
| `GET /api/batch-detail?id=` | 批次详情（含覆盖工单、包信息） |
| `POST /api/batch-tickets` | 工单归入/移出批次（落实时调用） |
| `POST /api/batch-lock` | 批次周截止封板（进开发会议） |

### D.2 steward 对接（新增，见 §E 契约）
| 端点 | 方向 | 用途 |
|---|---|---|
| `GET /api/steward/checklist?batch=` | steward 拉 | 某批次落实功能清单 |
| `POST /api/steward/progress` | steward 回写 | 工单/UC 开发进度 |
| `POST /api/steward/release` | steward 发包 | 更新包 + 更新说明 + 版本 + 覆盖工单 |

### D.3 客户/版本回写（改/新增）
| 端点 | 用途 |
|---|---|
| `POST /api/customer-save`（改） | 增字段 level/region/impl/status |
| `POST /api/customer-version` | 某医院某产品版本回写 + 留痕 |
| `GET /api/batch-download?batch=&customer=`（实施端） | 下载包 + 记下载数 |

### D.4 工单处理（复用+微调）
- 复用 `intake-transition`：落实=`→已立项`(带 batchId)、答复=`→已回复`(带 reply)、暂缓/驳回=新增 to。
- 复用 `intake-analyze`（AI 初判）。

## E. steward 对接契约（P0 必须与 steward 侧敲定的核心）

> 字段结构即接口契约。**这是唯一强外部依赖，建议本 P0 里和 steward 团队面对面定死。**

**① 拉落实清单**（steward 定时拉，或运营封板后推）
```jsonc
GET /api/steward/checklist?batch=B-3601   →
{ "batch":"B-3601", "product":"psp", "week":"第36周",
  "items":[ { "ticketId":"T-1028", "type":"需求", "title":"…",
    "subsystem":"药师工作站主站", "desc":"…", "accept":"…", "ai":{...} } ] }
```

**② 回写进度**（steward → 运营）
```jsonc
POST /api/steward/progress
{ "items":[ { "ticketId":"T-1028", "stewardUC":"UC-8842",
  "state":"开发中|已完成", "at":"2026-07-15 14:30" } ] }
```

**③ 发包**（steward → 运营）
```jsonc
POST /api/steward/release
{ "batch":"B-3601", "product":"psp", "pkgVersion":"v2.1",
  "releaseNote":"…", "releaseTime":"…", "ticketIds":["T-1028","T-1025"],
  "artifactUrl":"…或上传" }
```

**待定**：拉 vs 推、鉴权方式（服务账号 token，现有 accounts 已有 `steward 服务号`）、发包产物是 URL 还是上传、失败重试。

## F. 5 个产品决策（NEEDS-HUMAN + 推荐默认）

| # | 决策 | 推荐默认 |
|---|---|---|
| 1 | 认领医院/产品是否需运营审批 | **实施自助即生效**（认领来自后台已有台账，越权风险低）；越权只在数据权限层控 |
| 2 | 发包对接 steward：自动建项 vs 导出包人工导入 | **接口自动**（§E 契约）；过渡期先支持"导出清单人工导入"兜底 |
| 3 | 批次编号 + 周截止 | 编号 `B-{周}{产品序}`（如 B-3601）；**周日 24:00 封板** |
| 4 | 复议机制 | 允许**暂缓→复议**回到 分析中/已立项；驳回不复议（可重开） |
| 5 | 版本回写是否强制 | **非强制但强提醒**（下载后弹提示 + 工作台挂"待改版本"待办，不阻断） |

## G. 结论与 P1 可立即开工范围

**运营端可以开工。** 现有系统已把状态机、工单/账号/客户/经验/产品/模型/工作台的骨架做好，P0 锁定后即可并行：

- **P1（内部闭环，不依赖 steward，先干）**
  1. 工单管理：状态机加"暂缓/驳回"，处理决策抽屉接 `intake-transition`（落实带 batchId）。
  2. 客户/医院：`customers` 扩字段（level/region/impl/status），建议迁 MySQL。
  3. 账号：补 status；hospitals 用现有 sites。
  4. 前端：用 `theme.css/shell.js` 那套把 8 页对齐（已成型）。
- **P2（依赖 §E 契约）**：批次表 + 批次/发包接口 + steward 三接口 + 版本回写。
- **P3**：实施端（提交/下载/改版本）打通。

**开工前置（本 P0 需人拍板）**：§E steward 契约 + §F 5 决策 + 「客户是否迁 MySQL」。这三样定了，P1 立即可排 `/build`。

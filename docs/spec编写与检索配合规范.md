# spec 编写与检索配合规范

> **给谁看**：写 spec、维护「功能模块地图」的人（产品 / 开发 / 实施）。
> **目标**：让现场答疑 AI 能**答得准、少误判「没覆盖」、绝不臆造**。
> **一句话**：检索引擎（平台侧）已基本成型，接下来 80% 的答疑质量提升，靠**内容侧**——spec 和功能模块地图怎么写。
> 关联：`docs/specs/00-功能模块地图.json`（产品仓）、平台「AI 检索诊断」页、`docs/lessons.md`。

---

## 0. 背景：AI 答疑现在怎么工作（先懂这个再写 spec）

现场同事在答疑框问一句话，平台按**三层**检索、再让 AI 作答：

| 层 | 机制 | 靠什么命中 | spec 要喂什么 |
|---|---|---|---|
| ① **功能模块地图**（questionRoutes） | 人工整理的「问题→spec 章节 + 经确认事实」路由 | 别名 / 关键词 | `aliases`（现场原话）+ `answerFacts`（正确事实）+ `primaryRefs` |
| ② **specSearch 底座** | spec 正文分段 + 中文二字词重叠 + IDF 打分 | **spec 正文用了哪些词** | 正文用词要贴现场说法；摘要放前面 |
| ③ **AI 覆盖判定** | AI 判「检索到的内容是不是真在讲用户问的那个功能」 | spec 颗粒度、结构清不清 | 一功能一 spec、标题清晰、契约结构化 |

**关键认知**：
- 命中 ① 的问题答得最准（有 `answerFacts` 兜底）；没命中 ① 才落到 ② specSearch。
- ② 靠**词汇重叠**——spec 用的词和用户问的词对不上，就搜不到。
- ③ 会「宁可不答也不臆造」——spec 没写清的具体表名/字段/接口，AI 不会编，只会说「问开发」。
- 都没相关内容 → AI 一句「说明书没覆盖，建议转工单」，**不硬编**。

> 所以 spec 写得好不好，直接决定：该答的能不能答、答得准不准、会不会误「没覆盖」。

## 1. 🔴 头号铁律：spec 必须和「真实上线的系统」一一对应

**AI 只信 spec。spec 写错，AI 就答错——而且答得理直气壮。**

现场答疑最常见、最伤的错，就是 **spec 里的功能/按钮/入口和真实系统对不上**：
- spec 写「点【导出】按钮」，但系统里那个按钮叫【下载】或根本没有 → AI 让现场「点导出」，现场找不到，白折腾。
- spec 写的字段/接口/配置是**设计稿或旧版**，和实际部署不一致 → AI 给的排查方向全错。

**要求**：
1. **按钮 / 菜单 / 入口 / 页面名**：spec 里写的名称、位置，必须和**真实上线系统**一致（以现场实际能看到的为准，不是设计稿、不是开发的内部叫法）。
2. **字段 / 表 / 接口 / 配置 key**：写进 spec 的具体技术名，必须是**真实存在**的（开发确认过），否则宁可不写、标「待确认」，也别写错——AI 会照着 spec 的名字答，写错=误导现场。
3. **随版本更新**：功能改了、按钮改名了、入口挪了，**spec 同步改**。spec 按医院版本（git tag）读，旧 tag 的 spec 要反映那个版本的真实样子。
4. **标注不确定**：拿不准的地方明确写「（待开发确认）」或「（此为设计，实际以系统为准）」——这样 AI 会转述这个不确定，而不是当成事实。

> 自查：**拿一份 spec，对着真实系统点一遍**——写到的按钮/入口/字段，系统里都有、名字都对得上吗？对不上的，先改 spec。
> （用户本次反馈：「功能按钮这部分跟系统没对应上」——就是这条。这类必须优先修，比补新内容更重要，因为它是「答错」不是「没答」。）

## 2. 功能模块地图 `questionRoutes`（最高杠杆，优先做这个）

这是 pwrs 答疑答得准的根本原因。它是一份**从真实现场问题长出来的 FAQ 索引**。

### 2.1 一条 questionRoute 长这样

```json
{
  "id": "QR-ORDER-INSTRUCTION",
  "title": "医嘱干预中查看药品说明书／说明书地址如何配置",
  "aliases": [
    "医嘱干预查看说明书", "说明书按钮不显示", "说明书打不开",
    "合理用药说明书地址如何配置", "order_instruction"
  ],
  "keywords": ["医嘱干预", "说明书", "地址", "配置", "order_instruction"],
  "answerFacts": [
    "配置项是 usercenter 系统设置中的 order_instruction，不在 PWRS 本地维护。",
    "open 控制入口是否显示，value 保存带占位符的 URL，url_placeholder 定义可替换变量。",
    "Web 通过 GET /api/config/all 加载并缓存；修改后应重新登录或重载配置验证。"
  ],
  "mustNotConfuse": ["gy_engine", "audit_drug_instruction", "臆造 /drug/manual 等不存在的配置"],
  "primaryRefs": [{ "specId": "PWRS-SYS-06", "section": "7. order_instruction 的完整配置答案", "path": "docs/specs/PWRS-SYS-06-...md" }]
}
```

### 2.2 每个字段怎么写（重点）

- **`aliases`——写「现场同事的原话」，不是正式标题。** 这是命中率的关键。
  用户不会说「医嘱药品说明书地址配置」，会说「说明书打不开」「说明书按钮咋没了」「点了没反应」。**把现场真实说法都列进去**，越口语越好。一条路由挂 5~10 个别名不嫌多。
- **`answerFacts`——写「经确认的正确事实」。这是金子。**
  配置叫什么、在哪个系统、什么字段控什么、什么机制……凡是**开发确认过、你们踩坑后搞明白的结论**，都沉淀成一条 answerFact。AI 命中后**直接照它答，不猜、不错**。
  > 每解决一个疑难问题，就想一句：这个结论该不该进某条 route 的 answerFacts？
- **`mustNotConfuse`——写「易混/易错项」。** 专治 AI 张冠李戴（「别和 gy_engine 混」「别臆造 /drug/manual」）。
- **`keywords`——关键词**（含英文标识符如 `order_instruction`），补充别名。
- **`primaryRefs`——指到具体 spec 章节**，命中后 AI 会去读。

### 2.3 什么时候加 / 改 route
- 现场高频问题 → 建一条。
- AI 答错 / 误「没覆盖」 → 加别名 或 补 answerFacts 或 修 primaryRefs（**用「AI 检索诊断」页定位，见 §5**）。
- 一个 route 覆盖的是「一类问题」，不是一句话——把同义问法都收进 `aliases`。

## 3. spec 正文写作清单（喂好 specSearch 底座 + AI 判定）

### 3.1 开头一段「大白话摘要」
每份 spec 开头写一段：**这个功能是干什么的、现场会怎么问它、常见啥问题**。
> 检索只读每份 spec 的**前 800 字**做索引——把最该被搜到的精华放最前面，别埋在文档中段。

### 3.2 正文同时用「用户的话」和「技术术语」
specSearch 靠**词汇重叠**命中。spec 只写术语、用户说口头话，就搜不上。
- ✅ 好：患者列表 spec 里写「现场常问：**按床位号 / 住院号查不到患者**、串院区、同号患者混淆」。
- ❌ 差：只写「支持多条件筛选与检索」——用户说「床位号查不到」时命中不了。

**做法**：功能描述里，顺手把现场的口头说法、常见问句写进去（等于把别名也埋进正文）。

### 3.3 「数据契约 / 接口契约 / 配置项」结构化列出
AI 有红线「不臆造具体表名/字段/接口/配置名」。**spec 明确列了，AI 才敢答**「看哪张表 / 哪个接口」；没列，只能推给开发。
- 用固定小节写清：**表名 + 字段**、**接口路径 + 方法**、**配置 key + 含义**。
- 这些也进功能模块地图的 `indexes`（configs/tables/apis 反查表）——保持完整，能让「问某配置在哪」直接命中对应 spec。

### 3.4 每个模块写「症状 → 定位 → 解法」FAQ 段
现场答疑八成是**排查类**（「XX 不生效 / 查不到 / 为什么」）。spec 里有这段，AI 的排查步骤就**有据、可照做**，不靠常识编。
- 格式：`症状（现场现象）→ 先查什么（哪个页/哪个值）→ 怎么判断 → 解法 / 转谁`。

### 3.5 一功能一 spec、颗粒度适中
- 一份 spec 聚焦一个功能/模块，标题清晰。一份塞太多功能，相关度会被稀释、AI 也难判「是不是在讲这件事」。
- pwrs 拆 `PWRS-CARE-01a/01b/01c`（患者列表 / 病情概要 / 体温单）就是好例子。

### 3.6 版本打 tag
spec 按医院版本（git tag）读。发版就打 tag，让版本感知检索准确；旧版本的 spec 反映旧版本真实样子。

## 4. 闭环：用「AI 检索诊断」驱动 spec / 地图补全（最省力的做法）

**别埋头把 spec 一次写完美——用诊断页「哪里答错补哪里」，投入产出最高。**

运营后台 → AI 引擎 → **AI 检索诊断**：

1. **对话诊断**：逐轮看每条真实答疑，AI **当时到底检索到了什么**（spec 片段 / 经验库 / 源码 + 打分）。
2. **标记**：对每条检索标 `对 / 跑题 / 缺失 / 该命中没命中` + 备注 → 攒成**「问题清单」**。
3. **回放**：拿任意问题重跑检索，看会取到什么、打分多少（调不准时看 `retrieval.routing.specTop` 等）。

**问题清单直接告诉你怎么补**：
| 诊断结论 | 根因 | 怎么补 |
|---|---|---|
| 该命中的 spec 没进 top / 分很低 | spec 用词和问题对不上 | 给 route 加**别名**、spec 正文补**用户的话** |
| 检索到的跑题（同域别的功能） | 缺这个功能的 route/spec | 建 **route** 或 补 **spec** |
| 答得对但没点到关键事实 | 缺 answerFacts | 给 route 补 **answerFacts** |
| AI 说的按钮/字段和系统对不上 | **spec 与真实系统不一致**（§1） | **改 spec**（最高优先） |
| 真没这功能 | spec 没覆盖 | 补 spec，或接受「没覆盖」（诚实） |

> 这样 **spec 质量和检索质量一起滚动提升**，而不是一次写死。

## 5. ✅ 快速自检清单（写 / 改 spec 前后过一遍）

**准确性（铁律，最优先）**
- [ ] spec 写到的**按钮 / 入口 / 菜单 / 页面名**，和真实系统一致（对着系统点一遍）。
- [ ] 写进 spec 的**具体表名 / 字段 / 接口 / 配置 key** 都真实存在（开发确认过），拿不准的标「待确认」。
- [ ] 功能改了、按钮改名了，spec 同步改。

**可检索性**
- [ ] 每份 spec 开头有**大白话摘要**（功能是啥 + 现场怎么问 + 常见问题），放前 800 字内。
- [ ] 正文用了**现场口头说法**（不只术语），把常见问句写进去。
- [ ] **数据 / 接口 / 配置契约**结构化列出（表/字段/接口/配置 key）。
- [ ] 有「**症状→定位→解法**」FAQ 段（排查类）。
- [ ] 一功能一 spec、标题清晰。

**功能模块地图**
- [ ] 高频问题有对应 `questionRoute`。
- [ ] `aliases` 收了现场原话（口语、别名、易错说法）。
- [ ] `answerFacts` 有经确认的正确事实；`mustNotConfuse` 标了易混项。
- [ ] `primaryRefs` 指到真实存在的 spec 章节。
- [ ] `indexes`（configs/tables/apis）反查表完整。

## 6. 反面例子（本轮真实踩的坑，照着避）

| 问题 | 现象 | 根因 | 正确做法 |
|---|---|---|---|
| 床位号查不到患者 | 一度误「没覆盖」 | spec 只写「筛选/查询」，没写「床位号」 | 给 route 加别名「按床位号查不到患者」/ spec 补现场说法 |
| 系统激活失败 | 一度误「没覆盖」 | 路由错配到「收费失败」，好 spec 被盖（平台侧已修底座） | 给激活加一条 route，别名收「激活失败/激活不了/激活包传不上」 |
| 检验异常值箭头 | 答「没覆盖」 | spec 真没写这功能的显示规则 | 补一份 spec，或接受「没覆盖」（这是诚实，不是 bug） |
| 功能按钮对不上系统 | AI 让点某按钮，现场找不到 | **spec 与真实系统不一致** | 改 spec，以真实系统为准（§1，最高优先） |

## 7. 分工

- **平台（本项目）**：检索引擎——路由 / 打分 / 覆盖判定 / 诊断工具 / 答疑提示词。已基本成型。
- **内容（产品 / 开发 / 实施）**：`00-功能模块地图.json`（questionRoutes + answerFacts）+ spec 正文（用词 + 契约结构化 + 与真实系统一致）。
- **闭环**：用「AI 检索诊断」页标记 → 按问题清单补内容 → 再验。

> 检索引擎够用了。**答疑质量的天花板，现在在内容上——尤其「地图 answerFacts/aliases」+「spec 与真实系统一致」这两件事。**

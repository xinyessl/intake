# 收件 `intake` —— 立项沟通记录（从 steward 会话迁移过来）

> 本文件是"收件 intake"从 steward 会话里孵化出来的**决策与讨论记录**，供在 intake 目录新开的 CLI 会话接上下文。
> 权威设计见同目录 `架构设计.md`；本文件是"我们怎么一步步定成这样"的来龙去脉。

## 一句话背景
在 steward（多项目研发编排中枢）里讨论时，决定**把"需求 / BUG 提交入口"单独拆成一个干净服务**，取名**收件 / `intake`**，给**产品经理 / 现场实施**用，产出**结构化、可被 AI 直接分析**的进件，喂回各项目的开发流程。

## 讨论演进（时间顺序 + 结论）

1. **起点**：想把"需求和 BUG 提交"做进来。用户方是**产品经理和实施工程师**（不是开发）。参考过一版简单 H5 原型 `需求与BUG提交入口.html`。目标：提交更清晰明确（BUG 必须指明问题描述/复现），AI 能直接理解分析。

2. **云端只做进件、不做开发**（用户明确）：
   - 云端这套**不做开发、不生成任务**，只与实施/产品**沟通需求**、对报错给**处理意见**，把内容**梳理进 docs**。
   - 真正的分析/开发由**本地开发的 steward** 跑 `/intake` 完成。云端只是"接收 + 沟通 + 归档"的助手。

3. **模型访问用 API Key 配置**（非交互登录）：做一个模型 API 配置页；Key 只存服务本机、不入库、掩码回传。

4. **进件要结构化 + 定位到人**：
   - 单独一个文件夹专门存需求/BUG，**必须结构化且符合需求/BUG 描述的整体要求**。
   - **定位到人**：提出人 + 联系方式（后期不清楚可回访）。

5. **交互形态几次迭代**（重要，最终形态别再退回）：
   - 先做了"表单 + 右侧对话"→ 用户嫌样式糙、要求参照《高保真原型设计规范》（医疗蓝 #1A6DBE 等 token）。
   - 一度改成"**纯聊天窗口**"（全在对话里完成）。
   - 最终用户敲定：**先选"需求 / BUG" → 填对应表单 → 提交后 AI 给沟通建议**（不是一上来纯聊）。→ 这是当前原型 `prototype/submit.html` 的形态。
   - **不要用 emoji，一律用 icon**（本地 Tabler，`prototype/vendor/tabler/`）。

6. **架构大转向：拆成独立干净服务**（本项目由此诞生）：
   - 云端进件**不做进 steward**：steward 控制台能起 `claude`、开终端，**绝不能暴露公网**；进件是半公开面，权限面完全不同，**物理隔离**。
   - **两系统唯一契约 = 各项目 git 里的 `docs/`**，不互相调 API（"文件即接口"）。

7. **specs 与 intake 的落点（关键决策，已拍板）**：
   - **版本 = git tag**：产品发一个版本就打一个 tag，`docs/specs/` 随 tag 原子快照，取某版本 spec = `git show v1.3.0:docs/specs/x.md`，**不另建 spec 版本库**。
   - **specs 留在各项目代码仓库**（搬出去就拆掉"版本=tag"，也丢掉"checkout 一个 tag、spec+代码一起就位"）。
   - **intake（提交进来的需求/BUG）独立成一个 git 仓**（intake-store）：进件服务写自己这个库，**对代码仓库只读**。
   - 结果：进件服务**永不写代码仓库** → "公网表单要不要 push 到 main / 开 PR"的纠结消失；真正 spec/代码改动仍由开发在代码仓走 `/build` + 人审。

8. **版本感知 + 定位到现场**：
   - 进件新增字段 **`version`（产品版本=tag）+ `site`（现场/客户）**；BUG 的 `version` 必填。
   - **版本别靠人填**：产品内嵌"反馈"入口打开 `…/submit?project=&site=&ver=&type=`，`ver` 由产品自己的构建版本注入，提交页**预填并锁定**。
   - 开发侧 `/intake` 按 `spec@version` 分析：①该版本本就这样→非bug ②违反该版本 spec→是bug，再 diff `spec@version` vs `spec@main` 判断新版是否已修/要否 backport ③全新诉求→进下一版 spec。多现场同现象→归并看"通病 vs 某版本回归"。

9. **命名**：候选 礼宾/concierge、门房/doorman、纳言/nayan、收件/intake → 用户选 **收件 / `intake`**。

## 安全红线（务必延续）
- **绝不把任何密钥/私密配置提交进 git**：模型 API Key 存服务本机（原型里是 `~/.steward/model-api.json`，本项目应改成 intake 服务自己的本地配置文件），**不入库、GET 掩码回传**。
- 进件对话会**本地留存 + 发给模型 API**，提示提交人**不要输入敏感信息**。
- 公网面**必须认证**（现场账号 / 一次性提交链接），不裸奔。
- 进件服务对各项目代码仓库**只读**（读 tag + `spec@tag`），凭证只对 intake-store 有写权。

## 现在手上有什么（原型种子，在 `prototype/`）
- `submit.html`：选类型→填表→AI 沟通（最终形态，医疗蓝 + Tabler icon）。
- `model-config.html`：模型 API 配置页（已对齐医疗蓝）。
- `server.mjs.reference`：**steward 的完整 server.mjs 快照**，进件/模型相关的后端逻辑都在里面，按 `prototype/说明.md` 提取。
- `vendor/tabler/`：本地图标字体（国内不依赖 CDN）。

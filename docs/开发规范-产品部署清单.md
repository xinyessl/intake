# 开发规范 · 产品部署清单与升级 SQL

> **面向对象**：各产品（子系统仓）的开发同学 —— 含 AI 辅助/模型生成。
> **一句话目的**：把「一次部署 / 升级，实施在现场要做的事 + 要跑的 SQL」以**固定格式写进产品自己的代码仓**。收件平台（intake）**只读**读取，按每家医院的现场版本自动算出「首次部署 / 跨版本更新」清单，交给现场实施逐条执行、逐条勾选。
> **核心原则**：清单与 SQL 是**产品交付的一部分**，跟着代码走、随版本维护；intake 不手工维护、不臆造，只读。

---

## 1. 你要产出两类文件（在每个子系统仓里）

```
<子系统仓>/
  docs/deploy/                 # ① 部署清单目录：一个版本一个文件
    2.7.0.json
    2.7.1.json
    2.8.0.json
  sql/                         # ② 升级 SQL 脚本：被上面的清单引用
    2.7.1_add_col.sql
    2.8.0_index.sql
```

- **`docs/deploy/<版本>.json`** —— 该 **版本** 的部署/升级清单（实施任务 + 要跑的 SQL）。
  - **文件名去掉 `.json` = 版本号，必须与该版本的 git tag 完全一致**（如 tag `2.8.0` → 文件 `docs/deploy/2.8.0.json`）。
  - **一个版本一个文件；发新版本 = 新增一个文件，不要改旧文件**。
  - 每个文件**只写"本版本新增的 delta"**（本版新增的实施步骤/SQL），**不要**把历史步骤重复写进新文件。
- **`sql/*.sql`** —— 真实 SQL 脚本，被 `docs/deploy/<版本>.json` 里的 `sql[].file` 引用。

---

## 2. `docs/deploy/<版本>.json` 格式

```jsonc
{
  "tasks": [                                  // 本版本：实施要做的事（逐条，现场勾选）
    { "id": "stop",   "title": "停应用服务",   "desc": "通知现场用户后停止本系统服务" },
    { "id": "deploy", "title": "部署更新包",   "desc": "覆盖安装本版本应用与依赖" }
  ],
  "sql": [                                     // 本版本：要执行的数据库脚本（可空）
    { "id": "s1", "file": "sql/2.8.0_index.sql", "desc": "为报表查询加索引" }
  ]
}
```

| 字段 | 必填 | 类型 / 约束 | 说明 |
|---|---|---|---|
| `tasks` | 否 | 数组（无则 `[]`） | 本版本实施任务 |
| `tasks[].id` | 是 | 字符串 · 同子系统内唯一 · **稳定** | 完成态按它记录；**改标题别改 id** |
| `tasks[].title` | 是 | 字符串 ≤120 | 现场实施看到的任务名 |
| `tasks[].desc` | 否 | 字符串 ≤1000 | 补充说明（建议写清） |
| `sql` | 否 | 数组（无则 `[]`） | 本版本 SQL 脚本 |
| `sql[].id` | 是 | 字符串 · 唯一 · 稳定 | |
| `sql[].file` | `file`/`content` 二选一 | 仓内相对路径 | **推荐**：引用真实 `.sql` 文件 |
| `sql[].content` | `file`/`content` 二选一 | 字符串 | `file` 缺时用；能用 `file` 就别内联 |
| `sql[].desc` | 否 | 字符串 | 一句话说明 |

> JSON 必须合法（intake 用原生 `JSON.parse` 读）。字段名严格照上表，别自造。

---

## 3. SQL 文件约定

- 放 `sql/` 下，**一个变更一个文件**，文件名建议带版本，如 `2.8.0_add_index.sql`。
- **每个脚本要能独立、幂等地在目标库执行**（实施手动跑）：建议 `ADD COLUMN IF NOT EXISTS` / `CREATE INDEX IF NOT EXISTS` / 先判存在，避免重复执行报错。
- 只放 DDL/DML 升级语句；**别放业务数据、密钥、环境相关的东西**。

---

## 4. intake 怎么用这两份文件（理解行为，避免踩坑）

- intake 从各子系统仓 **读 `docs/deploy/` 目录（最新代码 HEAD）**，文件名 = 版本，**跨子系统按版本聚合**。
- **首次部署**（该医院该产品**现场版本为空 = 未部署**）→ 累积**所有 ≤ 最新版本**的 `tasks` + `sql` = 从零全装一遍；实施做完设现场版本。
- **跨版本更新**（现场版本有值）→ 只累积 **`(现场版本, 目标版本]`** 区间的版本文件。
- **SQL 合并**：区间内所有 `sql` 被 intake 按版本序**拼成一个 `.sql` 文件**给实施下载，一次跑完（现场不必逐个脚本找）。
- 因此的铁律：**每版只写本版 delta**，别把历史步骤/SQL 重复写进新版本文件（否则跨多版会累积重复项）。

> **🔁 2026-08-05 更新（核心更新流·发包审核快照）**：产品侧产出**完全不变**（仍是本规范的 `docs/deploy/<版本>.json` 目录形态，读 @HEAD）。变化只在 intake 内部：**你写的清单/SQL 是「草稿源」**——运营在**发包（上传包）时**会从代码拉出 `(起始版本, 目标版本]` 累积草稿，**人工审核（可增删改标题/说明/SQL 正文）后冻结成快照**存进该批次；实施现场执行的是这份**审核过的快照**（不是实时读你代码）。含义：
> - 你照常一版一文件写清晰的 delta 即可；**运营审核是安全阀**（现场看到的清单经人过目、SQL 正文发包时已固化，之后即使你改了代码也不影响已发批次）。
> - `sql[].file` 引用的脚本正文在**发包那一刻**被读出冻结进批次快照；所以**发包前**把 SQL 脚本按本规范 §3（独立、幂等）写好放进仓即可。

## 5. 完整示例（药师工作站 · kwsb 子系统 · 2.8.0 版）

`docs/deploy/2.8.0.json`：
```json
{
  "tasks": [
    { "id": "stop",   "title": "停应用服务",         "desc": "通知现场用户后停止抗网上报服务" },
    { "id": "deploy", "title": "部署 2.8.0 包",       "desc": "覆盖安装本版本应用与依赖" },
    { "id": "runsql", "title": "执行数据库升级 SQL",  "desc": "按 intake 生成的合并脚本在目标库执行" },
    { "id": "verify", "title": "回归验证",            "desc": "核心上报流程冒烟通过" }
  ],
  "sql": [
    { "id": "s1", "file": "sql/2.8.0_add_flag.sql", "desc": "上报表加 demo_flag 列" }
  ]
}
```

`sql/2.8.0_add_flag.sql`：
```sql
-- 幂等：列已存在则跳过
ALTER TABLE kwsb_report ADD COLUMN IF NOT EXISTS demo_flag TINYINT DEFAULT 0;
```

## 6. Do / Don't

**✅ Do**
- 一版一文件，文件名 = 版本号 = git tag。
- 每版只写**本版新增**的实施步骤与 SQL。
- SQL 脚本独立、幂等、可重复执行不报错。
- `id` 稳定（现场完成态按 id 记）。

**❌ Don't**
- 别改已发布版本文件里的 `id`（会丢现场完成态）。
- 别把全部历史步骤堆进每个新版本文件。
- 别在 JSON 里塞大段 SQL（用 `file` 引用脚本）。
- 别放密钥 / 业务数据 / 环境相关内容。

---

## 7. 给「模型生成」用的产出约束（可直接放进生成规范/提示）

> 当你为某产品的某个**新版本**产出交付时，除业务代码外，**必须在该子系统仓额外产出**：
> 1. `docs/deploy/<本版本号>.json`（版本号与 git tag 一致），含**本版本**的实施任务 `tasks` + 本版本 SQL 引用 `sql`，格式严格遵循本规范 §2；
> 2. `sql/` 下对应的 `.sql` 脚本（独立、幂等）。
>
> 只写**本版本相对上一版新增的 delta**，不重复历史；JSON 合法、字段名照 §2、`id` 稳定。

---

## 8. 容错说明（intake 侧，给你安心逐步落地）

目录 / 文件缺失、JSON 非法、SQL 文件读不到 —— intake **一律静默跳过、不报错**，对应清单为空并提示"该版本未在代码中声明部署清单"。所以：**先建空目录不影响使用，逐版本补齐即可**，不必一次到位。
